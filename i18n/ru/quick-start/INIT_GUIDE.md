# Repomix — Универсальный гайд init/update/reinit для AI-агентов (v2)

> **Назначение:** этот документ — инструкция для AI-агента. Прочитай его и
> выполни шаги, чтобы развернуть (или обновить) Repomix-индекс контекста в
> любом проекте пользователя.
>
> **Ключевая идея v2:** один гигантский `output.xml` — антипаттерн. На
> реальных проектах он перерастает окно контекста модели (Symfony-бэкенд на
> 452 файла дошёл до ~258K токенов — мгновенное переполнение 256K-окна *ещё до
> начала задачи*). Вместо этого индекс — набор **семантических доменных
> пакетов**, каждый под потолком токенов, плюс маленький **каталог**, плюс
> короткая таблица маршрутизации в AGENTS.md. Агент грузит каталог и МАКСИМУМ
> ОДИН доменный пакет на задачу.
>
> **Эталонные шаблоны** лежат рядом с этим гайдом в `quick-start/templates/`:
> скрипт обновления, git-хуки, установщик хуков, примеры манифеста и
> pack-конфигов, секция AGENTS.md. Копируй и адаптируй их — не перепечатывай
> с нуля.

---

## Промпты для пользователя (вставить в сессию AI-агента в целевом проекте)

**Свежий проект (init):**

> Прочитай quick-start/INIT_GUIDE.md из <путь-к-этому-репо> и инициализируй
> пакетный Repomix-индекс в этом проекте (режим init). Моё окно контекста —
> <256k/200k/1m>. Покажи предлагаемую таблицу пакетов до записи конфигов.

**Уже инициализированный проект — обычная пересборка (update):**

> Запусти scripts/update-repomix-index.sh и доложи статус пакетов. Если
> какой-то пакет превысил потолок — скажи мне, ничего не перенарезай без
> моего согласия.

**Уже инициализированный проект — старый монолитный индекс или устаревшая
нарезка (reinit):**

> Прочитай quick-start/INIT_GUIDE.md из <путь-к-этому-репо> и
> ПЕРЕинициализируй Repomix-индекс в этом проекте (режим reinit). Тут может
> быть старый .repomix/output.xml, старый repomix.config.json и старые
> git-хуки — померь всё с нуля, предложи новую нарезку на пакеты, покажи diff
> с текущей схемой, сделай backup старых конфигов и мигрируй. Не удаляй мои
> ручные правки repomix.packs.json, не показав их мне.

## Выбор режима (агент: сделай это первым)

Определи текущее состояние проекта и выбери режим:

| Состояние | Режим |
|-----------|-------|
| Нет `repomix.config.json`, нет `.repomix/` | **init** |
| Есть `repomix.packs.json` | **update** (или **reinit**, если пользователь просил перенарезку) |
| Только монолитный `repomix.config.json` + `.repomix/output.xml` | **update-legacy** → рекомендуй **reinit**, если монолит >150K токенов |

Оценка размера монолита без сборки: `токены ≈ байты / 4` для существующего
XML, либо `repomix --token-count-tree` (см. Фазу 2).

## Профили токен-бюджета (константы)

| Профиль окна | Потолок пакета | Бюджет на сессию | Цель каталога |
|--------------|---------------|------------------|---------------|
| `256k` (дефолт, консервативный) | **80K** | каталог + макс. 1 доменный пакет | 5–15K |
| `200k` | 60K | каталог + макс. 1 доменный пакет | 5–15K |
| `1m` | 150K | каталог + 1–2 доменных пакета | 5–15K |

Метрика успеха: агент с окном 256K **никогда** не читает дамп ≥150K целиком.
Комфортное чтение целиком — до ~80–100K.

Порог склейки: домены меньше **15K** токенов склеиваются в общий пакет
`platform` (или `aux`) вместо отдельного файла — 20 крошечных пакетов так же
вредны для маршрутизации, как один гигантский.

# Режим: init

## Фаза 0: предварительный анализ

Спроси пользователя (пропусти очевидное из структуры проекта):

1. **Тип проекта / стек?** (определяет include-паттерны)
2. **Окно контекста?** (`256k` дефолт / `200k` / `1m`) — задаёт потолок пакета
3. **Legacy / архивные папки**, которые исключить полностью?
4. **Приоритет: экономия токенов или полнота?** Для **кода** дефолт —
   `compress: true, removeComments: true, removeEmptyLines: true`. Для
   **баз знаний / прозы** — всегда `compress: false`, см. отдельную секцию в
   конце.

Автоматический анализ:

```bash
# Структура
find . -maxdepth 3 -type d ! -path '*/node_modules/*' ! -path '*/.git/*' ! -path '*/vendor/*' ! -path '*/target/*' ! -path '*/dist/*' ! -path '*/__pycache__/*' ! -path '*/.venv/*' | sort

# Есть ли Git?
git rev-parse --is-inside-work-tree 2>/dev/null && echo "GIT: YES" || echo "GIT: NO"

# Существующие хуки / AGENTS.md
ls .git/hooks/ .husky/ 2>/dev/null; test -f AGENTS.md && echo "AGENTS.md: EXISTS"
```

## Фаза 1: установка / поиск repomix

```bash
command -v repomix && repomix --version || npm install -g repomix
```

Нет глобальной установки → `npx --yes repomix` работает везде, где есть node.
(Скрипт обновления сам умеет fallback на npx.)

**Windows:** всё в этом гайде выполняется в Git Bash (идёт в комплекте с Git
for Windows). Git запускает `.sh`-хуки через собственный `sh.exe`, так что
хукам ничего дополнительно не нужно. Для ручных запусков из cmd есть
`.bat`-обёртки в шаблонах.

## Фаза 2: замер

Проведи перепись токенов до любых решений:

```bash
# Токены по папкам/файлам (файлы >1K токенов)
repomix --token-count-tree 1000 --no-files -o /dev/null 2>/dev/null || repomix --token-count-tree 1000
```

Если на огромном репо это медленно — оцени: `токены ≈ символы / 3.8`
(o200k_base, смешанный код). Зафиксируй: всего токенов, по верхним папкам,
топ-10 самых жирных файлов.

**Маленькие проекты тоже получают пакеты.** Даже если весь проект (со сжатием)
влезает под потолок — НЕ откатывайся к единому монолитному `output.xml`:
проекты растут незаметно, а у монолита нет сигнализации роста. Вместо этого
создай минимальную пакетную схему — `catalog` + один пакет `app` со всем
содержимым — под тем же манифестом. Это ничего не стоит, а предупреждение о
потолке в скрипте обновления само скажет, когда проект перерос один пакет и
нужна настоящая доменная нарезка (reinit).

## Фаза 3: нарезка доменов (индивидуальная часть — никогда не хардкодь)

**Эта фаза — решение под конкретный проект, не шаблон.** Примеры в
`templates/` показывают только ФОРМАТ ФАЙЛОВ — реальная нарезка должна
родиться из замера *этого* проекта и понимания, что агента будут просить в
нём делать. Каждый стек режется по-своему:

- **Бэкенд в стиле Symfony/Laravel:** домены идут по бизнес-сущностям сквозь
  слои (`src/Controller/Order*` + `src/Service/Order/` + их тесты = один
  пакет `orders`), миграции отдельно, фреймворковый `vendor/` исключён.
- **WordPress и подобные CMS:** большая часть дерева — системный код, который
  никто не редактирует (`wp-admin/`, `wp-includes/`, чужие плагины), и он
  ОГРОМНЫЙ — исключай его из пакетов полностью (максимум — присутствие в
  дереве каталога). Индексируй то, что реально редактируется: кастомную тему,
  кастомные плагины, экспорты ACF/конфигов. Пакет «весь проект» для
  WordPress-сайта — на 95% мёртвый груз.
- **JS/TS-монорепа:** пакеты по workspace/пакетам, общие библиотеки —
  отдельным пакетом; сгенерированные бандлы и дампы дизайн-токенов исключены.
- **Data/ML-проект:** ноутбуки и датасеты исключены или только в каталоге;
  код пайплайнов/моделей пакуется по стадиям пайплайна.

Вопрос для каждой папки-кандидата: *«будут ли агента когда-нибудь просить это
менять, и нужно ли ему видеть это целиком?»* — тяжёлый, никогда не
редактируемый фреймворковый/системный/сгенерированный код исключается (или
только в каталоге), какого бы размера он ни был; пакеты существуют для
данных, которые важны.

Кластеризуй замеренное дерево в семантические домены **по типам задач,
которые будет получать агент**, а не по `src/` vs `tests/`:

1. **Кандидаты:** верхние папки (`src/Service/Task`, `app/modules/…`),
   префиксы имён (`Inspection*`, `Task*`, `Map*`) и тесты каждого домена
   (`tests/Service/Task` принадлежит пакету `tasks`, а НЕ пакету тестов).
2. **Склей** каждый домен меньше 15K в `platform`.
3. **Раздели** каждый домен больше потолка: по подпапкам, выносом его тестов
   в пакет `<домен>-tests` (только как крайняя мера) или выносом жирных
   one-off (импорты, сгенерированный код, fixtures) в отдельный редко
   загружаемый пакет.
4. `migrations` / дампы схем → отдельный пакет, грузится только для задач по
   схеме БД.
5. Всегда создавай пакет **catalog**: только метаданные (`"files": false`),
   полное дерево каталогов, без тел кода.

**Что исключать из каждого пакета:** vendor, node_modules, var, dist, build,
lock-файлы, бинарники, `.git`, папки IDE, сам `.repomix/`, секреты/pem,
сгенерированные бандлы, огромные fixtures/xlsx/json-дампы, **и `AGENTS.md` /
`CLAUDE.md`** — они уже в системном промпте; их индексация удваивает цену.

Пример нарезки реального Symfony-бэкенда (~258K монолит, окно 256K) — образец
*метода*, не шаблон для всех:

| Пакет | Содержимое | ~Токены |
|-------|-----------|---------|
| catalog | дерево + инвентарь | 9K |
| inspections | карточки, протоколы, суд + их тесты | 72K |
| tasks | workflow, автозадачи + тесты | 40K |
| map, logs | малые домены + тесты | 13–14K каждый |
| platform | конфиг, импорт, админка, glossary, support | 25–40K |
| migrations | схема | 22K |

## Фаза 4: покажи таблицу, потом пиши конфиги

**Покажи пользователю предлагаемую таблицу** (пакет / ~токены / глобы /
when_to_load) и дай поправить её **до** записи чего-либо. Нарезка И ЕСТЬ
индивидуальная настройка проекта.

После согласования запиши:

```
repomix.packs.json           # манифест — коммитится (шаблон: templates/repomix.packs.json.example)
.repomix/configs/<pack>.json # per-pack конфиги — коммитятся (templates/configs/*.example)
repomix.config.json          # опциональный базовый конфиг для голого `repomix`;
                             # если оставляешь — направь его на каталог, не на монолит
```

Per-pack конфиги (через `repomix -c`) используются вместо флагов `--include`,
чтобы семантика мержа CLI/конфига никогда не преподнесла сюрприз. Массив
`watch` каждого пакета в манифесте перечисляет его исходные корни — скрипт
обновления использует их для skip-if-fresh проверок.

## Фаза 5: инфраструктура (скрипты + хуки)

Скопируй из `quick-start/templates/`:

```
scripts/update-repomix-index.sh    # chmod +x
scripts/update-repomix-index.bat   # ручная обёртка для Windows
scripts/install-git-hooks.sh       # chmod +x
scripts/install-git-hooks.bat
.githooks/pre-push post-commit post-merge post-rewrite   # chmod +x
```

Затем:

```bash
mkdir -p .repomix
./scripts/install-git-hooks.sh
```

В `.gitignore`:

```
.repomix/*.xml
.repomix/update.log
.repomix/update.lock
.repomix/PACKS_STATUS.md
```

**Коммить** `repomix.packs.json`, `.repomix/configs/`, `scripts/`,
`.githooks/`. Сами XML-пакеты остаются локальными — именно поэтому механика
пересборки обязана быть надёжной (PATH-бутстрап, npx-fallback, nohup, лог,
всегда exit 0 — всё это уже внутри шаблонного скрипта; не упрощай его).

Почему именно эти хуки: одного `post-commit` мало — `git push` его не
вызывает, а merge/rebase меняют файлы без коммитов. `pre-push` работает
синхронно (со stdin, отвязанным от git — git подаёт туда refs); остальные —
в фоне через nohup, чтобы git оставался быстрым.

Задокументируй в README (одна строка): *«После clone выполните
`./scripts/install-git-hooks.sh`, чтобы включить автопересборку AI-индекса.»*

Нет git в проекте → пропусти хуки; скрипт обновления сам по себе — ручная
точка входа `reindex`.

## Фаза 6: первая сборка + проверка

```bash
./scripts/update-repomix-index.sh --force
cat .repomix/PACKS_STATUS.md
```

Проверь: каждый пакет под потолком; каталог в диапазоне 5–15K; скрипт
предупреждает о любом пакете сверх потолка. Чини нарезку сейчас, не потом.

## Фаза 7: AGENTS.md

Скопируй блок из `templates/AGENTS_SECTION.md` в AGENTS.md проекта, заполни
таблицу пакетов. Жёсткие правила:

- **Никогда** не пиши «прочитай весь output.xml перед большими задачами» —
  именно эта инструкция взрывает окна контекста.
- Держи секцию в ~30–40 строк. Длинные архитектурные тексты — в `docs/`.
- Не хардкодь числа токенов, которые протухнут — таблица ссылается на
  `.repomix/PACKS_STATUS.md` за свежими значениями.
- Сохрани правило «если потерял нить посреди сессии» из шаблона: оно велит
  агенту перечитать маленькую таблицу маршрутизации вместо перечитывания
  пакетов, когда длинный чат начинает деградировать.

## Чек-лист init

```
[ ] repomix доступен (глобально или npx)
[ ] Перепись токенов сделана; домены нарезаны; таблица согласована с пользователем
[ ] repomix.packs.json + .repomix/configs/*.json записаны и закоммичены
[ ] scripts/ + .githooks/ скопированы, исполняемы, закоммичены; хуки установлены
[ ] .gitignore закрывает артефакты .repomix/
[ ] Первая сборка: все пакеты под потолком, каталог 5–15K
[ ] AGENTS.md: таблица пакетов + правила загрузки (коротко!), без советов «читай всё»
```

# Режим: update

Обычная пересборка — её запускают хуки; агенты/пользователи могут запускать
вручную:

```bash
./scripts/update-repomix-index.sh            # пропускает свежие пакеты
./scripts/update-repomix-index.sh --force    # пересобирает всё
```

Поведение (уже реализовано в шаблонном скрипте — не трогай его):

- Skip-if-fresh на пакет по `watch`-корням манифеста (сравнение mtime);
  правки манифеста/конфига тоже триггерят пересборку.
- Пишет `.repomix/PACKS_STATUS.md` со свежими оценками токенов.
- **Предупреждает**, когда пакет превышает потолок — агент обязан после
  этого *предложить* пользователю перенарезку (reinit), никогда не резать
  молча и никогда молча не давать пакетам раздуваться.
- Legacy-режим: нет манифеста → обычная сборка монолита + предупреждение при
  >150K с рекомендацией reinit.
- Никогда не блокирует git (везде exit 0), лог в `.repomix/update.log`.

Правила агента в режиме update:

1. Не переписывай `repomix.packs.json` — пользователь мог настроить его
   вручную.
2. Новая верхняя папка, не попадающая ни в один пакет → скажи пользователю,
   предложи добавить в существующий пакет или создать новый.
3. Предупреждение о потолке → предложи reinit; выполняй только после
   согласия.
4. **AGENTS.md мержится, никогда не заменяется.** Это живой файл, который
   команда и агенты дорабатывают между запусками. Если его Repomix-секцию
   надо освежить — прочитай текущий файл, поправь ТОЛЬКО изменившееся
   (строки таблицы пакетов, протухшие числа), сохрани каждое локальное
   дополнение и покажи diff до записи.

# Режим: reinit (миграция / перенарезка)

Когда: монолит >150K; пакет перерос потолок; структура доменов уехала; или
проект хочет получить фиксы этого гайда поверх старой схемы («подкинуть
скрипт заново и переразвернуть»).

1. **Инвентаризуй старую схему:** существующие `repomix.config.json`,
   `.repomix/*.xml`, `repomix.packs.json`, хуки в `.git/hooks/` и `.husky/`,
   секцию Repomix в AGENTS.md. Ожидаемые старые поломки: только post-commit
   хук, молчаливый no-op `command -v repomix`, фон без nohup, конфиг в
   .gitignore, совет «читай весь индекс» в AGENTS.md.
2. **Backup:** скопируй старые конфиги + манифест в `.repomix/backup-<дата>/`
   (никогда не удаляй файлы пользователя).
3. **Перемерь** с нуля (Фаза 2) и **перенарежь** домены (Фаза 3).
4. **Покажи diff**: старые пакеты vs новые (или «монолит → N пакетов») с
   числами токенов. Если пользователь правил манифест руками — покажи его
   правки явно до любой замены. Жди согласия.
5. Запиши конфиги (Фаза 4), обнови скрипты/хуки из актуальных шаблонов
   (Фаза 5 — перезапиши старые копии `update-repomix-index.sh`/хуков;
   установщик сам бэкапит чужие хуки), пересобери (Фаза 6), обнови секцию
   AGENTS.md (Фаза 7) — **удали** старую инструкцию «DO read output.xml» и
   протухшие числа токенов. **AGENTS.md мержь, не пересоздавай**: скрипты и
   хуки безопасно перезаписывать из шаблонов, но AGENTS.md накапливает
   собственные правила проекта между запусками — правь Repomix-секцию по
   месту, сохраняй всё остальное, покажи diff до записи.
6. Удали устаревший монолитный `output.xml` с диска, если пакеты его
   заменяют (после согласия пользователя), либо оставь с пометкой «не читать
   целиком» в AGENTS.md, если пользователь хочет CI-артефакт.

# Базы знаний и прозаические проекты (не код)

Два жёстких отличия от кода:

1. **`compress: false`, `removeComments: false` — всегда.** Tree-sitter
   сжатие вырезает «тела», что для кода приемлемо (структура выживает), а для
   текста знаний уничтожает ровно то содержимое, ради которого база
   существует. Формулировки, нюансы и целые абзацы — И ЕСТЬ полезная
   нагрузка. Цена — пакеты крупнее; компенсируй более агрессивной нарезкой,
   а не сжатием.
2. **Пакеты идут по секциям контента, а не по доменам кода:** например, база
   писателя → `core` (профиль, принципы, голос, таблицы маршрутизации),
   `domain`, `insights`, и библиотека полка-за-полкой (`library-craft`,
   `library-marketing`, …). «Библиотека учебных книг» НИКОГДА не делит пакет
   с рабочими знаниями — книги грузятся только когда задача о них.

Для баз, развёрнутых из AI Knowledge Engine, это автоматизировано: секция
`index:` в `kb.config.yml` + `kb_reindex.py` собирают пакеты и авто-разделяют
переросшие секции по подпапкам (см. `knowledge-base/05_INDEX.md`). Для
ad-hoc прозаических проектов применяй этот гайд вручную с теми же профилями
и правилом `compress: false`; бинарные источники (docx/pdf/pptx) сначала
конвертируются в Markdown (pandoc / marker), оригиналы исключаются, короткие
описания — в `assets-index/*.md`.
