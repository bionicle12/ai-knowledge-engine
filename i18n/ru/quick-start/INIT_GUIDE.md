# Repomix — Универсальный гайд init/update/reinit для AI-агентов (v2)

> **Назначение:** этот документ — инструкция для AI-агента. Прочитай его и
> выполни шаги, чтобы развернуть (или обновить) Repomix-индекс контекста в
> любом проекте пользователя.
>
> **Ключевая идея v2:** один гигантский `output.xml` — антипаттерн. На
> реальных проектах он перерастает окно контекста модели (Symfony-бэкенд на
> 452 файла дошёл до ~258K токенов — мгновенное переполнение 256K-окна *ещё до
> начала задачи*). Вместо этого индекс — набор **семантических доменных
> пакетов**, каждый под потолком токенов, плюс маленький **каталог**, плюс
> короткая таблица маршрутизации в AGENTS.md. Агент грузит каталог и МАКСИМУМ
> ОДИН доменный пакет на задачу.
>
> **Эталонные шаблоны** лежат рядом с этим гайдом в `quick-start/templates/` checkout AI Knowledge Engine:
> скрипт обновления, git-хуки, установщик хуков, примеры манифеста и конфигов пакетов, секция AGENTS.md. Копируй их в точные места из фазы 5 (никогда в собственную папку `templates/` проекта — Twig, Blade, Django… используют это имя) и адаптируй; не перепечатывай с нуля.

## Выбор режима (агент: сделай это первым)

Определи текущее состояние проекта и выбери режим:

| Состояние | Режим |
|-----------|-------|
| Нет `repomix.config.json`, нет `.repomix/` | **init** |
| Есть `repomix.packs.json` | **update** (или **reinit**, если пользователь просил перенарезку) |
| Только монолитный `repomix.config.json` + `.repomix/output.xml` | **update-legacy** → рекомендуй **reinit**, если монолит >150K токенов |

Оценка размера монолита без сборки: `tokens ≈ bytes / 4` для существующего
XML, либо `repomix --token-count-tree` (см. Фазу 2).

| Профиль окна | Потолок пакета | Бюджет на сессию | Цель каталога |
|--------------|---------------|------------------|---------------|
| `400k` (Codex) | **120K** | каталог + макс. 1 доменный пакет | 5–15K |
| `256k` (Cursor / консервативный дефолт) | **80K** | каталог + макс. 1 доменный пакет | 5–15K |
| `200k` | 60K | каталог + макс. 1 доменный пакет | 5–15K |
| `1m` | 150K | каталог + 1–2 доменных пакета | 5–15K |

Метрика успеха: агент с окном 256K **никогда** не читает дамп ≥150K целиком.
Комфортное чтение целиком — до ~80–100K.

Порог склейки: домены меньше **15K** токенов склеиваются в общий пакет
`platform` (или `aux`) вместо отдельного файла — 20 крошечных пакетов так же
вредны для маршрутизации, как один гигантский.

# Режим: init

## Фаза 0: предварительный анализ

Спроси пользователя (пропусти очевидное из структуры проекта):

1. **Тип проекта / стек?** (определяет include-паттерны)
2. **Окно контекста?** (`400k` Codex / `256k` дефолт / `200k` / `1m`) — задаёт потолок пакета
3. **Legacy / архивные папки**, которые исключить полностью?
4. **Приоритет: экономия токенов или полнота?** Для **кода** дефолт —
   `compress: true, removeComments: true, removeEmptyLines: true`. Для
   **баз знаний / прозы** — всегда `compress: false`, см. отдельную секцию в
   конце.

Автоматический анализ:

```bash
# Structure
find . -maxdepth 3 -type d ! -path '*/node_modules/*' ! -path '*/.git/*' ! -path '*/vendor/*' ! -path '*/target/*' ! -path '*/dist/*' ! -path '*/__pycache__/*' ! -path '*/.venv/*' | sort

# Git present?
git rev-parse --is-inside-work-tree 2>/dev/null && echo "GIT: YES" || echo "GIT: NO"

# Existing hooks / hook manager / AGENTS.md
ls "$(git rev-parse --git-path hooks)" .githooks/ .husky/ 2>/dev/null
git config --get core.hooksPath && echo "HOOK MANAGER: core.hooksPath is set (see Phase 5)"
test -f AGENTS.md && echo "AGENTS.md: EXISTS"
```

## Фаза 1: установка / поиск repomix

```bash
command -v repomix && repomix --version || npm install -g repomix
```

Нет глобальной установки → `npx --yes repomix@1.14.0` работает везде, где есть node. Скрипт обновления автоматически переходит к npx и всегда запускает версию из `repomix_version` манифеста (по умолчанию `1.14.0` — на ней проверены ignore-глобы шаблонов), никогда «latest». PACKS_STATUS.md указывает версию repomix последней сборки.

**Windows:** всё в этом гайде выполняется в Git Bash (идёт в комплекте с Git
for Windows). Git запускает `.sh`-хуки через собственный `sh.exe`, так что
хукам ничего дополнительно не нужно. Для ручных запусков из cmd есть
`.bat`-обёртки в шаблонах.

## Фаза 2: замер

Проведи перепись токенов до любых решений:

```bash
# Per-directory/per-file token costs (files >1K tokens)
repomix --token-count-tree 1000 --no-files -o /dev/null 2>/dev/null || repomix --token-count-tree 1000
```

Если на огромном репо это медленно — оцени: `tokens ≈ chars / 3.8`
(o200k_base, смешанный код). Зафиксируй: всего токенов, по верхним папкам,
топ-10 самых жирных файлов.

**Маленькие проекты тоже получают пакеты.** Даже если весь проект (со сжатием)
влезает под потолок — НЕ откатывайся к единому монолитному `output.xml`:
проекты растут незаметно, а у монолита нет сигнализации роста. Вместо этого
создай минимальную пакетную схему — `catalog` + один пакет `app` со всем
содержимым — под тем же манифестом. Это ничего не стоит, а предупреждение о
потолке в скрипте обновления само скажет, когда проект перерос один пакет и
нужна настоящая доменная нарезка (reinit).

## Фаза 3: нарезка доменов (индивидуальная часть — никогда не хардкодь)

**Эта фаза — решение под конкретный проект, не шаблон.** Примеры в
`templates/` показывают только ФОРМАТ ФАЙЛОВ — реальная нарезка должна
родиться из замера *этого* проекта и понимания, что агента будут просить в
нём делать. Каждый стек режется по-своему:

- **Бэкенд в стиле Symfony/Laravel:** домены идут по бизнес-сущностям сквозь
  слои (`src/Controller/Order*` + `src/Service/Order/` + их тесты = один
  пакет `orders`), миграции отдельно, фреймворковый `vendor/` исключён.
- **WordPress и подобные CMS:** большая часть дерева — системный код, который
  никто не редактирует (`wp-admin/`, `wp-includes/`, чужие плагины), и он
  ОГРОМНЫЙ — исключай его из пакетов полностью (максимум — присутствие в
  дереве каталога). Индексируй то, что реально редактируется: кастомную тему,
  кастомные плагины, экспорты ACF/конфигов. Пакет «весь проект» для
  WordPress-сайта — на 95% мёртвый груз.
- **JS/TS-монорепа:** пакеты по workspace/пакетам, общие библиотеки —
  отдельным пакетом; сгенерированные бандлы и дампы дизайн-токенов исключены.
- **Data/ML-проект:** ноутбуки и датасеты исключены или только в каталоге;
  код пайплайнов/моделей пакуется по стадиям пайплайна.

Вопрос для каждой папки-кандидата: *«будут ли агента когда-нибудь просить это
менять, и нужно ли ему видеть это целиком?»* — тяжёлый, никогда не
редактируемый фреймворковый/системный/сгенерированный код исключается (или
только в каталоге), какого бы размера он ни был; пакеты существуют для
данных, которые важны.

Кластеризуй замеренное дерево в семантические домены **по типам задач,
которые будет получать агент**, а не по `src/` vs `tests/`:

1. **Кандидаты:** верхние папки (`src/Service/Task`, `app/modules/…`),
   префиксы имён (`Inspection*`, `Task*`, `Map*`) и тесты каждого домена
   (`tests/Service/Task` принадлежит пакету `tasks`, а НЕ пакету тестов).
2. **Склей** каждый домен меньше 15K в `platform`.
3. **Раздели** каждый домен больше потолка: по подпапкам, выносом его тестов
   в пакет `<domain>-tests` (только как крайняя мера) или выносом жирных
   one-off (импорты, сгенерированный код, fixtures) в отдельный редко
   загружаемый пакет.
4. `migrations` / дампы схем → отдельный пакет, грузится только для задач по
   схеме БД.
5. Всегда создавай пакет **catalog**: только метаданные (`"files": false`),
   полное дерево каталогов, без тел кода.

**Что исключать из каждого пакета:** vendor, node_modules, var, dist, build,
lock-файлы, бинарники, `.git`, папки IDE, сам `.repomix/`, секреты (файлы `.env`, ключи, сертификаты — шаблоны конфигов заканчиваются этими паттернами в форме, работающей на repomix 1.14.0; сохраните их),
сгенерированные бандлы, огромные fixtures/xlsx/json-дампы, **и `AGENTS.md` /
`CLAUDE.md`** — они уже в системном промпте; их индексация удваивает цену.

Пример нарезки реального Symfony-бэкенда (~258K монолит, окно 256K) — образец
*метода*, не шаблон для всех:

| Пакет | Содержимое | ~Токены |
|-------|-----------|---------|
| catalog | дерево + инвентарь | 9K |
| inspections | карточки, протоколы, суд + их тесты | 72K |
| tasks | workflow, автозадачи + тесты | 40K |
| map, logs | малые домены + тесты | 13–14K каждый |
| platform | конфиг, импорт, админка, glossary, support | 25–40K |
| migrations | схема | 22K |

## Фаза 4: покажи таблицу, потом пиши конфиги

**Покажи пользователю предлагаемую таблицу** (пакет / ~токены / глобы / when_to_load) и дай поправить её **до** записи чего-либо. Нарезка И ЕСТЬ индивидуальная настройка проекта.

После согласования запиши:

```
repomix.packs.json           # манифест — коммитится (шаблон: templates/repomix.packs.json.example)
.repomix/configs/<pack>.json # конфиги пакетов — коммитятся (templates/configs/*.example)
repomix.config.json          # необязательный базовый конфиг для запуска голого `repomix`;
                             # если оставляешь — направь его на каталог, не на монолит
```

Конфиги пакетов (через `repomix -c`) используются вместо флагов `--include`, чтобы семантика слияния CLI/конфигурации не преподнесла сюрпризов. Массив `watch` каждого пакета в манифесте перечисляет исходные папки/файлы — реальные пути, никогда не префиксы имён (`docs/plan/08.`) и не глобы: скрипт обновления пересобирает пакет при добавлении, удалении, переименовании или изменении файла под ними и сообщает о несуществующих путях watch. Объединение всех watch-путей — то, что проверка покрытия (фаза 6) ожидает найти ровно в одном пакете; намеренно исключённые из всех пакетов файлы (fixtures, сгенерированный код) перечисли в `coverage_ignore` манифеста (git pathspecs, `*` также совпадает с `/`). Не записывай числа токенов в манифест.

**Ловушка ignore-глобов (проверено на repomix 1.14.0).** Если конфигурация содержит список `include`, ignore `customPatterns` вида `**/*Name*` или `**/.env*` (голый префикс `**/`, без расширения файла) **молча не применяются** — пакет собирается без ошибок и выходит в 2–4 раза толще замеренного (или содержит файлы `.env`). Паттерны с явным корнем (`src/**/*Name*`), расширением (`**/*Name*.php`) или удвоенным префиксом (`**/**/*Name*`) РАБОТАЮТ. Всегда пиши междоменные исключения в рабочей форме, например `src/**/*Order*.php` + `tests/**/*Order*.php`, никогда `**/*Order*`. Другие версии repomix могут вести себя иначе — поэтому резервный npx закреплён на версии, а скрипт обновления перепроверяет покрытие при каждом запуске.

**Принадлежность между пакетами.** Домены по префиксам имён пересекаются: файл может совпасть с include двух пакетов (`InspectionProtocol` подходит и под `*Inspection*`, и под `*Protocol*`; `Service/Task/CourtDecisionResolver` подходит под глоб папки tasks и глоб имени court). Определи приоритет доменов, затем добавь проигравшему пакету явное исключение паттернов победителя — каждый файл должен попасть РОВНО в один пакет. Проверка покрытия в фазе 6 находит пропуски.

## Фаза 5: инфраструктура (скрипты + хуки)

Копируй каждый шаблон точно в указанное место в **корне проекта** (`<engine>` — checkout AI Knowledge Engine, в котором лежит этот гайд). Никогда не копируй саму папку `templates/`: у многих проектов уже есть свои `templates/` (Twig, Blade, Django, Jinja), и файлам Repomix там не место.

| Из `<engine>/quick-start/templates/` | В `<project>/` |
|----------------------------------------|-----------------|
| `scripts/update-repomix-index.sh` (+ `.bat`) | `scripts/update-repomix-index.sh` (+ `.bat`) — `chmod +x` для `.sh` |
| `scripts/install-git-hooks.sh` (+ `.bat`) | `scripts/install-git-hooks.sh` (+ `.bat`) — `chmod +x` для `.sh` |
| `githooks/post-commit`, `post-merge`, `post-rewrite`, `post-checkout`, `pre-push` | `.githooks/<same name>` — `chmod +x` |
| `repomix.packs.json.example` | `repomix.packs.json` (заполненный, фаза 4) |
| `configs/catalog.json.example`, `configs/domain-pack.json.example` | `.repomix/configs/<pack>.json` (по одному на пакет, фаза 4) |
| `AGENTS_SECTION.md` | объединить с `AGENTS.md` (фаза 7) |

Затем:

```bash
mkdir -p .repomix
./scripts/install-git-hooks.sh
```

Установщик копирует хуки в папку, из которой git действительно запускает их (`git rev-parse --git-path hooks`, поэтому работает и из связанного worktree). Отличающийся существующий hook сохраняется рядом как резервная копия (`<hook>.bak-<timestamp>`), выводится diff. Если задан `core.hooksPath` (husky, lefthook, …), git игнорирует `.git/hooks`: установщик ничего не копирует, завершается с кодом 1 и печатает однострочные команды для добавления в хуки менеджера (`core.hooksPath=.githooks` распознаётся и работает как есть).

**Логика хуков конкретного проекта** (CI-проверка в `pre-push`, форматтер в `post-commit`) помещается в исполняемый `.githooks/<hook>.local`. Каждый шаблонный hook сначала запускает свой `.local` с аргументами и stdin от git; ошибка `pre-push.local` блокирует push. Сами хуки остаются идентичными шаблонам, поэтому обновление ничего не теряет.

В `.gitignore` добавляются (результаты сборки локальные, конфиги версионируются):

```gitignore
# Repomix index: build output stays local; configs are versioned
.repomix/*
!.repomix/configs/
```

Это покрывает пакеты, `PACKS_STATUS.md`, `coverage.txt`, состояние сборки (`packs.state`), журнал и его ротированную копию, блокировку и резервные копии reinit (`.repomix/backup-*/`). Скрипт обновления сообщает в PACKS_STATUS.md, когда `.gitignore` не покрывает его файлы.

В `.gitattributes` добавляются (sh-скрипты и хуки ломаются от CRLF при checkout в Windows, метки `.bat` — от LF):

```gitattributes
scripts/update-repomix-index.sh text eol=lf
scripts/install-git-hooks.sh text eol=lf
scripts/update-repomix-index.bat text eol=crlf
scripts/install-git-hooks.bat text eol=crlf
.githooks/* text eol=lf
```

**Закоммить** `repomix.packs.json`, `.repomix/configs/`, `scripts/`, `.githooks/`, `.gitignore`, `.gitattributes`. Сами XML-пакеты остаются локальными — именно поэтому механизм пересборки должен быть надёжным (настройка PATH, закреплённый резервный npx, nohup, блокировка, журналирование, всегда exit 0 — всё уже есть в шаблонном скрипте; не упрощай его).

Почему эти хуки: одного `post-commit` недостаточно — `git push` его не вызывает, merge/rebase меняют файлы без коммитов, переключение веток — без всего перечисленного (`post-checkout`, только переключения веток). `pre-push` работает синхронно (stdin отсоединён — git передаёт туда refs), но никогда не ждёт уже работающую сборку; остальные запускаются фоново через nohup, сохраняя быстрый git. Если хуки срабатывают подряд (rebase 5 коммитов, `commit --amend`), запуск, обнаруживший сборку в процессе, лишь ставит повторную проверку, которую работающая сборка выполнит по завершении — обычно две сборки, не более трёх проходов за запуск; проверка, поставленная после последнего прохода, ждёт следующего hook или ручного запуска. `git reset --hard` и `git stash` не вызывают хуков: изменения подхватит следующий hook или ручной запуск (свежесть определяется списком файлов и содержимым, поэтому ничего не теряется, только задерживается).

Добавь в README одну строку: *«После clone выполни `./scripts/install-git-hooks.sh`, чтобы включить автоматическую пересборку AI-индекса».*

Нет git в проекте → пропусти хуки; скрипт обновления сам служит ручной точкой входа `reindex` (без git он также не может проверить покрытие).

## Фаза 6: первая сборка и проверка

```bash
./scripts/update-repomix-index.sh --force
cat .repomix/PACKS_STATUS.md
```

Проверь в PACKS_STATUS.md: нет пакетов OVER или FAILED; каталог в диапазоне 5–15K (`files: false` может дать каталог меньше 5K — нормально, меньше затрат на маршрутизацию); нет раздела «Problems». Исправляй нарезку сейчас, не позже.

**Проверка покрытия (автоматически, при каждом запуске).** Одни размеры не доказывают правильность нарезки — молча потерянное исключение (ловушка глобов в фазе 4) или пересечение доменов дают правдоподобные пакеты, пока файлы остаются сиротами или индексируются дважды. Скрипт сравнивает текстовые файлы под всеми watch-путями (отслеживаемые git или неотслеживаемые, но не игнорируемые; исключены `AGENTS.md`, `CLAUDE.md`, `.repomix/` и секретные файлы, которые исключают шаблоны конфигов) с записями `<file path="…">` каждого пакета и сообщает в PACKS_STATUS.md:

- **files in no pack** (сироты) — добавь в пакет или в `coverage_ignore`, если исключение намеренное;
- **files in two or more packs** (дубликаты) — исправь межпакетными исключениями по приоритету владения из фазы 3.

Проверка знает исключения выше и `coverage_ignore`, но не собственный список исключений repomix (lock-файлы и подобное) и не `.repomixignore`: самостоятельно пропущенные repomix файлы показываются как «in no pack» — перечисли их в `coverage_ignore`. Вне рабочего дерева git проверка невозможна; PACKS_STATUS.md тогда сообщает «Coverage not checked» как примечание, а не проблему.

Полные списки — в `.repomix/coverage.txt`. Цель — 0 и 0. При реальном reinit проверка нашла 5 дублирующихся файлов и пакет platform, молча выросший с 34K до 160K без предупреждений сборки.

Тот же запуск ищет во всех пакетах строки, похожие на секреты (ключи GitHub, AWS, Slack, Stripe, OpenAI, приватные PEM-ключи), и фиксирует, что исключила собственная проверка секретов repomix — оба результата появляются в «Problems» (только пути файлов, никогда значения) и `.repomix/update.log`.

## Фаза 7: AGENTS.md

Скопируй блок `templates/AGENTS_SECTION.md` в AGENTS.md проекта, заполни таблицу пакетов. Строгие правила:

- **Никогда** не пиши «прочитай весь output.xml перед большими задачами» — именно эта инструкция переполняет контекст.
- Держи раздел в пределах ~30–40 строк. Длинное описание архитектуры помещается в `docs/`.
- **Никаких чисел токенов** нигде в AGENTS.md (в таблице шаблона нет столбца размера): они устаревают — пакет, указанный как «~72K», незаметно вырос до 217K. Размеры, флаги OVER/FAILED и проблемы находятся только в `.repomix/PACKS_STATUS.md`.
- Сохрани правило «пакет с OVER, FAILED или STALE в PACKS_STATUS.md никогда не загружается целиком».
- Сохрани правило восстановления «если потерял нить в середине сессии» из шаблона: оно велит перечитать небольшую таблицу маршрутизации, а не пакеты, когда длинный чат начинает деградировать.

# Режим: update

Обычная пересборка — её выполняют хуки; агенты/пользователи могут запускать вручную:

```bash
./scripts/update-repomix-index.sh            # rebuilds changed packs only
./scripts/update-repomix-index.sh --force    # rebuilds everything
./scripts/update-repomix-index.sh --check    # builds nothing: refreshes PACKS_STATUS.md,
                                             # exit 1 when it has warnings
```

Поведение (уже реализовано в шаблонном скрипте — сохрани его):

- Свежесть каждого пакета определяется списком файлов и состоянием индекса под `watch`-путями манифеста (git; без git обычный список файлов), плюс mtime файлов, запись пакета в манифесте и его конфигурация: добавленные, удалённые, переименованные и изменённые файлы вызывают пересборку. Первый запуск после обновления скрипта один раз пересобирает все пакеты.
- При каждом запуске записывается `.repomix/PACKS_STATUS.md`: для пакета — число токенов, сообщённое repomix, `ok`/`OVER` относительно потолка (и для свежих пакетов), `fresh`/`rebuilt`/`STALE`/`FAILED` и время сборки; заголовок со временем, HEAD и версией repomix; заметные строки для пакетов OVER/FAILED/STALE; раздел «Problems» (покрытие, несуществующие watch-пути, секреты, устаревший `.gitignore`, оставшийся монолитный `output.xml`).
- При ошибке сборки строка пакета остаётся `FAILED (old copy)` или `FAILED (no output)`, и следующая попытка повторяет сборку; журнал сохраняет настоящий код выхода и конец вывода repomix.
- Пакет, у которого `output.filePath` конфигурации не совпадает с `output` манифеста, не собирается: строка сообщает `FAILED (config writes …)`, а «Problems» называет оба пути (иначе repomix записал бы файл, о котором манифест не знает).
- XML-пакеты в `.repomix/`, которые больше не создаёт ни один пакет манифеста (переименованные или удалённые пакеты), удаляются (только файлы с заголовком repomix; `output.xml` лишь отмечается).
- **Предупреждает** о превышении потолка — агент должен *предложить* пользователю перенарезку (reinit), никогда не делать её молча и не позволять пакетам молча разрастаться.
- Legacy-режим: нет манифеста → обычная пересборка монолита с предупреждением при >150K и предложением reinit.
- Одна сборка за раз (`flock` или блокировка через `mkdir` в macOS/Git Bash); запуски хуков (`--background`, а в pre-push `--no-wait`) её никогда не ждут — ставят одну повторную проверку. Ручной запуск ждёт до 5 минут. Никогда не блокирует git (exit 0 везде, кроме `--check`), пишет в `.repomix/update.log` (ротация в `update.log.1` при размере выше 1 MB).

Правила агента в режиме update:

1. Не переписывай `repomix.packs.json` — пользователь мог настроить его вручную.
2. Читай раздел «Problems» PACKS_STATUS.md: файлы вне пакетов → сообщи пользователю, предложи добавить их в существующий или новый пакет (либо `coverage_ignore`); несуществующий watch-путь → предложи реальный; строки с признаками секретов → сразу предложи исключение.
3. OVER / предупреждения о потолке → предложи reinit; применяй только после одобрения.
4. **AGENTS.md объединяется, никогда не заменяется.** Это живой файл, который команда и агенты развивают между запусками. Если раздел Repomix требует обновления, прочитай текущий файл, измени ТОЛЬКО изменившееся (строки таблицы пакетов, удаление старых чисел токенов), сохрани каждое локальное дополнение и покажи diff до записи.
5. Старые установки (нет hook `post-checkout`, четырёхстрочный список `.repomix/…` в `.gitignore`, числа токенов в AGENTS.md или манифесте) → предложи шаги reinit 5–6 ниже.

# Режим: reinit (миграция / перенарезка)

Когда: монолит >150K; пакет перерос потолок; доменная структура изменилась; либо проект хочет получить исправления этого гайда поверх старой настройки («подкинуть скрипт заново и переразвернуть»).

1. **Инвентаризируй старую настройку:** существующие `repomix.config.json`, `.repomix/*.xml`, `repomix.packs.json`, `.githooks/`, установленные хуки (`git rev-parse --git-path hooks`, `core.hooksPath`, `.husky/`), раздел Repomix в AGENTS.md. Ожидаемые старые ошибки: только post-commit hook, молчаливый no-op `command -v repomix`, фон без nohup, конфиг в .gitignore, совет «читай весь индекс» и числа токенов в AGENTS.md, записи `watch` в виде префиксов имён.
2. **Создай резервную копию:** старые конфиги + манифест в `.repomix/backup-<date>/` (никогда не удаляй файлы пользователя; блок `.gitignore` фазы 5 исключает копии из git).
3. **Перемерь** с нуля (фаза 2) и **перенарежь** домены (фаза 3).
4. **Покажи diff:** старые пакеты против новых (или «монолит → N пакетов»), с числами токенов. Если пользователь редактировал манифест вручную, явно покажи его изменения до замены. Дождись одобрения.
5. **Обнови скрипты и хуки, сохранив локальную логику.** Прежде чем перезаписывать копию `scripts/update-repomix-index.sh`, `scripts/install-git-hooks.sh` или `.githooks/*` проекта, сравни её с новым шаблоном (`diff -u .githooks/pre-push <engine>/quick-start/templates/githooks/pre-push`). Строки, которых нет ни в одном шаблоне (CI-проверка, дополнительные команды), принадлежат проекту: покажи их пользователю и перенеси логику hook в `.githooks/<hook>.local` (исполняемый) до копирования шаблона; никогда не теряй их молча. Затем запусти установщик — он сохраняет и показывает diff каждого заменяемого установленного hook.
6. Запиши конфиги (фаза 4), обнови `.gitignore`/`.gitattributes` (фаза 5), пересобери (фаза 6), обнови раздел AGENTS.md (фаза 7) — **удали** старую инструкцию «ОБЯЗАТЕЛЬНО читай output.xml» и все числа токенов. **Объединяй AGENTS.md, никогда не создавай заново**: он накапливает правила проекта между запусками — редактируй раздел Repomix на месте, сохраняй остальное, показывай diff до записи.
7. Удали устаревший монолит `output.xml` с диска, если его заменяют пакеты (после одобрения пользователя), либо оставь с пометкой «не читать целиком» в AGENTS.md, если пользователю нужен артефакт CI (PACKS_STATUS.md продолжает о нём сообщать). Оставшиеся XML-пакеты переименованных пакетов удаляет сам скрипт обновления.

# Базы знаний и текстовые проекты (не код)

Два строгих отличия от кода:

1. **`compress: false`, `removeComments: false` — всегда.** Сжатие Tree-sitter убирает «тела», что допустимо для кода (структура остаётся), но в тексте знаний уничтожает именно то содержимое, которое база призвана хранить. Формулировки, нюансы и полные абзацы И ЕСТЬ полезная нагрузка. Цена — более крупные пакеты; компенсируй более активным разделением, а не сжатием.
2. **Пакеты следуют разделам содержания, а не доменам кода:** например, база писателя → `core` (профиль, принципы, голос, маршрутизация), `domain`, `insights` и библиотека по полкам (`library-craft`, `library-marketing`, …). «Библиотека справочных книг» НИКОГДА не делит пакет с рабочими знаниями — книги загружаются только для задач о них.

В базах, развёрнутых из AI Knowledge Engine, это автоматизировано: раздел `index:` в `kb.config.yml` + `kb_reindex.py` создают пакеты и автоматически разделяют слишком большие разделы по подпапкам (см. `knowledge-base/05_INDEX.md`). Для отдельных текстовых проектов применяй гайд вручную с теми же профилями и правилом `compress: false`; бинарные источники (docx/pdf/pptx) сначала конвертируются в Markdown (pandoc / marker), оригиналы исключаются, а короткие описания помещаются в `assets-index/*.md`.
