# 16 — Слияние между базами (импорт и экспорт)

> Контракт обмена знаниями между **двумя развёртываниями одной и той же базы**
> — студийный и рабочий ноутбуки, десктоп и машина для поездок.
>
> **Reference implementations:** `scripts/kb_export.py` (упаковка) и
> `scripts/kb_import.py` (слияние). Обёртки: `shell/export.sh`, `shell/import.sh`,
> плюс `export.command` / `import.command` (macOS) и `export.bat` /
> `import.bat` (Windows).

---

## Проблема

Одна и та же база, развёрнутая дважды, расходится. Одна машина копит знания
о плагинах и оборудовании; другая — аналитические заметки. Обе правили
`knowledge/domain/tools.md`. Ни `rsync`, ни простое копирование тут не помогут:
первый затрёт работу одной из сторон, второе оставит две несвязанные кучи
Markdown.

## Цели дизайна

1. **Никогда не терять знания.** Ни одна перезапись не происходит без бэкапа,
   а неоднозначная перезапись не происходит вовсе — она становится решением
   для агента.
2. **Механика — в Python, смысл — у агента.** Скрипт делает то, что доказуемо
   безопасно (дедупликация по хэшу содержимого, аддитивные копии, штампы
   provenance). Всё, что требует суждения, уходит в `review/needs-merge/`
   и разбирается командой `!merge`.
3. **Идемпотентность.** Повторный импорт того же архива во второй раз не
   меняет ничего.
4. **Сходимость, а не накопление.** Повторные синхронизации не должны плодить
   дубликаты, поэтому идентичное содержимое распознаётся независимо от имени
   файла, а страницы, которые были импортированы и с тех пор не правились
   локально, молча обновляются fast-forward.

```text
                                         │
                                         ├─ безопасное → применяется автоматически
                                         └─ спорное    → review/needs-merge/

                                                              │

                                                              │
                                                       переиндексация
```

## Экспорт

```bash
python3 scripts/kb_export.py                    # → sync/outbox/kb-bundle__<label>__<date>.zip
python3 scripts/kb_export.py --label studio-laptop
python3 scripts/kb_export.py --since 2026-06-01 # только знания, затронутые с этой даты
python3 scripts/kb_export.py --with-assets      # включить бинарные оригиналы
python3 scripts/kb_export.py --dry-run          # показать содержимое, ничего не записывать
```

### Что уезжает

| Секция | Путь в архиве | Зачем |
|---------|----------------|-----|
| `knowledge` | `knowledge/**.md` | сами знания |
| `assets-index` | `assets-index/**.md` | описания бинарников — дёшево и полезно |
| `interactions` | `interactions/**` | история сессий — append-only, никогда не конфликтует |
| `meta` | `meta/extracted-metadata/`, `meta/nlp-meta/` | provenance и NLP-обогащение |
| `config` | `config/entities.yml` | роль, язык, отслеживаемые сущности |
| `log` | `log.md` | хронология операций другой базы |
| `assets` | `assets/**` | **только opt-in** (`--with-assets`) |

### Что не уезжает никогда

`raw/`, содержимое `processed/`, очереди `review/`, сама `sync/`, вывод
`.repomix/` и операционное состояние (`.watcher.pid`, lint-отчёты). Сырьё
остаётся на машине, которая его произвела: оно самое большое, самое приватное
и наименее полезное другой стороне.

> **Ассеты — opt-in намеренно.** Для медиа-тяжёлых ролей бинарники превосходят
> знания на три порядка. Архив по умолчанию несёт их *описания*
> (`assets-index/`); если у импортирующей базы нет соответствующего файла,
> запись получает пометку `- Note: original file not present in this base`,
> так что ссылка остаётся честной, а не битой.

### Манифест

Каждый архив начинается с `manifest.yml`: формат бандла, метка источника, роль,
язык, дата экспорта, счётчики по секциям, а для каждого файла — размер, SHA-256
и (для страниц знаний) **отпечаток содержимого** (content fingerprint) плюс
title, lifecycle и importance. Именно отпечаток делает дедупликацию возможной.

## Импорт

```bash
python3 scripts/kb_import.py                 # все *.zip в sync/inbox/
python3 scripts/kb_import.py bundle.zip
python3 scripts/kb_import.py --dry-run       # классифицировать, ничего не записывать
python3 scripts/kb_import.py --strategy prefer-incoming
```

### Отпечаток содержимого

**Тело — это знание; frontmatter — бухгалтерия.** Две страницы несут одно и то
же знание, когда совпадают их нормализованные **тела** — переводы строк
унифицированы, хвостовые пробелы срезаны, замыкающие пустые строки схлопнуты.
Реализовано в `kb_common.content_fingerprint()`.

Frontmatter намеренно оставлен за пределами отпечатка. Чтение страницы на одной
машине увеличивает `access_count`; проставленный там тег поднимает `importance`.
Ничто из этого — не повод спрашивать человека, какая версия победит: метаданные
сливаются неразрушающе (теги объединяются, счётчики поднимаются до максимума,
даты сдвигаются к самой свежей, отсутствующие поля заполняются, существующие
значения никогда не заменяются).

### Таблица решений

| Исход | Условие | Что происходит |
|---------|-----------|--------------|
| `new` | нет страницы по этому пути, нет страницы с этим slug, нет страницы с этим отпечатком | копируется в базу, ставится штамп provenance |
| `identical` | тот же путь, то же тело, те же метаданные | пропускается |
| `enriched` | тот же путь и тело, входящие метаданные что-то добавляют | метаданные сливаются — тело не тронуто |
| `duplicate` | то же тело по **другому** пути | пропускается, попадает в отчёт (страница уже существует под другим именем) |
| `fast-forward` | локальное тело всё ещё совпадает с `merge_source_fingerprint`, записанным при прошлом импорте, — то есть здесь его не правили | тело обновляется, локальные поля frontmatter сохраняются, бэкап остаётся |
| `conflict` | оба тела изменились | **локальный файл не тронут**; входящая версия и diff кладутся в `review/needs-merge/` |

Страница, классифицированная как `new`, но пересекающаяся с существующей на
≥ `similarity_threshold` (по умолчанию 0.85), всё равно добавляется — знания
никогда не удерживаются, — но при этом пишется пакет **кандидата на слияние**
(merge candidate), чтобы агент мог консолидировать обе.

### Штампы provenance

Импортированные страницы получают:

```yaml
merged_from: "studio-laptop"                  # sync.label базы-источника
merge_bundle: "kb-bundle__studio-laptop__2026-07-31.zip"
imported_at: "2026-07-31T10:14:36+03:00"
merge_source_fingerprint: "sha256:1a2b3c…"    # отпечаток на момент импорта
```

`merge_source_fingerprint` — это весь механизм fast-forward: если при следующем
импорте локальный отпечаток всё ещё равен ему, значит, обновление не потеряет
ничего локального. Если отличается — пользователь правил страницу и здесь,
а это уже конфликт.

Эти ключи живут во frontmatter, который находится вне отпечатка, поэтому их
проставление никогда не делает страницу «изменённой» в глазах другой базы.

### Секции помимо знаний

- **`assets-index/`** — сливается поблочно (`## <asset>`). Отсутствующие блоки
  дописываются; существующие не трогаются.
- **`interactions/`, `processed/extracted-metadata/`, `processed/nlp-meta/`** —
  аддитивно. Идентичные файлы пропускаются; файлы с тем же именем, но другим
  содержимым кладутся рядом как `<name>__from-<label>.<ext>`.
- **`log.md`** — архивируется как `log-archive/imported__<label>__<date>.md`.
  Локальный лог никогда не переписывается; сам импорт дописывается в него.
- **`config/entities.yml`** — **только попадает в отчёт, никогда не
  применяется.** Добавление сущности меняет маршрутизацию и раскладку папок,
  поэтому это решение агента во время `!merge`.

### Безопасность

- Каждый изменяемый файл сначала копируется в `sync/backups/<timestamp>/<path>`.
- Элементы архива с абсолютными путями или `..` отклоняются (zip-slip).
- `--dry-run` классифицирует всё и ничего не записывает.
- Архив перемещается в `sync/applied/` только после успешного импорта.

### Коды выхода

| Код | Значение |
|------|---------|
| `0` | слито чисто, решать больше нечего |
| `1` | слито, конфликты ждут в `review/needs-merge/` |
| `2` | ошибка (нет архива, нечитаемый архив, неподдерживаемый формат) |

## `!merge` — половина работы агента

Запускается после каждого импорта. Именно здесь база становится *лучше*,
а не просто больше.

**Стоимость:** ~5–40K токенов в зависимости от числа конфликтов.

### Процедура

1. **Прочитай отчёт.** Самый свежий файл в `sync/reports/`. В нём перечислено
   всё, что было добавлено, обновлено, пропущено, — и всё, что ещё не решено.

2. **Разбери каждый пакет в `review/needs-merge/`.**
   - *Конфликты:* прочитай локальную страницу и `_incoming/<path>` целиком.
     Собери одну слитую страницу **по локальному пути**, которая сохраняет
     каждое утверждение, верное хотя бы в одной из версий, и предпочитает более
     конкретную формулировку. Никогда не выбрасывай факт из-за того, что его
     не было у другой стороны.
   - *Настоящие противоречия* (стороны утверждают несовместимое): оставь
     утверждение с лучшим источником, а второе запиши в
     `knowledge/open-questions/` с обоими источниками и датами. Не выбирай
     победителя молча.
   - *Кандидаты на слияние* (почти-дубликаты): если обе страницы описывают одно
     и то же — консолидируй в ту, что названа лучше, а вторую перенеси в
     `knowledge/_archive/` с `supersedes:`. Если они различаются — вместо этого
     свяжи их через `[[wikilinks]]`.
   - Разобрав пакет, установи `merge_source_fingerprint` слитой страницы равным
     отпечатку входящей, обнови `last_verified`, оставь большее `importance`,
     объедини `tags` — затем удали пакет и его файл в `_incoming/`.

3. **Проведи аудит противоречий.** По слитым страницам *и их соседям* (всему,
   на что они ссылаются через `[[wikilinks]]`): не противоречит ли
   импортированное знание тому, что база уже держала? Две базы, расходившиеся
   месяцами, будут не согласны — вытащи это на поверхность, а не оставляй оба
   утверждения в индексе.

4. **Обогати.** Ради этого слияние и затевается:
   - свяжи импортированные страницы с существующим графом через `[[wikilinks]]`
   - обнови `knowledge/routing/` (`python3 scripts/kb_route.py`)
   - если импорт принёс цельную новую область — подумай, не заслуживает ли она
     страницы в `insights/`, синтезирующей обе стороны
   - сообщи о сущностях, которые другая база отслеживает, а эта — нет,
     и спроси пользователя, принимать ли их

5. **Заверши.** Запусти `python3 scripts/kb_lint.py`, затем переиндексацию
   (`python3 scripts/kb_reindex.py`). Отчитайся пользователю: что добавлено,
   что слито, что чему противоречит и что осталось в `open-questions/`.

### Правила для агента

- **Никогда** не разрешай конфликт, целиком удаляя одну из сторон. Если факт
  есть только во входящей версии — ему место в слитой странице.
- **Никогда** не применяй изменения `entities` из архива без вопроса.
- Если конфликт нельзя решить без пользователя (обе стороны правдоподобны,
  арбитражного источника нет) — задай **один** конкретный вопрос по этой
  странице и переходи к следующей; не тормози всё слияние целиком.
- Правила про длинные книги из `03_PIPELINE.md` продолжают действовать:
  импортированной странице, которая на деле — проза произведения под
  копирайтом, не место в `voice/`.

## Типичный цикл на двух машинах

```bash
# на студийном ноутбуке
./shell/export.sh --label studio-laptop
# скопируй sync/outbox/kb-bundle__studio-laptop__<date>.zip в sync/inbox/ другой машины

# на рабочем ноутбуке
./shell/import.sh
# → "2 conflicts waiting in review/needs-merge/"
```

Затем в чате с AI:

```
Используй AGENTS.md как основную инструкцию
!merge
```

Проделай то же в обратную сторону — и обе базы сойдутся: каждая держит
объединение знаний, а противоречия вытащены на поверхность, а не похоронены.

## Конфигурация (`kb.config.yml` → `sync`)

```yaml
sync:
  label: "studio-laptop"        # как эта база себя называет. ДОЛЖЕН отличаться на каждой машине
  export:
    sections: ["knowledge", "assets-index", "interactions", "meta", "config", "log"]
    with_assets: false
  import:
    strategy: "safe"            # safe | prefer-incoming | prefer-local
    similarity_threshold: 0.85
    backup: true
    move_applied: true
```

CLI-флаги переопределяют конфиг; конфиг переопределяет встроенные значения
по умолчанию.

| Стратегия | Поведение при двустороннем изменении |
|----------|--------------------------------|
| `safe` (по умолчанию) | локальное не тронуто, конфликт встаёт в очередь для `!merge` |
| `prefer-incoming` | побеждает входящее, бэкап остаётся в `sync/backups/` |
| `prefer-local` | входящее отбрасывается, только попадает в отчёт |

`prefer-incoming` и `prefer-local` существуют для массовых односторонних
синхронизаций (свежая база подтягивается из устоявшейся). Для обычной
двусторонней работы используй `safe` — всё остальное молча выбирает победителя.

## Приватность

Архив — это знания, а не сырьё, но это всё ещё **твои** знания: относись
к нему как к чувствительным данным. Переноси его между машинами так же,
как переносил бы саму базу. Ничто на пути экспорта не обращается к сети,
а `sync/` исключена из индекса (`repomix.config.json`) и из git (`.gitignore`).

Если базой пользуется кто-то ещё, экспортируй с `--only knowledge` и просмотри
результат: `interactions/` содержит историю сессий,
а `meta/extracted-metadata/` — исходные имена файлов.
