# 17 — Refactor: погашение долга инструкций

> Сокращение действующих файлов инструкций в два шага. Анализ отделён от переписывания, чтобы решения принимал владелец, а агент не выдумывал дополнительные правила. Дополнение к этапу 4 `!heal` (`kb-docs/18_HEAL.md`).
>
> Скрипта `kb_refactor.py` **нет**. Агент следует этому модулю.

---

## Когда

Lint предупреждает `agents-bytes`, `instruction-absolutes`, `work-ordering` или `instructions-review` (устарело `instructions_review.reviewed_at`); появилось новое поколение моделей; или владелец сказал `!refactor`.

Если база уже укладывается в пороги lint и недавно проверена — это **допустимый** результат: сообщите об этом и остановитесь.

---

## Команда

`!refactor` → следуйте этому модулю.

`!refactor --global` → **только отчёт**. Сравните `~/.codex/AGENTS.md` (или `$CODEX_HOME/AGENTS.override.md`, если этот файл непустой) с `AGENTS.md` этой базы. Перечислите пересечения и противоречия. **Не записывайте** файлы вне базы. Не редактируйте `~/.codex/*`.

---

## Область действия

По умолчанию (только внутри базы):

- `AGENTS.md`
- `kb.config.yml` (ключи инструкций: `instructions_lint`, `instructions_review`, комментарии `mode_profiles` — не `knowledge/`)
- `KNOWLEDGE_STRUCTURE.md`
- `DATA_PLACEMENT_EXAMPLES.md`

Никогда:

- Тела `AI-KE:INVARIANT` (`forbidden`, `language`) — сообщайте, если они чему-то противоречат; не переписывайте формулировки
- Управляемые блоки `AI-KE:INDEX`, `AI-KE:VIEW`, `AI-KE:STATUS` — оставляйте как есть. Ими управляет `kb_upgrade.py`: он сравнивает каждый блок с `templates/AGENTS.md.template` движка, сохраняет локальную правку, только пока эталонный блок неизменен, и запрашивает слияние, когда тот меняется
- Файлы вне базы, включая `~/.codex/AGENTS.md`
- Страницы содержимого `knowledge/**` (это область `!audit` / `!review`)

## Чистые сессии

Для eval нужна **чистая сессия** — та, которая не видела этот рефакторинг. Вы не можете открыть её самостоятельно. Одним сообщением попросите владельца: «Откройте новый чат в этой базе, вставьте три вопроса из `eval/QUESTIONS.md` и сохраните ответы как `eval/results/<file>`» — или запустите субагента с чистым контекстом, если инструмент это позволяет. Никогда не отвечайте на вопросы в сессии, которая проводит аудит или переписывание.

## Цикл

1. **Исходный замер.** Чистая сессия. Ответьте на `eval/QUESTIONS.md`. Запишите `eval/results/<YYYY-MM-DD>__before-refactor.md`. Если трёх вопросов нет, остановитесь и считайте это пунктом `!heal` для человека (этап 3). Если страница, которую вопрос требует цитировать (`must cite`), ещё не существует (молодая база), вопрос ничего не измеряет — попросите владельца заменить его на тот, на который база уже может ответить. Не сокращайте без измерения.
2. **Шаг 1 — аудит (без записи).** Построчно, по пяти категориям из таблицы ниже. Выведите таблицу: id, цитата, категория, предлагаемое действие, причина. **Остановитесь.** Задайте владельцу конкретные вопросы с вариантами ответа. Пока ничего не переписывайте.
3. **Шаг 2 — переписывание только по решениям.** После ответов владельца соберите новый текст из этих вердиктов. Не добавляйте ничего, чего он не выбрал. Сначала резервная копия: скопируйте каждый изменяемый файл в `.kb-state/refactor-backups/<YYYYMMDDTHHMMSS>/`, сохраняя путь относительно корня базы. Не в `.kb-backups/`: эта папка содержит собственные запуски `kb_heal.py`, и `--verify` / `--rollback` heal пропускают папки, которые heal не создавал. Запишите новый `AGENTS.md` (и остальные файлы области действия, только если это предписано вердиктом).
4. **После.** Чистая сессия. Ответьте на те же три вопроса → `eval/results/<YYYY-MM-DD>__post-refactor.md`. Владелец сравнивает ответы до и после по строкам `must cite` / `must mention` / `must NOT propose` и самостоятельно добавляет одну строку вердикта: `eval: ok` или `eval: regressed`. Вердикт не принимает сессия переписывания. Не используйте других формулировок. При `eval: regressed` скопируйте каждый файл из папки резервной копии обратно по его пути и **остановитесь**. `kb_heal.py --verify` никогда не отменяет рефакторинг: он оценивает запуски heal по файлам `*after*` в `eval/results/` — поэтому этот файл называется `post-refactor`.
5. **Отметка.** В `kb.config.yml` (редактируйте только эти строки, сохраняйте комментарии) установите `instructions_review.reviewed_at` в сегодняшнюю дату, `reviewed_model` — в модель, которая только что работала, `clean_run_baseline` — в путь результата после рефакторинга. Запишите операцию `refactor` в журнал.

## Категории (шаг 1)

| # | Название | Если владелец согласен |
|---|----------|-----------------------|
| 1 | инвариант — модель сама этого не знает | сохранить |
| 2 | усвоенное поведение по умолчанию | удалить |
| 3 | пережиток — написано для старой модели или уже исправленной ошибки | удалить |
| 4 | правило на 90% случаев, сформулированное как всегда/никогда | переписать как условие |
| 5 | конфликт / внутренний дубль | оставить одну сторону |

Блоки `AI-KE:INVARIANT` автоматически относятся к категории 1. Не включайте их в набор решений.

---

## Чистый запуск (смена модели)

Когда владелец меняет основную модель (или `instructions_review` устарел):

1. Одна чистая сессия **без** `AGENTS.md` — исходные способности на `eval/QUESTIONS.md`. Попросите владельца провести её вне базы (чат в пустой папке, чтобы `AGENTS.md` не загрузился) и сохранить ответы как `eval/results/<date>__clean-run.md`.
2. Одна чистая сессия **с** базой, загруженной как обычно. Сохраните как `eval/results/<date>__instructed.md`.
3. Владелец сравнивает результаты. Если instructed хуже clean-run, инструкции стали долгом — запустите `!refactor` с шага 1. Если instructed лучше или равен, поставьте отметку в `instructions_review` и остановитесь.

---

## Ограничители

| Ограничитель | Правило |
|--------------|---------|
| Честный ноль | Пороги не превышены и проверка свежая → остановиться |
| Нет измерения | Нет `eval/QUESTIONS.md` → не писать сокращённый `AGENTS.md` |
| Регрессия eval | Строка вердикта `eval: regressed` → скопировать файлы обратно из `.kb-state/refactor-backups/<stamp>/` и остановиться |
| `--global` | Только отчёт; никогда не писать вне базы |
| INVARIANT | Никогда не менять формулировки внутри обёрток |

---

## Конфигурация

```yaml
instructions_review:
  reviewed_at: "2026-08-23"
  reviewed_model: "gpt-5.6-codex"
  clean_run_baseline: "eval/results/2026-08-23__post-refactor.md"
```

Lint (`kb-docs/09_LINT.md`) предупреждает, когда `reviewed_at` старше `instructions_lint.review_stale_days` (по умолчанию 90). Отсутствующее `reviewed_at` не даёт предупреждения — heal может добавить блок.
