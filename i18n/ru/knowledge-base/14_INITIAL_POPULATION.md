# 14 — Помощник первоначального наполнения

> После завершения `02_INIT` агент **обязан** создать персонализированный `DATA_PLACEMENT_EXAMPLES.md` для выбранной роли. Это устраняет эффект пустых папок: пользователь смотрит на `raw/work/unsorted/` и не понимает, что туда положить.
>
> **Эталонный шаблон:** `knowledge-base/templates/DATA_PLACEMENT_EXAMPLES.md.template` — исходный каркас.
> **Эталонный шаблон роли (для пользовательских ролей):** `knowledge-base/templates/role.yml.template`.
> **Эталонный генератор (предпочтительно):** `scripts/kb_populate.py` — yaml → markdown без токенов LLM.
> **Эскизы структуры (до создания папок):** `scripts/kb_structure.py` — четыре варианта и список слепых зон из того же YAML (`02_INIT.md`).
> **Источник примеров:** раздел `placement_examples:` в `examples/<role>.yml`.
>
> ⚠️ **О путях:** при развёртывании база находится в `<project-root>/knowledge-base/`, поэтому во время сборки верен аргумент `--kb-root knowledge-base`. После `setup/shell/finalize.sh` база находится прямо в корне проекта, и для повторного запуска используется `--kb-root .` (либо флаг опускается, поскольку cwd — корень). Примеры ниже предполагают путь при развёртывании.

---

## Два пути

У агента два способа создать `DATA_PLACEMENT_EXAMPLES.md`:

| Путь | Когда | Стоимость |
|------|------|------|
| **A. Встроенная роль** — пользователь выбрал существующий шаблон | Запустить `kb_populate.py --role <role>`, затем необязательный разбор | ~50 токенов (только вызов скрипта) |
| **B. Пользовательская роль** — пользователь придумал новую роль | Создать и сохранить `examples/<slug>.yml` из `role.yml.template`, затем путь A | ~3–8K токенов (подготовка yaml) + вызов скрипта |

Оба заканчиваются **одинаковым необязательным разбором**: агент читает созданный файл и добавляет заметки о проекте, не выраженные в YAML.

### Как `--role` находит YAML

`--role` принимает имя файла (`programmer-senior` или `programmer-senior.yml`) **либо** заголовок `role:` внутри YAML (`"Senior Software Engineer"`, без учёта регистра). Сначала скрипт ищет в `<kb-root>/examples/` (по умолчанию текущая папка), затем в `examples/` рядом со своей папкой `scripts/`: пользовательская роль в `knowledge-base/examples/` находится даже при запуске `setup/scripts/kb_populate.py`. `kb_structure.py --role` ищет так же. Без `--role` и `--from` роль берётся из `knowledge_base.roles.primary` в `<kb-root>/kb.config.yml` (так работает `!populate`), поэтому `roles.primary` должен быть именем YAML-файла либо его заголовком `role:`. Неизвестная роль даёт код 1 и список известных; если роль пришла из `roles.primary`, сообщение указывает это.

## Путь A: встроенная роль

1. Пользователь выбирает (либо агент предлагает) роль из `examples/`; каждый `*.yml` там — роль (`ls examples/`), например `programmer-senior`, `marketing-director`, `product-manager`, `researcher`, `founder`, `content-creator`, `fiction-writer`, `psychologist-gestalt`.
2. Агент запускает при развёртывании, до `finalize.sh`:

   ```bash
   python3 knowledge-base/scripts/kb_populate.py --role <role> --kb-root knowledge-base
   ```

   Либо, если cwd агента уже внутри `knowledge-base/`:

   ```bash
   python3 scripts/kb_populate.py --role <role> --kb-root .
   ```

3. Необязательный флаг `--create-samples` также записывает файлы-заглушки в `raw/_samples/`.
4. Агент **читает** созданный `DATA_PLACEMENT_EXAMPLES.md` и переходит к разбору (ниже).

Сама генерация требует **0 токенов LLM**: `kb_populate.py` просто применяет шаблон.

`--dry-run` выводит файл вместо записи; `--json` выводит сводку.

## Путь B: пользовательская роль, придуманная на ходу

Если пользователь описывает роль, которой нет в `examples/`, агент **обязан сначала создать YAML**, прежде чем наполнять базу.

### B.1. Создать YAML роли

1. Скопировать `templates/role.yml.template` в `knowledge-base/examples/<slug>.yml` (в развёртываемой базе, пока она находится в `<project>/knowledge-base/`).
2. Агент заполняет заглушки, **интервьюируя пользователя**:
   - `{{ROLE_TITLE}}` — короткий заголовок
   - `{{ROLE_DESCRIPTION}}` — 2–3 предложения
   - `entities:` — 3–5 записей с `why` и `knowledge_paths`
   - `raw_data_examples:` — 5–10 типичных видов артефактов
   - `ai_assistant_tasks:` — 5–7 задач, в которых помощник должен быть полезен
   - **`placement_examples:`** — часть, которую использует `kb_populate.py`:
     - `intro` — 1–2 абзаца голосом пользователя
     - `by_artifact` — 5–9 конкретных записей артефактов
     - `quickstart` — 3–5 первых шагов
     - `do_not_drop` — 3–5 исключений для роли

3. Использовать тот же текст, что в `role:`, для `knowledge_base.roles.primary` в `kb.config.yml` (заглушка `{{PRIMARY_ROLE}}`, фаза 2 в `02_INIT.md`). `!populate` запускается без `--role` и находит YAML по заголовку; несовпадение с любым `examples/*.yml` даёт код 1.
4. Проверить, что файл разбирается:

   ```bash
   python3 -c "import yaml; yaml.safe_load(open('knowledge-base/examples/<slug>.yml'))"
   ```

### B.2. Затем запустить kb_populate

Когда YAML сохранён, процесс совпадает с путём A:

```bash
python3 knowledge-base/scripts/kb_populate.py --role <slug> --kb-root knowledge-base
```

> **Почему сначала сохранить YAML, а не генерировать напрямую?** Две причины:
> 1. YAML становится повторно используемым артефактом: повторный `kb_populate.py` после правок дешёв и детерминирован.
> 2. Пользователь может со временем уточнять роль (добавлять сущности, менять размещение) без повторного обращения к LLM.

## Помощник: копирование сущностей роли в `kb.config.yml`

`kb.config.yml` начинается с `entities: {}`. После создания конфигурации (`02_INIT.md`, фаза 2) скопируйте отображение `entities:` роли, не перепечатывая:

```bash
python3 knowledge-base/scripts/kb_populate.py --entities-from <role> --kb-root knowledge-base
```

- `<role>` разрешается как `--role` (имя файла или заголовок, включая пользовательские роли в `knowledge-base/examples/`).
- Правка построчная: остальные ключи, комментарии и пустые строки `kb.config.yml` сохраняются. Блок начинается с комментария `# Copied from … by kb_populate.py --entities-from`.
- Заполняется только отсутствующий или пустой `entities:` (`entities:`, `entities: {}`). Если сущности уже есть, ничего не меняется (код 0, сообщение "already has entities"): это сущности владельца.
- Затем вручную удалите неподтверждённые владельцем сущности и добавьте запрошенные.
- `--dry-run` показывает будущий блок или сообщает об уже имеющихся сущностях, оставляя `kb.config.yml` неизменным; с `--json` сводка содержит `"dry_run": true` и `"would_copy"`.
- Нет `kb.config.yml` в `--kb-root` → код 2; роль без `entities:` → код 1.

## Необязательный шаг: ИИ-разбор

После записи файла `kb_populate.py` агенту **следует** прочитать его и найти улучшения:

| Цель | Примеры дополнений |
|------|-----------------------|
| Заметки о проекте | «Сначала положите README highway-clicker: там большая часть контекста» |
| Стек инструментов | «Ваш стек Rust + React; добавьте `Cargo.toml` и `package.json` в первые материалы приёма» |
| Предпочтения пользователя | «Пользователь не любит шум экспортов Slack: выделите `review/needs-redaction/`» |
| Уточнение быстрого старта | Выбрать *один* файл в окружении пользователя, который быстрее всего покажет пользу |

Сгенерированная часть заканчивается строкой:

```markdown
<!-- kb_populate: everything above is regenerated; notes added below this line are kept on re-run -->
```

Агент добавляет раздел `## Project notes` **ниже этой строки**. Не правьте ничего выше: повторный запуск переписывает всё до маркера и сохраняет всё после. (Файл, созданный до появления маркера, сохраняет `## Project notes` от заголовка до конца и получает маркер при следующем запуске.)

Этот проход обычно стоит ~1–2K токенов и приносит пользу. При строгом бюджете пользователя пропустите его и продолжайте.

## Необязательный шаг: `raw/_samples/`

Если пользователь хочет примеры форматов или передан `--create-samples`:

```bash
python3 knowledge-base/scripts/kb_populate.py --role <role> --create-samples --kb-root knowledge-base
```

Для каждого артефакта из `placement_examples.by_artifact` записывается `raw/_samples/<artifact-slug>.example.md`. Папка исключена из приёма (имя начинается с `_`).

## Когда генерировать заново

| Триггер | Действие |
|---------|--------|
| Пользователь правит `examples/<role>.yml` | Повторить `kb_populate.py`: сгенерированная часть переписывается, заметки после маркера сохраняются |
| Пользователь хочет другой набор артефактов | Изменить YAML → повторить скрипт |
| Команда пользователя `!populate` | `python3 scripts/kb_populate.py --kb-root .` (роль из `knowledge_base.roles.primary`) + ИИ-разбор |
| Новая роль обнаружена после развёртывания | Создать новый YAML (путь B), затем запустить скрипт |

## Чек-лист агента

Для модуля 14 при развёртывании:

- [ ] Определено, подходит ли встроенная роль (путь A) или нужна пользовательская (путь B)
- [ ] (Только B) Создан `examples/<slug>.yml` из `templates/role.yml.template`, проверен разбор YAML
- [ ] `kb.config.yml` содержит подтверждённые сущности (`--entities-from <role>`, затем ручное сокращение)
- [ ] Выполнено `python3 knowledge-base/scripts/kb_populate.py --role <role> --kb-root knowledge-base`
- [ ] Проверено создание `DATA_PLACEMENT_EXAMPLES.md`
- [ ] (Рекомендуется) Прочитан созданный файл, добавлен `## Project notes` ниже строки `<!-- kb_populate: … -->`
- [ ] (Необязательно) Повторён запуск с `--create-samples`, если нужны примеры форматов
- [ ] Выполнен переход к модулю 15. `START_HERE.md`, `eval/QUESTIONS.md`, запуск doctor, `finalize.sh` и сводка пользователю идут после модуля 18 (`02_INIT.md`, «Завершение развёртывания»)

`kb_populate.py` фиксирует каждое сохранение файла в `log.md` как `populate | DATA_PLACEMENT_EXAMPLES generated` (роль, исходный YAML, сохранены ли заметки), если `--kb-root` содержит `kb.config.yml`; папка без конфигурации получает файл без журнальной записи.
