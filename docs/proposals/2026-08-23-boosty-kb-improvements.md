## 0. Что изменилось в ревизии 2

Уточнение от владельца: база живёт **в Codex ~90% времени**, изредка Claude Code и
Cursor. Проверил, как эти три инструмента на самом деле подхватывают инструкции,
и это поменяло не один пункт, а рамку всего плана.

**Проверенные факты (август 2026):**

| Инструмент | Что грузит автоматически | Что это значит для нас |
|---|---|---|
| **Codex** | `~/.codex/AGENTS.md` → `AGENTS.md` от git-root вниз до cwd, **конкатенация**, файл ближе к cwd перебивает | Наш `AGENTS.md` в корне базы **уже автозагружается**. Ритуал не нужен. |
| **Codex, лимит** | **32 KiB суммарно** на все AGENTS.md (`project_doc_max_bytes`); при достижении лимита Codex **перестаёт добавлять файлы** | Наш файл = 10 852 B = **33% бюджета**. Переполнение — молчаливое. |
| **Codex, override** | `AGENTS.override.md` на любом уровне имеет приоритет над `AGENTS.md` | Если у пользователя окажется `AGENTS.override.md` в корне — наш файл не прочитают вообще. |
| **Cursor** | `AGENTS.md` из корня — без настройки; `.cursor/rules/*.mdc` для scoped-правил | Тоже работает из коробки. Ритуал не нужен. |
| **Claude Code** | **только** `CLAUDE.md` / `.claude/CLAUDE.md` / `.claude/rules/`. AGENTS.md не читает | Нужен мостик — но однострочный, а не второй документ. |

Источники: [Codex — Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md) · [Claude Code не читает AGENTS.md](https://makandracards.com/makandra/626671-claude-code-read-agents-md) · [AGENTS.md в Cursor](https://thepromptshelf.dev/blog/cursor-agents-md-complete-guide-2026/)

**Три следствия, которые перестроили план:**

1. **Пункт «мост CLAUDE.md» был лишним в исходном виде.** Для 90%+ использования
   (Codex + Cursor) AGENTS.md — уже правильный и уже автозагружаемый файл.
   Для Claude Code достаточно однострочного `CLAUDE.md` с `@AGENTS.md`, и его
   создание — вопрос на finalize, а не автоматика. Дублировать инструкции во
   второй документ было бы прямым производством долга.
2. **Вводная строка «используй AGENTS.md» остаётся — но перестаёт быть догмой.**
   В Codex и Cursor файл подхватывается сам, так что строка не обязательна. Но она
   стоит ~10 токенов и страхует от **трёх молчаливых отказов**: переполнение
   32 KiB, `AGENTS.override.md` в корне, вложенный `AGENTS.md` ближе к cwd.
   Поэтому рекомендацию оставляем, а меняем формулировку и вырезаем одно правило
   внутри самого AGENTS.md, которое в Codex работает во вред (см. A1).
3. **Сокращение AGENTS.md переехало на позицию №1 и получило жёсткое число.**
   Не «хорошо бы покороче», а: 33% из 32 KiB бюджета Codex тратит один наш файл,
   и если глобальный `~/.codex/AGENTS.md` пользователя разрастётся — наш файл
   **выпадет целиком и молча**. Это не стилистика, это отказ.

## 4. Итерации

### 4.1. Итерация A — среда (Codex-first). Ничего не ломает

**A1. Вводная строка остаётся, автозагрузка объясняется, `CLAUDE.md` — по запросу**

Решение владельца: рекомендацию «начинай с "используй AGENTS.md"» пишем **всегда**,
себе и другим пользователям. Обоснование ниже честное, а не ритуальное — строка
страхует от трёх молчаливых отказов Codex, которые иначе выглядят как «агент
внезапно тупой».

- `templates/START_HERE.md.template`, секция «How to talk to the AI» — переписать так:

  > Начинай новый чат словами **«Используй AGENTS.md как основную инструкцию»**.
  > В Codex и Cursor файл и так подхватывается автоматически, но строка ничего не
  > стоит и страхует от трёх случаев, когда автозагрузка молча не срабатывает:
  > переполнен лимит инструкций (32 KiB на все AGENTS.md вместе), в корне лежит
  > `AGENTS.override.md`, или ты запустил агента из подпапки со своим `AGENTS.md`.
  > В чат-ботах (claude.ai, проект ChatGPT) автозагрузки нет вообще — там строка обязательна.

  Убрать из этой секции неверное для Codex утверждение «если вы пропустите этот
  шаг, агент не знает, что база существует».

- **`shell/finalize.sh`: спросить** — «работаешь ли в Claude Code? создать
  `CLAUDE.md`?». При «да» создать файл из **одной строки** `@AGENTS.md`.
  Содержимое не копировать. Симлинк тоже работает, но ломается на Windows — берём импорт.

- `templates/AGENTS.md.template`, секция `## CRITICAL: how the user talks to you`
  (823 B) — **сжать до ~250 B, а не удалить**. Что остаётся: «вводная строка
  пользователя = сигнал загрузить контекст базы; прочитай `kb.config.yml`,
  `profile/`, `principles/`, `voice/`, коротко подтверди». Что **вырезаем
  обязательно** — вот это правило:

  > *«If the user issues a `!`-command before that line, gently say: "Read AGENTS.md
  > first so I have your context, then re-issue the command."»*

  В Codex это прямой вред: файл уже загружен, контекст у агента есть, а инструкция
  велит ему отказать пользователю и потребовать пароль. Классический реликт —
  правило, написанное под чат-бота, доживает до среды с автозагрузкой.

- Строку таблицы сбоев «Agent ignores my voice / rules → You forgot the opening
  line» заменить на «→ скажи вводную строку; если не помогло — `./shell/doctor.sh`,
  секция Codex environment».

**A4. `MIGRATIONS.md` — реестр догоняющих шагов (заводим сразу, используем в F)**

Каждая версия движка, которая добавляет возможность, обязана записать, что нужно
сделать **уже развёрнутой** базе, чтобы её догнать. Файл `MIGRATIONS.md` в корне
репозитория, формат:

```markdown
## 0.14.0
- id: codex-window-profile
  bucket: auto
  detect: "index.window_profile отсутствует или = 256k при primary_agent = codex"
  fix: "выставить 400k, пересобрать паки"
- id: agents-md-invariants
  bucket: assisted
  detect: "в AGENTS.md нет маркеров AI-KE:INVARIANT"
  fix: "обернуть Forbidden / privacy / Language, показать диф человеку"
- id: eval-bootstrap
  bucket: human
  detect: "eval/QUESTIONS.md отсутствует"
  fix: "спросить у владельца 3 типовых вопроса к базе"
```

**Почему сейчас, а не в итерации F.** Если завести реестр в конце, список миграций
для A–E придётся восстанавливать задним числом по чейнджлогу — и часть шагов
потеряется. Правило: **каждая итерация ниже дописывает свои записи в `MIGRATIONS.md`
в том же коммите, что и саму возможность.** `kb_heal.py` в итерации F просто
читает реестр и берёт диапазон между `instructions_version` базы и текущей.

**A2. `kb_doctor`: проверки среды Codex** — новая функция `check_agent_env(root)`
рядом с существующими `check_structure` / `check_config` в `scripts/kb_doctor.py`:

| Проверка | Порог | Уровень |

Это шесть дешёвых проверок, каждая ловит сбой, который сейчас **происходит молча**.

втрое, прирост нулевой. Это буквально grep.

**B3. `eval/` lite — гейт для итерации C.** *(решение: lite)*

Никакого `kb_eval.py` и YAML на этом этапе. Только:

```
eval/
├── QUESTIONS.md          ← 3 типовых вопроса владельца к своей базе
└── results/
    └── 2026-08-23__before-agents-trim.md
```

Формат `QUESTIONS.md` — обычный markdown, три блока:

```markdown
## Q1. Что мы решили по кэшу и почему?
- должна сослаться на: knowledge/decisions/2026-03__dragonfly.md
- должна упомянуть: DragonflyDB, 25x
- НЕ должна предлагать: Redis Cluster  (вариант, который мы отвергли)
```

Прогон — вручную: задать три вопроса свежей сессии, сложить ответы в
`results/<дата>__<что-меняем>.md` вместе с вердиктом «сошлось / не сошлось» по
каждому пункту. До правки и после. Занимает минут двадцать.

Это 80% ценности за 10% работы. **Меньше этого — нельзя: тогда C2 и C3 становятся
верой, а не инженерией.** К полной версии (`kb_eval.py`, автоподсчёт попаданий)
вернуться, когда ручное сравнение начнёт мешать.

Генерировать `eval/QUESTIONS.md` на развёртывании: агент и так спрашивает про роль —
пусть заодно спросит «какие три вопроса вы будете задавать этой базе чаще всего».
Пустой `eval/` у уже развёрнутой базы — это шаг `bucket: human` в `MIGRATIONS.md`.

### 4.3. Итерация C — возврат долга. **Каждый шаг сверяется прогоном `eval/` до и после**

**C1. Разбор `AGENTS.md.template` по строкам (ничего не переписывая).**
Шаг 1 двухшаговой ревизии. Каждую инструкцию — в одну категорию:

| # | Категория | Рекомендация |
|---|---|---|
| 1 | инвариант — факт или ограничение, которое модель сама не узнает | оставить |
| 2 | дубль обученного — модель делает это и без инструкции | удалить |
| 3 | реликт — писалось под старую модель или под ошибку, которая не воспроизводится | удалить |
| 4 | правило-90% — верно чаще всего, но записано как «всегда/никогда» | переписать условием |
| 5 | конфликт — противоречит другой строке или дублирует её | какую оставить |

Блоки `AI-KE:INVARIANT` → категория 1 автоматически, в выдачу не попадают.
**Решения принимает человек.** Выход: `docs/proposals/agents-md-audit.md`.

**C2. Переписать шаблон под outcome-first.** Целевые числа и откуда они:

| Секция | Байт | Что делаем |
|---|---:|---|
| `## CRITICAL: how the user talks` | 823 | сжать до ~250 B, правило-стоппер вырезать (A1) |
| `## Operating mode` (таблица + default/super) | 1161 | заменить на 2 строки: «прочитай `mode` в `kb.config.yml`, применяй `mode_profiles`» |
| `## Token budget` | 915 | удалить — дословно повторяет Operating mode |
| `## Context budget` | 620 | 8 правил → 3 критерия |
| `## Chat-attached files` | 944 | 8 нумерованных шагов → 2 критерия |
| `## Knowledge lifecycle` | 499 | ссылка на `KNOWLEDGE_STRUCTURE.md` |
| **итого кандидатов** | **4962** | ← 46% файла |
| `### Commands` (таблица команд) | 2769 | **не трогаем** — решение владельца |

10 852 − 4962 + ~1450 B новых критериев и сжатой вводной ≈ **7,3 KiB (−33%)**.
Порог lint оставляем 8 KiB, чтобы был запас на команды `!heal` и `!refactor`,
которые добавятся в таблицу. Для сравнения: OpenAI на своих прогонах получила
−41–66% токенов при +10–15% качества; Anthropic вырезала >80% системного промпта
Claude Code без просадки метрик — так что 33% это консервативно, и это осознанно.

Ключевые замены по существу, а не по объёму:

- `mode_profiles` описан **четырежды** (`AGENTS.md.template`, `06_AGENTS_TEMPLATE.md`,
  `kb.config.yml.template`, `07_INTERACTION_LOOP.md`). Правило Anthropic после
  чистки: каждая вещь описана **один раз, там, где ей место**. Место цифр —
  `kb.config.yml`.
- «at most 7 knowledge/ files», «if you've loaded > 5, stop and reassess» — цифры
  с потолка, записанные как абсолюты; Opus 5 и GPT-5.6 исполняют промпт как
  контракт. Переписать критерием: *«грузи то, что нужно вопросу; тянешься за третьим
  доменным паком — виновата routing-table, чини её»*.
- «Never read a full-base index dump» — настоящий инвариант, **оставить как есть**.

**C3. Команда `!refactor`.** Двухшаговая, анализ отделён от действия (иначе
пользователь соглашается с чужим выбором, а не делает свой).
Шаг 1 — разбор по таблице C1. Шаг 2 — «собери итоговую версию с учётом моих
решений: [список]. Ничего не добавляй от себя.» Перед записью — бэкап в

**Область ревизии по умолчанию:** только файлы базы — `AGENTS.md`, `kb.config.yml`,

**`~/.codex/AGENTS.md` — не включаем.** ⏳ Аргумент за был такой: Codex
конкатенирует глобальный файл перед нашим, и конфликт правил между зонами — это
ровно проблема «шести зон» из статьи 07-03. Аргумент против сильнее: главный
практический риск от глобального файла — это его **размер**, а он уже полностью
закрыт проверкой A2 в doctor. Конфликт правил — риск теоретический, пока не
наступил, а трогать файл вне базы неприятно.

Компромисс: заложить флаг `!refactor --global`, который **только показывает**
пересечения и противоречия между глобальным файлом и AGENTS.md базы. Ничего не
пишет. Включать, когда конфликт реально укусит.

Куда: новый модуль `17_REFACTOR.md` (по образцу `16_MERGE.md`), команда в
`AGENTS.md` и в `START_HERE.md`.

### 4.4. Итерация D — качество петли

**D1. `kb_mutate.py`.** Копирует базу во временную папку, вносит N известных
дефектов, прогоняет `kb_lint.py`, считает **survivors**:

| Мутация | Какое L1-правило должна разбудить |
|---|---|
| битый `[[wikilink]]` | Broken wikilinks 🔴 |
| дублирующийся slug в двух подпапках | Duplicate slugs 🔴 |
| подменённый `source_hash` | Source hash mismatch 🔴 |
| `last_verified` за порогом | Stale pages 🟡 |
| удалить все входящие ссылки на страницу | Orphan pages 🟡 |
| `valid_until` в прошлом, файл не в `_archive/` | Expired temporal 🟡 |
| выкинуть обязательное поле фронтматтера | Frontmatter integrity 🔴 |
| (для L2) факт, противоречащий существующей странице | Contradictions |

Отчёт: `27 мутаций / 25 killed / 2 survivors`. Прямо сейчас никто не знает,
работают ли 13 L1-проверок из `09_LINT.md` на живой базе — тесты есть на скрипты,
но не на связку «дефект → детект». Плюс это калибровка `!audit`: если L2 не ловит
подсаженное противоречие, значит 50–100K токенов уходят на плаузибельный отчёт —
ровно то, что HANDBOOK.md называет ложным рапортом. Формулировка Мартина: *ноль
выживших — не вердикт о качестве, а условие выхода из цикла*.

Шаг в `kb_doctor.py`: `--with-mutation` (не в дефолтном прогоне, он дольше).

**D2. `!audit` — чистый контекст, по пакам, с цитатами.** Три проблемы сразу:
проверяющий = писатель (единственное переносимое правило роя Мартина: писавший не
проверяет); судья без внешнего доступа плохо судит («More Convincing, Not More
Correct»: одобрение судьи 72% → 94% при реальной точности 20%; ансамбль из трёх
судей принял 55% неверных ответов); 50–100K в одном контексте — выше рабочей зоны.

- **Формулировка tool-neutral:** не «субагент», а **новая сессия с чистым
  контекстом**, куда передаётся только пак + чек-лист. В Codex это буквально новый
  запуск в папке базы.
- **Механизм, а не пожелание:** `kb_reindex.py` дополнительно пишет
  `.repomix/audit/<pack>__request.md` — пак + чек-лист + требование формата.
  Пользователь (или скрипт) скармливает файл свежей сессии. Это делает «чистый
  контекст» действием, а не инструкцией, которую агент может проигнорировать.
- **Резать по пакам** — инфраструктура уже есть (`index.packs`, `pack_token_ceiling`).
  Кросс-пак противоречия — отдельным финальным проходом только по заголовкам и выводам.
- **Находка без `file:line` + цитаты в отчёт не попадает.** «Принимаем артефакт,
  а не рассказ о нём».

**D3. Дневник допущений.** Секция `## Assumptions` в формате session-summary
(`07_INTERACTION_LOOP.md`), одна строка на допущение:

```markdown
## Assumptions
- Отнёс `q3-notes.md` в `domain/`, а не в `decisions/` — явного решения в тексте нет, только обсуждение
- Считал, что «DF» в стенограмме = DragonflyDB (по контексту трёх соседних абзацев)
- importance=7 поставлен по объёму синтеза; пользователь не подтверждал
```

Правило поведения: *при пограничном случае выбирай самый осторожный вариант,
записывай допущение и продолжай; останавливайся и спрашивай только там, где от
ответа зависит итог.* Lint: `> 3 допущений на одну область за 30 дней` → ℹ️
«уточнить DATA_PLACEMENT_EXAMPLES для \<area\>». Список допущений — это карта дыр
в routing-table, а не отчётность.

**D4. Тормоза рефлексии.**

1. Мета-инсайт (уровень 2) разрешён, только если с прошлого прохода уровня 1
   появились **новые факты уровня 0**. Сейчас синтез из синтеза без внешнего
   сигнала — это дословно «перечитай и улучши», которое статья называет
   не-информацией.
2. `max_insights_per_run: 3` — переформулировать как потолок и добавить явно:
   **ноль инсайтов — валидный и ожидаемый результат**, пишется в `log.md`.
   Сейчас это квота, а квоты выполняются (закон Гудхарта).
3. Застой: два прогона подряд без нового инсайта → перестать запускать по
   расписанию, сказать пользователю. *«Цикл, который умеет сказать "сегодня ничего
   нет", ценнее цикла, который вымучивает норму.»*

**D5. `!profile-review`.** `knowledge/profile/` — это память о пользователе, и по
`lifecycle: permanent` **L1 stale-проверка её явно скипает**. Два промпта из
статьи, они рабочие дословно:

1. «Прочитай, что ты знаешь обо мне из `knowledge/profile/`, и оцени, какой
   информации не хватает. Задавай вопросы по три за раз, начиная с важных;
   получая ответы — обновляй страницы.»
2. То же про «какая информация может быть устаревшей или неполной».

Плюс `profile_reviewed_at` в `kb.config.yml` и 🟡 в lint через 30 дней.

### 4.5. Итерация F — догоняющая починка после апгрейда

**Проблема.** `kb_upgrade.py` синхронизирует скрипты, `shell/`, вьюер и управляемые
блоки в `AGENTS.md`, чинит `index:` в конфиге и двигает `instructions_version`.
Он сознательно **не трогает содержимое базы** — и это правильно. Но следствие
такое: база, развёрнутая на 0.11, после апгрейда до 0.14 получает новые скрипты и
новые проверки, а внутри у неё по-прежнему раздутый AGENTS.md с локальными
правками, нет `eval/`, нет маркеров инвариантов, профиль не ревьюился год, и
пачка L1-ошибок, которых раньше просто некому было заметить, потому что проверок
не существовало.

Апгрейд включает диагностику — и тут же оставляет пользователя один на один с её
результатами. Нужен шаг, который замыкает петлю.

**F1. `scripts/kb_heal.py --plan` — детект, 0 токенов, ничего не меняет.**

Собирает всё в одном месте:

- `kb_doctor.py` — среда, структура, конфиг, новые проверки Codex из A2
- `kb_lint.py` L1 — 13 проверок + новые байтовые из B2
- **разрыв версий** — шаги из `MIGRATIONS.md` между `instructions_version` базы и текущей
- незакрытые хвосты апгрейда — висящие `.new` сидекары, конфликты управляемых блоков
- свежесть паков относительно `knowledge/`

Выход — **`review/needs-heal/HEAL_PLAN.md`**. Плюс однострочная правка
`REVIEW_DIRS` в `scripts/kb_common.py:93` (добавить `"needs-heal"`) — после неё
`kb_ingest --init-dirs` создаёт папку сам, `kb_doctor.check_structure` её проверяет,
а из индекса она исключена автоматически вместе со всем `review/`. Побочная
выгода против варианта «в корне»: план починки не попадает в паки.

Находки разложены по трём корзинам:

| Корзина | Кто чинит | Примеры |
|---|---|---|
| **auto** | скрипт, без AI и без вопросов | выставить `window_profile: 400k` и пересобрать паки, дописать недостающие поля конфига с дефолтами, ротация лога, создать скелет `eval/` |
| **assisted** | AI + подтверждение человека по каждому пункту | битые wikilinks, дубли slug, сироты, просроченные `valid_until`, слияние `.new` сидекаров, обёртывание секций в `AI-KE:INVARIANT` |
| **human** | только человек | три вопроса для `eval/QUESTIONS.md`, ревью профиля, подпись под сокращённым AGENTS.md, решения `!refactor` |

Разделение корзин — это то же «разделяйте анализ и действие»: скрипт не имеет
права чинить то, где нужно суждение, а AI не имеет права чинить то, что решается
одной строкой кода.

**F2. Команда `!heal` — цикл починки.** Процедура в новом модуле `18_HEAL.md`:

1. **Детект.** `python3 scripts/kb_heal.py --plan` → показать сводку человеку.
   Если находок нет — **сказать «база в порядке» и остановиться.** Это валидный
   и ожидаемый исход, а не повод что-нибудь поправить.
2. **База отсчёта.** Прогнать `eval/QUESTIONS.md` (lite, вручную) → сохранить в
   `eval/results/<дата>__before-heal.md`. Если `eval/` ещё нет — это первый пункт
   корзины human, и починка начинается с него.
3. **auto.** `kb_heal.py --apply auto`. Идемпотентно, с бэкапом в `.kb-backups/`.
4. **assisted.** Агент идёт по очереди **по одному пункту, в порядке дороговизны
   ошибки** — сначала то, что искажает ответы базы, потом косметика. По каждому
   пункту: что нашли, что предлагаем, одно решение от человека. Всё пишется в
   `log.md` операцией `heal`.
5. **human.** Список остаётся в `HEAL_PLAN.md` с чекбоксами. `!heal` не считается
   завершённым, пока они не закрыты, но и не блокирует работу.
6. **Проверка.** Повторный детект + прогон `eval/` → `<дата>__after-heal.md`.
   **Если eval просел — откатиться из `.kb-backups/` и остановиться.** Не
   продолжать «на всякий случай».

**F4. Мягкий режим для старых баз — пять ступеней.** *(решение: обрабатывать в
несколько этапов)*

База, у которой AGENTS.md год правился руками, а `knowledge/` набрал сотни
страниц, не должна получить всё сразу. Одна ступень — один запуск, прогресс
в `kb.config.yml → heal_stage`, следующая ступень не стартует, пока предыдущая
не закрыта:

| Ступень | Что делает | Риск |
|---|---|---|
| 1. **safe** | среда, структура, корзина `auto`, расстановка маркеров `AI-KE:INVARIANT` | нулевой — ничего не удаляется и не сокращается |
| 2. **hygiene** | L1-дефекты: битые ссылки, дубли slug, сироты, просроченные `valid_until`, разбор `.new` сидекаров | низкий, всё точечное и обратимое |
| 3. **measure** | завести `eval/QUESTIONS.md`, снять базу отсчёта | нулевой, но требует человека |
| 4. **trim** | `!refactor` над AGENTS.md | **высокий** — только после ступени 3 |
| 5. **content** | ревью профиля, противоречия, `!audit` по пакам | средний, дорогой по токенам |

Ключевое: **ступень 4 физически недоступна, пока ступень 3 не закрыта** — это тот
же гейт «не режь без замера», только зашитый в состояние, а не в инструкцию,
которую можно пролистать. Свежая база проходит ступени 1–3 за один заход, потому
что чинить нечего.

> **Что именно стало автоматическим** *(решение: heal автоматически)*
>
> После апгрейда `kb_upgrade.py` **сам** запускает детект и применяет корзину
> `auto` — она для того и выделена: детерминированные правки, идемпотентные, с
> бэкапом, без суждений. Выключается флагом `--no-heal` и ключом
> `heal.auto_apply: false` в `kb.config.yml`.
>
> Корзины `assisted` и `human` автоматически **не** применяются — и это не
> сужение задачи, а определение самих корзин: в них лежит ровно то, где нужно
> решение человека по каждому пункту. Автоматически они получают другое: очередь
> собрана, отсортирована по дороговизне ошибки и лежит готовая в
> `review/needs-heal/`, а doctor не даст о ней забыть. От пользователя остаётся
> одно слово `!heal`.
>
> Я бы не делал автоматическим даже `auto`-корзину — починка трогает содержимое
> базы. Но риск здесь реально мал (бэкап + идемпотентность + eval-гейт на откат),
> так что возражение снимаю.

**Тормоза** (иначе цикл превращается в то самое «перечитай и улучши»):

- **честный ноль** — находок нет, `!heal` завершается сразу;
- **застой** — два прохода подряд не уменьшили число находок → остановиться и
  показать, что не чинится, вместо третьей попытки;
- **бюджет** — assisted-очередь длиннее 20 пунктов режется на сессии, а не
  проглатывается одним заходом на 100K токенов;
- **регресс eval** — жёсткий стоп с откатом.

Каждая итерация здесь получает **новую внешнюю информацию** — повторный прогон
детерминированных проверок после реальных правок. Это законный цикл по правилу
из статьи о loops, в отличие от рефлексии, которая читает саму себя.

**F3. Свести с апгрейдом — автозапуск.**

- `kb_upgrade.py`, в конце `upgrade_one()` после `_bump_deployed_version`:
  1. вызвать `kb_heal.py --plan` → записать `review/needs-heal/HEAL_PLAN.md`;
  2. вызвать `kb_heal.py --apply auto` (если `heal.auto_apply` не выключен);
  3. напечатать сводку: что применено автоматически, сколько осталось в
     `assisted` и `human`, текущая `heal_stage`, и строку
     `→ next: скажи агенту "!heal"`.
- Делать это **и при `customized > 0`** — там как раз висят `.new` сидекары,
  которые разбирает assisted-корзина. Сейчас апгрейд в этой ветке возвращает 2 и
  просто уходит.
- `--dry-run` апгрейда обязан оставаться сухим: детект гоняем, `--apply auto` — нет.
- `kb.config.yml`: блок `heal:` — `auto_apply: true`, `last_run` (дата + версия),
  `stage` (1–5), `assisted_batch: 20`.
- `kb_doctor.py`: 🟡 если `instructions_version` двигался, а `heal.last_run` с тех
  пор не обновлялся, либо если `heal_stage` застрял между ступенями. Без
  напоминания процесс тихо не выполняется — ровно как с рефакторингом промптов.
- `docs/UPGRADING.md`: описать новый хвост апгрейда и шаг 6 «скажи `!heal` в базе».
  Сейчас поток заканчивается на doctor и reindex.

**Зависимости.** F технически можно собрать после A (детект + auto-корзина уже
дадут пользу). Полную ценность даёт после B (появляются байтовые проверки и eval)
и D1 (`kb_mutate.py` подтверждает, что проверки, на которые опирается детект,
действительно ловят дефекты). Порядок: **A → B → F → C → D**, если починка старых
баз важнее сокращения шаблона; **A → B → C → D → F**, если наоборот.
Рекомендую первое: у тебя уже есть развёрнутые базы, а шаблон правится один раз.

### 4.6. Итерация E — развёртывание (отложено)

**E1.** Blind-spot pass перед анкетой в `02_INIT.md`: «Структуру пока не предлагай.
Сначала пройдись по слепым зонам: чего люди с ролью X обычно не предусматривают,
заводя долгоживущую базу?» И интервью **в порядке важности** — сначала то, что
меняет структуру `knowledge/`.

**E2.** Четыре кардинально разные структуры вместо анкеты (по проектам / по типам
артефактов / по времени / по решениям), пользователь **реагирует**, а не выбирает.
Материал для генерации уже есть — 16 ролевых YAML в `examples/`. Четыре, не десять.

**E3.** `!quiz` — база экзаменует владельца: «пять вопросов о том, что лежит в базе,
начни с самых дорогих ошибок». Единственная механика, которая проверяет не базу.

**E4.** Exploration-слот в reflection: один-два вопроса формировать как «связать две
компоненты графа, между которыми нет пути». Surprise-фильтр (`overlap < 0.8`) —
чистая эксплуатация, со временем база сходится к собственному словарю. Данные графа
уже считает `kb_view.py`.

## 5. Порядок и зависимости

```
A1  A2  A3  A4 ──► независимы, делаются первыми, ничего не ломают
                     │
      B1 ─► B2 ──────┤
      B3 (eval lite) ─┤
                     │
        F1 ─► F2 ─► F3 ──► починка уже развёрнутых баз
                     │
      C1 ─► C2 ─► C3 ─► C4 ──► каждый шаг сверяется eval/ до и после
                     │
      D1 ─► D2       │
      D3  D4  D5 ────┤        ← независимы между собой
                     │
                E1…E4 ──────► отложено
```

**Две жёсткие зависимости:**

1. **C2/C3 не начинать без B3** (хотя бы lite). Сокращать инструкции без замера —
   ровно та ошибка, от которой предостерегает шаг 5 статьи.
2. **A4 (`MIGRATIONS.md`) заводится в первой же итерации**, и каждая следующая
   дописывает туда свои записи в том же коммите. Иначе F придётся собирать список
   миграций задним числом по чейнджлогу.

**Рекомендуемый порядок: A → B → F → C → D → E.** Починка уже развёрнутых баз
раньше сокращения шаблона: базы у тебя есть сейчас, а шаблон правится один раз и
затрагивает только будущие развёртывания.

## 6. Промпты для запуска в отдельных сессиях

Порядок: **A → B → F → C → D → E**, по одной итерации за запуск, с приёмкой между
ними. Промпты написаны по формуле outcome-first — результат, критерии готовности,
ограничения, — а не пошаговой инструкцией: что делать, подробно написано в разделе 4.

### Общие правила (действуют во всех запусках)

```text

Раздел «Решения владельца» согласован, по нему не переспрашивай.

Правила для любой итерации этого плана:
- Каждая итерация дописывает свои записи в MIGRATIONS.md тем же коммитом, что и
  саму возможность. Без этого команда !heal позже не увидит, что чинить.

- Правки в i18n/ru/ синхронизируй, если затронутый модуль там переведён.
- Прогони тесты и ./shell/doctor.sh на тестовой базе перед тем, как отчитаться.
- Коммит не делай — я посмотрю сам.
- В конце перечисли допущения, которые тебе пришлось сделать, и всё, что ты
  оставил недоделанным.
```
