# Критерии готовности инструмента

> Приёмочный набор. SPEC на него **ссылается**, а не копирует. У каждого
> критерия стабильный ID; карта ownership по slices живёт в
> [06-phase4-spec.md](06-phase4-spec.md).

---

## Control plane

- [ ] **AC-CP-01** Из AI Knowledge Engine можно указать путь к целевому проекту;
      `inspect` выдаёт schema-versioned machine-readable факты с источниками.
- [ ] **AC-CP-02** `inspect` не запускает project code, package scripts, тесты,
      hooks, контейнеры или серверы и не меняет project tree, Git refs/config.
- [ ] **AC-CP-03** Рекомендация объяснима, содержит confidence/cost/prerequisites
      и не предлагает ещё не реализованный профиль как доступный.
- [ ] **AC-CP-04** `plan-probe` показывает команды, cwd, env/network, timeout,
      ожидаемые записи, изоляцию и cleanup; `probe` принимает exact plan id.
- [ ] **AC-CP-05** Каждая мутация — init/start/integrate/abort/cleanup/heal/
      upgrade/reinit/rollback/uninstall — требует одобренный exact plan id,
      проверяет drift и записывает transaction/apply id.
- [ ] **AC-CP-06** Повторное применение того же plan идемпотентно; изменившиеся
      preconditions дают отказ, а не новый неявный план.
- [ ] **AC-CP-07** `doctor` пассивно проверяет структуру/discovery; исполняемые
      диагностики проходят только через `plan-probe/probe`.
- [ ] **AC-CP-08** Операции меняют только доказуемо owned-файлы/managed-блоки и
      не трогают пользовательские ветки, файлы и глобальный Git config.
- [ ] **AC-CP-09** Mutable run state атомарен, schema-versioned и доступен всем
      worktree через корректно разрешённый git common dir или выбранный backend.
- [ ] **AC-CP-10** `status`/`resume` в новой сессии восстанавливают run по
      manifest и заново сверяют branch/SHA/worktree, не доверяя памяти чата.
- [ ] **AC-CP-11** Временные refs/worktree не удаляются до интеграции либо
      отдельного подтверждённого cleanup plan.
- [ ] **AC-CP-12** Команды имеют документированные exit codes, JSON schema и
      понятный human-readable вывод с одинаковой семантикой.
- [ ] **AC-CP-13** Исполнитель ролей подменяем детерминированным stub: state,
      resume, Git-протокол, drift и integration проверяются без вызова живого
      агента, воспроизводимо и в CI.
- [ ] **AC-CP-14** `inspect` обнаруживает существующие скрипты подъёма стека и
      оркестрации и предлагает переиспользовать их как `serve`; change plan
      показывает любую коллизию имён с файлами, которые инструмент собирается
      создать, и без разрешения коллизии apply не выполняется.

## Обновляемость

- [ ] **AC-UP-01** Install manifest хранит owned-файлы с хешами, fingerprint
      managed-блоков, schema versions, ответы init, зависимости/хуки, `bundle_id`,
      content hash, source commit, plan/transaction/apply/backup ids.
- [ ] **AC-UP-02** Immutable release manifest перечисляет shipped-файлы и хеши;
      неизвестная поставка не используется для автоматического overwrite.
- [ ] **AC-UP-03** `list-installs` проверяет пути реестра при чтении и отличает
      рабочие, исчезнувшие и переименованные инсталляции.
- [ ] **AC-UP-04** `upgrade` синхронизирует managed-файлы и применяет нужный
      диапазон записей `MIGRATIONS.md` (`auto/assisted/human`).
- [ ] **AC-UP-05** `customized` файл не перезаписывается: создаётся `.new`
      sidecar, а операция сообщает требуемое слияние.
- [ ] **AC-UP-06** `clean_overwrite` разрешён только при совпадении с хешем из
      известного исторического release manifest.
- [ ] **AC-UP-07** Batch upgrade по умолчанию fail-fast: текущий неуспешный
      проект откатан, завершённые валидны, ещё не начатые `untouched`.
- [ ] **AC-UP-08** Продолжение batch после ошибки возможно только с явным
      `--continue-on-error`; отчёт содержит статус и transaction id каждого.
- [ ] **AC-UP-09** Каждый проект в batch атомарен и не остаётся в состоянии
      полуустановки при crash или ошибке migration/doctor.
- [ ] **AC-UP-10** `reinit` переобнаруживает проект, показывает дельту и сохраняет
      подтверждённые privacy/commit/budget settings и локальные команды.
- [ ] **AC-UP-11** `reinit --clean` перечисляет все потери в plan до удаления.
- [ ] **AC-UP-12** `upgrade`/`reinit` отказываются при активном run без порчи state.
- [ ] **AC-UP-13** `state_schema_version` мигрируется; невозможная миграция даёт
      честный отказ и инструкцию восстановления.
- [ ] **AC-UP-14** `plan-rollback TARGET APPLY_ID` указывает точный backup;
      rollback по plan id возвращает предыдущую рабочую версию.
- [ ] **AC-UP-15** После upgrade/reinit выполняется structural doctor, а на
      disposable fixture новая полоса обязана ловить подсаженные дефекты; иначе
      транзакция откатывается.
- [ ] **AC-UP-16** Обновление сохраняет обещанные данные и не меняет project code,
      текст вне managed-блоков, Git refs и глобальный Git config.

## Проекты и стеки

- [ ] **AC-ST-01** Capability manifest использует состояния `declared / runnable /
      verified / failed / missing / unsupported` и хранит evidence, host и время.
- [ ] **AC-ST-02** Generic-команды и mixed/monorepo routing работают без патча
      оркестратора; профиль выбирается по затронутым пакетам.
- [ ] **AC-ST-03** Greenfield, Symfony, WordPress plugin/theme/site и legacy
      покрыты fixture-тестами и честным capability report.
- [ ] **AC-ST-04** `serve`/`fixtures` описывают lifecycle портов, БД и teardown;
      при недоступности внешняя приёмка помечается unavailable, не имитируется.
- [ ] **AC-ST-05** Только успешный активный probe ставит `verified`; `missing`,
      `failed` и `unsupported` никогда не считаются пройденным барьером.
- [ ] **AC-ST-06** Новый стек заводится декларативным манифестом без изменения
      кода оркестратора; тест доказывает отсутствие в ядре веток по имени стека.
      Встроенные адаптеры используют тот же формат и тот же путь загрузки.
- [ ] **AC-ST-07** Порядок переопределения встроенный → пользовательский →
      проектный работает; пользовательский адаптер помечается `customized` и
      никогда не перезаписывается при `upgrade`. Схема манифеста версионируется.
- [ ] **AC-ST-08** `surface` (`http` / `cli` / `library` / `tui` / `none`)
      определяет способ внешней приёмки; при `none` результат получает
      пониженный штамп верификации, а не имитацию внешней проверки.
      Нераспознанный стек уходит в generic-режим с шаблоном манифеста, а не в ошибку.
- [ ] **AC-ST-09** У capability есть `scope: package | repo`. Repo-scoped барьеры
      обязательны при кросс-пакетном изменении и опциональны при изменении внутри
      одного пакета; барьеры вне пакетов (корневые e2e, deployment-тесты) не
      теряются при маршрутизации по затронутым пакетам.
- [ ] **AC-ST-10** Capability различает `declared` (объявлена проектом) и
      `inferred` (выведена из конфига или конвенции), хранит путь и строку
      источника обнаружения; `inferred` не попадает в полосу без подтверждения
      человеком.
- [ ] **AC-ST-11** Границы пакетов задаются манифестами **и** явными путями;
      каталог без манифеста (например одиночный файл SDK) обнаруживается как
      пакет и участвует в маршрутизации.
- [ ] **AC-ST-12** Нечитаемый или внешний CI (`include` из чужого репозитория)
      даёт `unknown`, а не вывод «CI-проверок нет». Читаемый граф джобов CI
      предлагается как готовое определение порядка и зависимостей барьеров.

## Host adapters и инструкции

- [ ] **AC-HOST-01** Codex, Claude Code и Cursor реализуют один core-контракт и
      проходят одинаковую capability matrix; ни один не считается вторичным.
- [ ] **AC-HOST-02** Adapter возвращает `unsupported` до мутации или применяет
      явно выбранный portable fallback; фиктивная parity запрещена.
- [ ] **AC-HOST-03** В `shared-repo` current/new session и worker в новом
      worktree автоматически находят local runtime при неизменном `git status`.
- [ ] **AC-HOST-04** Существующие `AGENTS.md`, `CLAUDE.md`, Cursor rules и чужие
      managed-блоки сохраняются; pipeline-блок ≤20 строк и учитывает budget хоста.
- [ ] **AC-HOST-05** Host adapter проверяемо передаёт run id/role/context и не
      полагается на расположение вложенного instruction-файла.
- [ ] **AC-HOST-06** Worker guard тестом запрещает рекурсивно создать второй run.
- [ ] **AC-HOST-07** `heal` восстанавливает owned runtime/instructions через
      двухфазный план, не перезаписывая пользовательские изменения.
- [ ] **AC-HOST-09** Бюджет инструкций хоста измеряется целиком, а не только для
      своего блока. Занято > 90% или лимит превышен — `apply` отказывается до
      разрешения человеком; установка «всё равно» помечает в install manifest
      известный дефект «блок может не читаться» и показывает его в `doctor`.
- [ ] **AC-HOST-08** Instruction-файлы, связанные symlink или иным алиасом
      (`CLAUDE.md -> AGENTS.md`), распознаются как один файл: один managed-блок,
      один fingerprint, одна запись в install manifest, второй путь — alias.
      Существующие symlink не разрываются и не создаются заново.

## Профили и роли

- [ ] **AC-ROLE-01** Профиль 2 проходит end-to-end на Codex, Claude Code и Cursor
      нативно либо через заявленный portable fallback.
- [ ] **AC-ROLE-02** Инвариант «писавший не проверяет» контролируется identity/
      handoff-механизмом, а не одной текстовой инструкцией.
- [ ] **AC-ROLE-03** Роль получает минимальный context pack с provenance/budget,
      а полный исходник или secret content не копируется в manifest.
- [ ] **AC-ROLE-04** Профиль 0 («конвейер не нужен») — валидный объяснённый исход.
- [ ] **AC-ROLE-05** Профили 4/6 проходят тот же lifecycle, safety и Git protocol.
- [ ] **AC-ROLE-06** Init задаёт default profile, а задача может повысить/понизить
      его с объяснением и user override в допустимых границах.
- [ ] **AC-ROLE-07** Изменение, затрагивающее публикуемый артефакт (SDK, плагин,
      интеграция), повышает профиль и делает приёмку обязательной независимо от
      объёма правки.

## Полоса препятствий

- [ ] **AC-GATE-01** Полоса собрана из реально объявленных и затем проверенных
      команд проекта, а не из догадок по фреймворку.
- [ ] **AC-GATE-02** Доступные барьеры имеют явные пороги, cwd, timeout и evidence.
- [ ] **AC-GATE-03** Каждый результат несёт видимый stamp уровня проверки: от
      `verified: unit+static+e2e+mutation` до обязательной ручной проверки.
- [ ] **AC-GATE-04** В disposable fixture подсажены известные дефекты, посчитаны
      survivors и доказано, что реальный target не менялся.
- [ ] **AC-GATE-05** `serve` выбирает свободный порт, готовит fixtures, ждёт
      readiness и гарантированно выполняет teardown.
- [ ] **AC-GATE-06** Security/performance/mutation барьеры имеют opt-in cost,
      stop conditions и не устанавливают зависимости без approval.
- [ ] **AC-GATE-07** `serve` объявляет зависимости поверхностей и поднимает их в
      правильном порядке; repo-level `serve` перекрывает package-level; teardown
      идёт в обратном порядке и не гасит стек, поднятый пользователем до запуска.
- [ ] **AC-GATE-08** Кросс-пакетное изменение обязательно проходит барьер
      `contract`; при его отсутствии штамп верификации **называет непроверенную
      границу явно** (например `контракт API↔admin не проверен`), а не
      ограничивается перечислением пройденного.
- [ ] **AC-GATE-09** Barrier `generate`: если источник сгенерированного артефакта
      изменился, а сам артефакт не перегенерирован, барьер падает и показывает
      диф. Протухший сгенерированный файл не проходит как «тесты зелёные».

## Git и интеграция

- [ ] **AC-GIT-01** При start сохраняются integration target, start SHA и точные
      preconditions; protected/default branch не выбирается молча.
- [ ] **AC-GIT-02** Writer lock/idempotency не дают создать дубликат run.
- [ ] **AC-GIT-03** Роль, входной/выходной SHA, проверки и handoff живут в
      manifest независимо от выбранной worktree/native архитектуры.
- [ ] **AC-GIT-04** Worker не пишет в target worktree/ref; результат приходит
      через integration candidate от актуального target tip.
- [ ] **AC-GIT-05** На candidate повторно выполняется обязательная полоса до
      изменения target.
- [ ] **AC-GIT-06** Target drift и merge conflict воспроизводятся тестами;
      конфликт переводит run в ожидание, а не решается молча.
- [ ] **AC-GIT-07** Dirty worktree, detached HEAD, moved/deleted branch и target в
      другом worktree приводят к безопасному stop, не к stash/reset/ref update.
- [ ] **AC-GIT-08** Повторный integrate идемпотентен; target обновляется только
      при совпадении одобренного SHA и чистых preconditions.

## История коммитов

- [ ] **AC-COMMIT-01** В `work/private` публичные и handoff commits не содержат
      AI/model/role attribution, emoji или agent `Co-authored-by`.
- [ ] **AC-COMMIT-02** Subject короткий и соответствует языку/стилю истории проекта.
- [ ] **AC-COMMIT-03** `pet/verbose` и `custom` включаются только явным opt-in.
- [ ] **AC-COMMIT-04** Валидатор отклоняет запрещённые маркеры до commit/integrate.
- [ ] **AC-COMMIT-05** Issue-id, signoff, GPG/DCO и squash/preserve соблюдают
      подтверждённую project policy; глобальный Git config не меняется.

## Человек, безопасность и приватность

- [ ] **AC-SAFE-01** Approval спецификации и ручная приёмка — две обязательные
      normal-flow точки человека; safety stops не маскируются под них.
- [ ] **AC-SAFE-02** Drift, конфликт, новые зависимости/hooks/CI, network,
      push/PR, секреты и превышение бюджета вызывают дополнительный stop.
- [ ] **AC-SAFE-03** Честный ноль, две итерации без прогресса и budget limit
      останавливают цикл и видны в status/audit.
- [ ] **AC-SAFE-11** Отказ на приёмке возвращает run в работу по определённому
      переходу, а не завершает его: причина отказа фиксируется структурно,
      выбирается роль-получатель, спецификация при необходимости переписывается и
      подписывается заново. У доработки есть тормоза — лимит итераций, застой,
      бюджет — и они видны в `status`.
- [ ] **AC-SAFE-04** До approval показана вилка time/tokens; status показывает
      фактический расход против бюджета.
- [ ] **AC-SAFE-05** Inspect/probe не читают содержимое `.env`, ключей, дампов и
      исключённых policy путей и не сохраняют source/prompts/secrets в manifest.
- [ ] **AC-SAFE-06** Path traversal и symlink не позволяют выйти за разрешённый
      target/root; найденные команды не исполняются как часть inspect.
- [ ] **AC-SAFE-07** Network, публикация кода, push и PR запрещены по умолчанию и
      требуют точного scoped approval.
- [ ] **AC-SAFE-08** `shared-repo` не меняет tracked files, общий `.gitignore`,
      hooks/CI или поведение сессий коллег.
- [ ] **AC-SAFE-09** В `shared-repo` каждый устанавливаемый путь проверяется на
      фактическое игнорирование (`git check-ignore`), а не на отсутствие в
      индексе; правило добавляется в `.git/info/exclude`, а не в общий
      `.gitignore`. Недостижимое игнорирование — blocking finding.
- [ ] **AC-SAFE-10** Существующие git hooks не перезаписываются; `pre-push`
      обнаружен и учтён до первой интеграции, а не встречен в момент push.

## Обучение между прогонами

- [ ] **AC-LEARN-01** По итогам прогона структурно накапливаются причины отказов,
      статистика срабатывания барьеров и места, где спецификации оказались
      дырявыми; формат пригоден для машинного чтения, а не только для человека.
- [ ] **AC-LEARN-02** Повторение одного класса замечаний N раз даёт **предложение**
      завести барьер или правило роли; предложение показывается человеку и никогда
      не применяется само. Ноль уроков — валидный результат, квоты нет.
- [ ] **AC-LEARN-03** Накопленное не покидает границ privacy-профиля: в
      `shared-repo` не попадает в tracked files, содержимое исходников и секретов
      в записи не сохраняется.
