## Вопросы

### 1b.4. Как безопасно менять `AGENTS.md`

Установка не имеет права перезаписывать существующие инструкции. Добавляется
короткий идемпотентный managed-блок:

```text
<!-- AI-PIPELINE:BEGIN — managed; edit source config, not this block -->
...минимальное правило start/resume/integrate и ссылка на локальный runbook...
<!-- AI-PIPELINE:END -->
```

Planner показывает diff блока до применения, хранит fingerprint прежнего
состояния, обновляет только свой диапазон и останавливается, если пользователь
изменил его вручную. Соседние блоки AI Knowledge Engine и пользовательский текст
сохраняются байт-в-байт. Те же требования — для host-specific файлов, если
включены Claude Code или Cursor; дублировать полную конституцию во все файлы
нельзя. Никаких автоматических symlink между `AGENTS.md` и `CLAUDE.md`: оба файла
могут уже иметь разный смысл.

**Но существующий symlink обязателен к обнаружению.** В `../iladno` уже сделано
`CLAUDE.md -> AGENTS.md`. Если этого не заметить, инструмент запишет managed-блок
дважды в одни и те же байты и заведёт два fingerprint на один файл — а `upgrade`
потом увидит несуществующий drift.

Правило: перед записью резолвить каждый instruction-путь и сравнивать по inode
или каноническому пути. Совпали — это **один** файл: один блок, один fingerprint,
одна запись в install manifest, а второй путь фиксируется как alias. Мы такие
symlink не создаём, но чужие уважаем и не разрываем.

**Бюджет блока — максимум 20 строк:** trigger/start-or-resume, worker guard,
bypass и ссылка на project-local runbook/config. Команды тестов и подробные роли
остаются там и не дублируют `CONTRIBUTING`, manifests или linter configs.
Проверить instruction-size budget каждого хоста по evidence фазы 0. Для Codex
текущий известный default может быть 32 KiB суммарно на цепочку `AGENTS.md`, но
источником истины остаётся зафиксированная версия и официальный контракт из
фазы 0; поведение при переполнении проверяется отдельным probe, а не считается
«молчаливым» без доказательства.

**Бюджет инструкций — блокирующее precondition, а не предупреждение.**
Проверено на `/home/popovalpe/www/esia/msh-nto`: тамошний `AGENTS.md` весит
**44 626 байт** — то есть на 36% больше известного лимита Codex **сам по себе**,
ещё до нашего блока и до глобального `~/.codex/AGENTS.md`.

В таком проекте managed-блок может не быть прочитан **никогда**, а инструмент
будет считать себя установленным. Это худший исход из возможных: молчаливый
отказ, замаскированный под успех.

Поэтому `inspect` меряет не свой блок, а **весь бюджет инструкций хоста**, и
результат влияет на установку:

| Занято от лимита | Поведение |
|---|---|
| < 60% | ставим обычно |
| 60–90% | ставим, change plan показывает остаток и предупреждает |
| > 90% или уже превышен | **apply отказывается** до разрешения человеком |

Варианты разрешения инструмент предлагает, но не выбирает сам: вынести часть
инструкций во вложенные `AGENTS.md` по каталогам (собственная рекомендация Codex
при упоре в лимит), сократить существующий файл, поднять лимит хоста, либо
поставить осознанно — но тогда «блок может не читаться» записывается в install
manifest как известный дефект и показывается в `doctor`.

Глобальное правило различает три контекста:

1. **Обычная сессия:** перед нетривиальной кодовой задачей запустить новый run
   или продолжить существующий; для typo/docs-only — настраиваемый bypass.
2. **Оркестратор:** один владелец меняет состояние, выдаёт handoff и интегрирует.
3. **Worker внутри run:** выполнить только назначенную роль и **не запускать новый
   конвейер рекурсивно**. Контекст run/role передаётся проверяемым host adapter,
   а не догадкой модели.

`doctor` пассивно проверяет, что bootstrap и ссылки структурно корректны и есть
актуальное evidence. Реальный запуск новой сессии/worker и доказательство
worker guard выполняются только через одобренный `probe`, потому что они создают
процессы и могут иметь побочные эффекты.

Для `shared-repo` managed-блок и runtime не попадают в tracked tree. При этом
инициализация считается успешной только если адаптер доказывает discovery
локального bootstrap в трёх местах: текущая сессия, новая сессия из корня и
worker в новом worktree — при неизменном `git status`. Конкретный механизм
(host-local instructions, launcher/wrapper или portable fallback) выбирается в
фазе 3. Если host не даёт надёжного локального entrypoint, это `unsupported` до
мутации, а не скрытая правка общего `AGENTS.md`.

- [ ] Формат и бюджет managed-блока определены
- [ ] Проверен instruction-size budget каждого поддерживаемого хоста
- [ ] Механизм worker guard описан как проверяемый, а не как инструкция модели
- [ ] Для `shared-repo` проверен bootstrap в новой сессии и worker-worktree без
      tracked-изменений

### 1b.5. Git-протокол: принципы и обязательные ситуации

> Здесь — **принципы и список ситуаций**. Сами decision tables и автомат
> состояний зависят от архитектуры и пишутся в фазах 3–4.

Integration-ветка определяется **при старте каждой задачи**, не при установке.
Run manifest запоминает её имя и исходный SHA. Если задача запущена на
`main`/protected, инструмент предлагает feature-ветку или требует явного
подтверждения политики проекта.

Базовый безопасный протокол:

1. Проверить Git preconditions. Не делать автоматический `stash`, `reset`,
   checkout чужой ветки, push или удаление пользовательских веток.
2. Создать run id и изолированный execution context по выбранной в фазе 3
   архитектуре и возможностям host adapter. Это может быть нативный worker,
   цепочка branch/worktree, portable runner или CI; инвариант один: worker не
   пишет напрямую в target worktree/ref, а следующая роль получает только
   одобренный handoff SHA/артефакт. Параллельная работа — только для действительно
   независимых задач.
3. Хранить роль, входной и выходной SHA, команды проверок и результат handoff в
   manifest, а не кодировать provenance в публичном commit message.
4. После последнего барьера создать **integration candidate** от актуального tip
   целевой feature-ветки и применить результат выбранной стратегией.
5. На candidate **заново прогнать обязательную полосу**. Показать base SHA,
   текущий target SHA, список коммитов/файлов, стратегию и конфликты.
6. Обновлять целевую ветку только если её worktree чист, HEAD всё ещё совпадает с
   проверенным SHA и integration plan одобрен. Иначе оставить готовую
   candidate-ветку и точную инструкцию продолжения.

Нельзя фоново двигать ref ветки, которая checkout в пользовательском worktree —
это рассинхронизирует index/working tree. Drift — нормальный сценарий: candidate
пересобирается от нового tip и барьеры выполняются повторно. Конфликт не
разрешается «по смыслу» молча — run переходит в ожидание.

**Ситуации, у которых обязан быть явный ответ** (таблицы — фаза 4):
dirty worktree · detached HEAD · ветка удалена или переименована · target
продвинулся · роль упала до commit · конфликт при интеграции · несколько worktree
уже существуют · прерванный процесс · повторный `integrate`.

- [ ] Принципы протокола зафиксированы
- [ ] Полный список обязательных ситуаций собран
- [ ] Изоляция, base SHA, handoff и candidate заданы как инварианты, а конкретная
      branch/worktree-механика отложена до выбора архитектуры
- [ ] Явно записано: таблицы решений — фаза 4, автомат состояний — фаза 3

### 1b.6. Состояние, продолжение и командный репозиторий

Разделить три вещи:

- **schema-versioned project config** — выбранные host/адаптеры, команды
  барьеров, доступные профили и публичная commit policy; tracked он или локальный,
  определяет privacy profile;
- **mutable run state** — PID/lock, абсолютные локальные пути worktree, счётчики
  бюджета, временные ветки и progress; не должно попадать в публичную историю;
- **durable audit summary** — при необходимости обезличенная трассировка, но
  только если политика проекта разрешает её коммитить.

Исследовать хранение mutable state через `git rev-parse --git-common-dir`, чтобы
все worktree видели один источник правды, а `.git`-file linked worktree не ломал
пути. Схема состояния versioned и мигрируемая; запись атомарная. Secrets, полные
промпты и содержимое исходников в manifest не сохраняются.

`status` и `resume` обязаны работать в новой агентной сессии: перед продолжением
сверять branch/SHA/worktree и команды с manifest, а не доверять тексту
предыдущего агента. На проект — один writer lock, но несколько run могут
существовать, если их integration targets и рабочие области не конфликтуют.
Повторный вызов из `AGENTS.md` сначала ищет resumable run, чтобы не создать дубликат.

**Командный репозиторий — отдельный контракт.** В `shared-repo` `.ai-pipeline/`,
runtime и managed-блоки не коммитятся и не навязываются коллегам. Локальное
состояние хранится вне tracked tree либо в уже игнорируемом месте, не меняя
общий `.gitignore` без отдельного плана. Новая сессия и каждый worker-worktree
обязаны автоматически обнаруживать одну и ту же установку; `probe` воспроизводит
это, а `doctor` затем проверяет сохранённое evidence и неизменный `git status`.

- [ ] Три уровня состояния разделены, с местом хранения каждого
- [ ] Требования к `status` / `resume` сформулированы проверяемо
- [ ] Для `shared-repo` runtime локален и автоматически обнаружим из всех
      worktree без tracked-изменений

### 1b.7. Политика коммитов и видимая история

На инициализации инструмент показывает обнаруженный стиль последних коммитов и
просит подтвердить режим:

- **work/private (безопасный default):** короткая формулировка в стиле истории
  проекта; Conventional Commits только если проект уже их использует; без
  упоминания AI/модели/роли, emoji и `Co-authored-by` от агента; подробности — в
  issue/PR или локальном run manifest;
- **pet/verbose:** разрешено подробное body и, только по отдельному opt-in,
  техническая атрибуция работы агентов;
- **custom:** явный шаблон, язык, максимальная длина subject, обязательные
  issue-id/signoff/GPG/DCO trailers и стратегия squash/preserve.

Два уровня: **internal handoff commits** на временных ветках и **public
integration history**. В `work/private` даже internal-коммиты сразу пишутся в
публично допустимом стиле — нельзя полагаться, что squash всегда произойдёт.
Run id и роль живут только в manifest. Финальный planner показывает точные
сообщения до интеграции, валидатор отклоняет запрещённые маркеры. Глобальный
`git config` пользователя не меняется.

Короткая версия политики попадает в managed-блок `AGENTS.md`, полная — в project
config. Разовая задача может ужесточить режим, но не ослабить `work/private`
без явного подтверждения.

- [ ] Три режима описаны с точными правилами
- [ ] Разделены internal и public уровни истории
- [ ] Определён валидатор запрещённых маркеров

### 1b.8. Точки человека, safety stops и приватность

«Ровно две точки человека» относятся к **нормальному feature-cycle** (см. 1a.5).
Это не отменяет control-plane одобрение установки и опасных изменений.

**Safety stops** — исключения, их может быть больше двух, и скрывать их ради
красивой метрики нельзя: drift · merge conflict · установка зависимостей ·
изменение hooks/CI · network/push/PR · доступ к секретам · превышение бюджета.

Privacy profile фиксируется на инициализации:

| Профиль | Смысл |
|---|---|
| `private-client` | код заказчика; максимальные ограничения |
| `private-personal` | свой закрытый проект |
| `shared-repo` | **рабочий репозиторий с коллегами**: runtime локальный, ничего не коммитится, managed-блок не навязывается чужим сессиям |

| `public` | открытый проект |

По умолчанию запрещены отправка кода/диффов во внешние сервисы помимо уже
выбранного host/model, публикация, push и создание PR без явного разрешения.
Детектор не читает `.env`, ключи, дампы и каталоги, исключённые политикой
проекта; найденное имя secret-файла можно сообщить, содержимое — нет.

**`shared-repo` проверяет, что файлы проигнорированы, а не просто не
отслеживаются.** В `msh-nto` `AGENTS.md` сейчас в состоянии `??` — untracked, но
**не в `.gitignore`**. Один `git add .` — и локальные инструкции уезжают в общий
репозиторий команды вместе с нашим managed-блоком.

«Сейчас не в индексе» — не гарантия. Профиль `shared-repo` обязан убедиться, что
каждый устанавливаемый путь реально покрыт правилом игнорирования (`git
check-ignore`), и при необходимости предложить его добавить — в
`.git/info/exclude`, а не в общий `.gitignore`, чтобы не менять tracked-файл.
Если добиться игнорирования нельзя, это blocking finding, а не примечание.

- [ ] Safety stops перечислены и отделены от двух точек человека
- [ ] Четыре privacy-профиля описаны, включая `shared-repo`
- [ ] `shared-repo` проверяет фактическое игнорирование каждого устанавливаемого
      пути, а не только его отсутствие в индексе
- [ ] Правила работы с секретами сформулированы как запреты

### 1b.9. Жизненный цикл и команды инструмента

Точные имена выберет SPEC, но продуктовый контракт должен покрывать:

```text
inspect TARGET                    # только пассивные факты, никакого исполнения
plan-probe TARGET                # exact plan активных диагностик
probe TARGET PLAN_ID             # выполнить только одобренные диагностики
plan-init TARGET                 # рекомендация + exact change plan
apply-init TARGET PLAN_ID         # drift-check → backup → apply
doctor TARGET                     # пассивная структурная диагностика/discovery
plan-start TARGET TASK            # оценка, preconditions и план создания run
start TARGET PLAN_ID              # создать run по одобренному плану
status / resume RUN_ID         # восстановление в новой сессии
plan-integrate RUN_ID          # exact integration plan
integrate RUN_ID PLAN_ID       # apply только проверенного плана
plan-abort RUN_ID
abort RUN_ID PLAN_ID
plan-cleanup RUN_ID
cleanup RUN_ID PLAN_ID

# обновляемость — см. 1b.11
list-installs [ROOT]           # где и какая версия установлена
plan-upgrade TARGET            # что изменится при переходе на новую версию
upgrade TARGET PLAN_ID         # синхронизация managed-файлов + миграции
plan-upgrade --all-root DIR    # сводный exact plan для batch
upgrade --all-root PLAN_ID [--continue-on-error]
plan-reinit TARGET             # пере-обнаружение проекта + новый план
reinit TARGET PLAN_ID          # применить транзакционную дельту
plan-reinit TARGET --clean     # перечислить все потери чистой переустановки
plan-heal TARGET               # exact plan догоняющей починки runtime
heal TARGET PLAN_ID
plan-rollback TARGET APPLY_ID  # источник отката — конкретная транзакция/backup
rollback TARGET PLAN_ID
plan-uninstall TARGET          # перечислить только owned-артефакты
uninstall TARGET PLAN_ID
```

Каждая mutating-команда идемпотентна и имеет двухфазный plan/apply: apply требует
точный plan id, проверяет preconditions/drift и пишет transaction/apply id.
`--dry-run` — только удобное представление plan, не обход этого протокола.
Команды имеют понятные exit codes и machine-readable JSON. `uninstall` удаляет
только файлы и managed-блоки, которыми владеет инструмент, и отказывается
продолжать при drift.
Временные ветки/worktree не удаляются автоматически, пока результат не
интегрирован или пользователь не подтвердил, что они больше не нужны.

- [ ] Каждая команда описана: вход, выход, что меняет, что проверяет
- [ ] У каждой мутации есть exact plan id, drift-check и transaction/apply id
- [ ] `heal` увязан с механизмом ревизии инструкций из 1a.4

### 1b.10. Стыковка с AI Knowledge Engine

Переиспользуем: паттерн `setup/` → параметризация → `doctor`; структуру
`templates/` + `examples/`; управляемые блоки для апгрейдов; паттерн
`MIGRATIONS.md` / `instructions_review` / `heal`.
Не переиспользуем: `raw/ → processed/ → knowledge/` — это про знание, не про код.

Здесь `finalize` — референс на проверяемое завершение deployment kit, а не имя
команды: project-local runtime остаётся установленным.

**Отдельный вопрос, который стоит проверить:** откуда роль берёт контекст
проекта? В реальном Symfony-репозитории это тонны кода, и «пусть coder сам
разберётся» — это гарантированный context rot. У нас рядом готовый механизм —
паки repomix с потолком токенов и routing-table. Проверить, можно ли отдать роли
один пак вместо того, чтобы она грепала репозиторий с нуля. Может не сложиться,
но вопрос дешёвый и потенциально снимает половину проблемы с контекстом ролей.

**Обмен двусторонний, а не только на вход.** Пак как контекст роли — это вход.
Выход не менее важен: причины отказов, статистика барьеров, дырявые места
спецификаций (см. 1b.13). Проверить, ложится ли это в `interactions/` базы и
годится ли как внешний сигнал для её рефлексии. Отдельно решить, что из
накопленного вообще допустимо коммитить в рабочем репозитории.

- [ ] Список «переиспользуем / не переиспользуем» составлен
- [ ] Решено, живёт ли конвейер рядом с базой и как они делят `AGENTS.md`
- [ ] Проверена гипотеза «пак как источник контекста для роли»
- [ ] Проверен обратный поток: записи конвейера как внешний сигнал для базы

### 1b.11. Обновляемость: тулза меняется, проекты уже стоят

Инструмент будет дорабатываться в процессе эксплуатации: недостатки вылезут на
живых задачах, исходник правится здесь, в `tools/ai-pipeline/`, и исправление
должно доехать до **всех** проектов, где конвейер уже развёрнут. Это не
второстепенная функция, а условие того, что инструментом вообще можно
пользоваться дольше месяца.

#### Две независимые оси изменений

Их нельзя путать, у них разные команды и разные последствия:

| Что изменилось | Команда | Что происходит |
|---|---|---|
| **Тулза** — правки в `tools/ai-pipeline/` | `upgrade` | синхронизировать managed-файлы, прогнать миграции; конфиг и локальные правки сохранить |
| **Проект** — добавились тесты, обновился фреймворк, сменился стек | `reinit` | пере-обнаружить проект, пересчитать capability manifest и профиль, показать дельту |
| **И то, и другое** | `reinit` | включает в себя upgrade |
| **Нужен чистый лист** | `reinit --clean` | снести установку и поставить заново, потеряв конфиг |

> **Про формулировку «сначала убрать старую инициализацию, потом сделать новую».**
> Как модель мышления — верно. Как реализация по умолчанию — опасна, и вот почему:
>
> - **Теряется заработанная конфигурация.** Команды барьеров, пороги, commit
>   policy, privacy profile, ответы на вопросы инициализации — всё это добывалось
>   через inspect и подтверждалось человеком. Снос означает пройти init заново на
>   каждом проекте после каждой правки тулзы. После третьего раза этим перестанут
>   пользоваться.
> - **Операция не атомарна.** Между «снесли» и «поставили» проект находится в
>   сломанном состоянии. Падение процесса, конфликт, отказ пользователя на
>   середине — и в репозитории полуустановка.
> - **Локальные правки под конкретный проект — легитимны.** У WordPress-сайта
>   команда e2e может быть подкручена руками. Снос молча их выбросит.
>
> Рекомендация: `reinit` по умолчанию **вычисляет дельту и применяет её
> транзакционно**, сохраняя конфиг; `--clean` остаётся явной кнопкой «мне правда
> нужен чистый лист», и она честно перечисляет, что будет потеряно.

#### Install manifest — без него ничего из этого не работает

Установка обязана записать, что именно она создала:

- immutable identity поставки: `bundle_id`, content hash, source commit и
  запись из release manifest;
- список файлов с хешами на момент установки;
- диапазоны и fingerprint managed-блоков в чужих файлах (`AGENTS.md` и т. д.);
- версия тулзы, версия схемы конфига, версия схемы состояния;
- plan id и transaction/apply id каждой применённой операции, включая backup id;
- какие ответы дал человек на init и когда;
- какие зависимости/хуки/CI были добавлены с его согласия.

Без такого манифеста «убрать старую инициализацию» — это угадывание: инструмент
либо удалит пользовательский файл, либо оставит сироту. **Манифест должен
появиться в slice 1B**, до того как что-то будет установлено хоть куда-то.
Ретроспективно восстановить ownership уже установленных файлов невозможно.

#### Три состояния файла при обновлении

Тот же приём, что в `kb_upgrade.py`: release manifest связывает immutable bundle
с хешами всех shipped-файлов, а инструмент по известной истории доказывает, что
файл не трогали. Версия без известного release manifest не устанавливается и не
используется как источник автоматического overwrite.

| Состояние | Что делаем |
|---|---|
| `up_to_date` | ничего |
| `clean_overwrite` | хеш совпал с известной исторической версией → безопасно перезаписать |
| `customized` | не совпал → **не трогаем**, пишем `.new` сидекар и просим человека или агента слить |

Managed-блоки в чужих файлах — так же: обновляем только свой диапазон, при
ручной правке блока останавливаемся.

#### Реестр миграций

Тот же паттерн, что заводится в соседнем плане для базы: `MIGRATIONS.md` тулзы,
где каждая версия объявляет, что должна доделать **уже установленная** инсталляция.
`upgrade` берёт диапазон между версией в install manifest и текущей и применяет
только его. Корзины те же: `auto` / `assisted` / `human`.

#### Фан-аут на все проекты

Владелец правит исходник один раз и хочет починить «для всех»:

- `list-installs [ROOT]` — где стоит конвейер и какой версии. Реестр инсталляций
  (например, `~/.ai-pipeline/installs.json`) **проверяется при чтении**: путь мог
  исчезнуть или быть переименован. Альтернатива — скан каталога, как
  `kb_upgrade.py --all-root`. Решить, что надёжнее.
- `plan-upgrade --all-root <dir>` — сводный план по всем найденным.
- Батч всегда сначала строит сводный план. Default — **fail-fast**: каждый проект
  атомарен; текущий неуспешный проект откатывается к своему backup, уже успешно
  обновлённые остаются обновлёнными, ещё не начатые не меняются. Продолжение
  после ошибки разрешает только явный `--continue-on-error`; итог содержит
  результат и transaction id по каждому проекту.

#### Незавершённые прогоны и схема состояния

- `upgrade` / `reinit` **отказываются работать при активном run**. Либо доведи,
  либо `abort`. Схема состояния может измениться между версиями.
- У состояния есть `state_schema_version` и правила миграции; если мигрировать
  нельзя — честный отказ с инструкцией, а не молчаливая порча.

#### Что переживает обновление — явный контракт

| | |
|---|---|
| **Сохраняется** | ответы init, commit policy, privacy profile, история прогонов, локально подкрученные команды барьеров |
| **Пересчитывается** | обнаруженный стек, capability manifest, рекомендация профиля |
| **Удаляется только с подтверждения** | временные ветки и worktree незавершённых прогонов |
| **Не трогается никогда** | код проекта, текст `AGENTS.md` вне managed-блока, git refs, глобальный `git config` |

#### Проверка, что обновление не сломало конвейер

Мало применить файлы — надо доказать, что новая версия работает:

- `doctor` после каждого `upgrade` / `reinit`, автоматически;
- бэкап перед применением и команда `rollback` к предыдущей версии;
- на disposable fixture — прогон полосы новой версии с подсаженными дефектами.
  Обновление, после которого полоса перестала ловить мутации, должно
  откатываться, а не считаться успешным.

- [ ] Разделены оси «изменилась тулза» и «изменился проект», у каждой своя команда
- [ ] Определена схема install manifest и то, что он обязан записывать
- [ ] Определены immutable bundle/release identity и transaction/apply ids
- [ ] Описаны три состояния файла и поведение при `customized`
- [ ] Заложен `MIGRATIONS.md` тулзы с корзинами auto/assisted/human
- [ ] Решено, как находить все инсталляции: реестр или скан
- [ ] Зафиксированы fail-fast и `--continue-on-error` semantics для batch
- [ ] Прописан отказ при активном run и `state_schema_version`
- [ ] Составлен контракт «что переживает обновление»
- [ ] Определены backup, `rollback` и проверка полосы после апгрейда
- [ ] Явно сказано, что `--clean` перечисляет потери перед выполнением

### 1b.12. Петля доработки: что происходит, когда человек не принял

Самый частый реальный исход приёмки — не «принято» и не «всё заново», а
**«почти, но переделай вот это»**. В автомате состояний есть `awaiting-acceptance`,
но ребра назад нет: описан только успешный путь. Это дыра, а не пропущенный
частный случай.

Причём это единственное место, где в конвейер попадает **настоящий внешний
сигнал от человека**. По правилу из статьи о циклах итерация легитимна, только
если получает информацию, которой не было в предыдущей; причина отказа — ровно
она. Без петли доработки конвейер умеет только «получилось» и «не получилось».

Вопросы, на которые нужен явный ответ:

- **Куда возвращается работа.** К coder, если сломана реализация; к specifier,
  если оказалась дырявой спецификация. Кто решает — человек или правило по
  формулировке отказа?
- **Что происходит со спецификацией.** Если отказ означает, что ТЗ было неполным,
  спецификация переписывается и **проходит подпись человека заново** — иначе
  вторая точка человека начинает подменять первую.
- **Одна итерация того же run или новый run.** Склоняюсь к первому: та же
  integration target, тот же run id, счётчик итераций растёт. Иначе история
  доработок рассыпается на несвязанные прогоны.
- **Что происходит с уже сделанными handoff-коммитами.** Остаются в цепочке или
  отбрасываются? От этого зависит, что увидит человек в integration candidate.
- **Тормоза.** Доработка — это цикл, значит нужны стоп-условия: лимит итераций,
  застой (две доработки без движения по существу замечаний), исчерпанный бюджет.
  Пятая доработка подряд — сигнал, что задачу надо переставить, а не докрутить.
- **Причина отказа обязана быть записана структурно**, а не только произнесена в
  чате: она нужна и следующей итерации, и накоплению из 1b.13.

- [ ] Определены переходы из `awaiting-acceptance` назад, с правилом выбора роли
- [ ] Сказано, когда отказ требует переписать и заново подписать спецификацию
- [ ] Решено, итерация это того же run или новый run
- [ ] Определена судьба handoff-коммитов при доработке
- [ ] Заданы тормоза доработки: лимит итераций, застой, бюджет
- [ ] Причина отказа фиксируется структурно, а не только текстом в чате

### 1b.13. Что конвейер узнаёт о себе между прогонами

Второй принцип из статьи о циклах: **не исправляй единичный случай — закодируй
урок в систему**, чтобы он работал во всех будущих запусках. Сейчас каждый run
стартует с чистого листа, и агент будет наступать на одни и те же грабли ровно
столько раз, сколько запусков.

Что накапливается само собой и просится в систему:

- причины отказов на приёмке — по категориям, а не текстом;
- какой барьер сколько дефектов поймал, а какой ни разу не сработал;
- где спецификации систематически оказываются дырявыми;
- сколько итераций доработки в среднем уходит на задачу такого типа;
- какие `inferred`-команды человек подтвердил, а какие отверг.

Правило превращения: если один и тот же класс замечаний повторился N раз, это
кандидат в **барьер или правило роли**, а не повод чинить в N+1-й раз вручную.
Предложение показывается человеку, а не применяется само.

**Асимметрия, которую надо закрыть.** Пункт 1b.10 спрашивает только про вход —
пак базы знаний как контекст для роли. Про выход не спрашивает ничего. А
конвейер производит именно тот материал, ради которого база и существует. База
знаний стоит рядом, у неё уже есть `interactions/`, `insights/` и рефлексия по
внешнему сигналу — и записи конвейера будут для неё честным внешним сигналом, в
отличие от синтеза из самой себя.

Здесь же — тормоза, чтобы не получить закон Гудхарта: накопление не должно
превращаться в квоту «выдай N уроков за период». Ноль уроков — валидный результат.

- [ ] Определено, что именно накапливается по итогам прогона и в каком формате
- [ ] Задано правило «N повторов → кандидат в барьер или правило роли»
- [ ] Решено, куда пишется накопленное: в project-local runtime, в базу знаний
      или в оба, и что из этого допустимо коммитить
- [ ] Предложение изменений показывается человеку, а не применяется само
- [ ] Ноль уроков — валидный результат, квоты нет
