## Зачем

Знания модели отстают. `swarm-forge` создан 17.04.2026, статья от 07.08.2026, API
хостов меняется ежемесячно. Любая фаза, начатая без этого шага, будет
проектировать под воображаемые возможности host API.

Отдельная цель — **зафиксировать дату и версию каждого внешнего контракта**, на
который мы опираемся. Позже `doctor` инструмента должен отличать подтверждённую
возможность от догадки, а для этого нужен исходный слепок.

## Задачи

- [ ] Разобрать репозиторий `github.com/unclebob/swarm-forge` по факту: роли,
      конституция, скрипты запуска, формат handoff. **Не пересказ статьи.**
- [ ] Посмотреть `github.com/unclebob/missile-command` — как выглядят 27 файлов
      спецификаций и вшитые отчёты мутационных прогонов на реальном проекте.
- [ ] Для **Codex, Claude Code и Cursor** собрать одинаковую capability matrix:
      версия · автоматические project instructions · local-only override · запуск
      worker/субагента · передача role/run context · resume · worktree · hooks ·
      background tasks · machine-readable status. Проверить официальную
      документацию **и** локально установленную версию каждого доступного хоста.
- [ ] Codex: семантика `AGENTS.md` и `AGENTS.override.md` — порядок загрузки,
      правила приоритета, лимит `project_doc_max_bytes`, поведение при
      переполнении. Проверить, можно ли надёжно передать worker-контекст, **не**
      меняя публичные файлы проекта на время прогона.
- [ ] Claude Code: отдельно проверить `CLAUDE.md`, локальные настройки,
      subagents/Agent Teams, `/goal`, worktree-изоляцию и hooks.
- [ ] Cursor: отдельно проверить project rules, user rules, background agents,
      worktree/checkout model и способ передать локальный worker-context.
- [ ] Для каждого хоста проверить `shared-repo` сценарий: новая основная сессия и
      новый worker-worktree находят локальный runtime, но `git status` не меняется.
      Непроверяемое пометить `unknown`, не подменять инструкцией «агент поймёт».
- [ ] Инструменты барьеров из таблицы 1a: живы ли, какие версии, совместимость
      с поддерживаемыми Symfony / WordPress.
- [ ] **Достижимость изолированного probe — проверить живьём, а не рассуждением.**
      Взять один Symfony и один WordPress fixture и выяснить, можно ли выполнить
      их реальные команды (`unit`, `e2e`, `serve`) в disposable worktree или
      контейнере так, чтобы побочные эффекты были ограничены и обратимы. Для
      каждой команды зафиксировать: что она пишет за пределы рабочей копии, нужна
      ли сеть, нужен ли Docker, можно ли гарантировать teardown.

  > Зачем это здесь. Правило из 1b.1 говорит: если безопасную изоляцию доказать
  > нельзя — команда остаётся `declared`, probe возвращает `unsupported`.
  > Применённое строго, оно рискует сделать `verified` **практически
  > недостижимым именно на целевых стеках**: `wp-env` требует Docker, DDEV
  > мутирует БД, `composer test` пишет кеши. Тогда вся ветка `serve` + e2e
  > схлопнется в «объявлено, но не проверено» — ровно та проблема, от которой мы
  > уходили.
  >
  > Фаза 2 обязана принять по этому решение (вопрос 6). Без фактов из этого
  > пункта она примет его вслепую. Возможный исход — легализовать «probe с
  > раскрытыми side effects по явному одобрению» как нормальный путь, а не как
  > исключение; но это должно быть выводом из замера, а не догадкой.
- [ ] Git worktree/ref edge cases: проверить на маленьком **временном**
      репозитории — ref locking, поведение при checkout ветки в другом worktree,
      `git rev-parse --git-common-dir` в linked worktree. Всё созданное в probe
      пометить как throwaway и удалить.
- [ ] Пост команды Claude Code «Getting started with loops» — актуальная
      классификация циклов и стоп-условий.
