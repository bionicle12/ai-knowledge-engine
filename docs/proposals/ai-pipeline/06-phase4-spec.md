# Фаза 4 — ТЗ и нарезка на vertical slices

**Статус:** ☐ не начата
**Выход:** `tools/ai-pipeline/SPEC.md` + карта slices
**Зависимости:** фаза 3 (архитектура выбрана, бриф собран).

---

## Зачем

Превратить бриф в проверяемое ТЗ и разрезать работу так, чтобы каждый кусок был
полезен сам по себе. Задача слишком велика для одного implementation plan.

---

## Форма ТЗ

Короткое, по формуле **outcome-first: результат → критерии готовности →
ограничения → живой контекст**. Не список шагов. Референсы вместо описаний.

Причина не стилистическая: длина промпта почти бесплатна, а вот пошаговые
описания процессов, которые модель и так выполняет надёжно, — это чистый долг.
Плюс SPEC будут читать все будущие сессии реализации.

## Что обязано войти

- [ ] Заполненный паспорт цикла (семь полей из фазы 1a.6)
- [ ] Явный список инвариантов — того, что не меняется никогда
- [ ] Команды product lifecycle: вход, выход, идемпотентность, exit codes, JSON
- [ ] Разделение пассивного `inspect` и активного двухфазного `probe`, включая
      изоляцию, side effects, cleanup и статусы capability с evidence/timestamp
- [ ] Формальный контракт portable core ↔ host adapter: discovery инструкций,
      запуск роли, передача run/role context, resume, worker guard и матрица
      `native / portable fallback / unsupported` для Codex, Claude Code, Cursor
- [ ] **Тестовый шов исполнителя ролей**: контракт, позволяющий подменить живого
      агента детерминированным stub, и правило, что вся логика ядра (state,
      resume, Git-протокол, drift, integration) проверяется именно через него.
      Без шва группа A fixture-матрицы неисполнима
- [ ] **Схема декларативного стекового адаптера** (versioned): detect-правила с
      confidence, capabilities с командами/cwd/timeout/prerequisites/cost,
      `surface`, пороги, признак `unsupported` с причиной. Плюс порядок
      переопределения встроенный → пользовательский → проектный и правило, что
      встроенные адаптеры используют ровно тот же формат
- [ ] **Контракт `surface`** (`http` / `cli` / `library` / `tui` / `none`): как
      поднять, как обратиться, как определить готовность, как гарантированно
      погасить; поведение при `none`
- [ ] **Scope capability** (`package` / `repo`), правило обязательности
      repo-scoped барьеров при кросс-пакетном изменении и граф зависимостей
      `serve` с порядком подъёма и погашения
- [ ] **Барьер `contract`** между `unit` и `e2e`: чем закрывается в каждом
      референсном стеке и как штамп верификации называет непроверенную границу
- [ ] **Барьер `generate`** и правило «протухший сгенерированный артефакт =
      провал»; границы пакетов по манифестам **и** по явным путям
- [ ] **Провенанс capability**: `declared` против `inferred`, путь и строка
      источника, требование подтверждения для `inferred`; нечитаемый или внешний
      CI даёт `unknown`, а читаемый граф джобов предлагается как определение полосы
- [ ] **Бюджет инструкций как precondition** с порогами 60% / 90% и поведением
      `apply` при превышении; фактическая проверка игнорирования путей в
      `shared-repo` через `git check-ignore`
- [ ] **Git decision tables** — теперь можно, архитектура выбрана. Обязательны для:
      dirty worktree · detached HEAD · ветка удалена/переименована · target
      продвинулся · роль упала до commit · конфликт при интеграции · несколько
      worktree уже существуют · прерванный процесс · повторный `integrate`
- [ ] Финальный автомат состояний run (из выбранного варианта фазы 3),
      **включая переходы петли доработки** после отказа на приёмке и её тормоза
- [ ] Формат накопления между прогонами и правило «N повторов → предложение
      завести барьер или правило роли»
- [ ] Ownership каждого managed-файла: кто создаёт, кто обновляет, кто удаляет
- [ ] Формат штампа уровня проверки и где он показывается
- [ ] Capability manifest как формальный контракт, включая `serve` и `fixtures`
- [ ] `shared-repo` bootstrap: current/new session и worker-worktree обнаруживают
      локальный runtime при неизменном tracked tree и `git status`
- [ ] **Схема install manifest** — файлы, хеши, диапазоны и fingerprint
      managed-блоков, версии тулзы / конфига / состояния, ответы init, добавленные
      с согласия зависимости и хуки, а также `bundle_id`, content hash, source
      commit, release manifest, plan/transaction/apply/backup ids
- [ ] Формат immutable release manifest и запрет `clean_overwrite` из неизвестной
      поставки
- [ ] **Формат `MIGRATIONS.md` тулзы** и правило: каждая версия дописывает свои
      записи тем же коммитом, что и саму возможность
- [ ] **Контракт обновления**: что сохраняется, что пересчитывается, что удаляется
      только с подтверждения, что не трогается никогда
- [ ] Двухфазный plan/apply-контракт всех мутаций и fail-fast semantics batch с
      явным `--continue-on-error`
- [ ] `state_schema_version` и правила миграции состояния; поведение, когда
      мигрировать нельзя
- [ ] Ссылка на [08-acceptance-criteria.md](08-acceptance-criteria.md) как на
      приёмочный набор — **не копировать его в SPEC**

## Предварительная нарезка на vertical slices

Фаза 4 вправе уточнить границы после выбора архитектуры, но не выбрасывать ни
одну строку полного scope. Каждый slice должен быть полезен и проверяем отдельно:

| # | Slice | Самостоятельный результат |
|---|---|---|
| 1A | пассивный `inspect`, evidence schema, generic capability discovery | безопасный machine-readable отчёт без исполнения project code |
| 1B | recommendation, `plan-probe/probe`, `plan-init/apply-init`, install/release manifests, local bootstrap трёх hosts | проект можно проверить и установить транзакционно |
| 2A | portable run state, writer lock, `status`/`resume`, budgets, **stub role executor** | прерванный run восстанавливается без памяти чата; ядро тестируемо без живых агентов |
| 2B | профиль 2 и role/handoff adapters для Codex, Claude Code и Cursor | одинаковый двухролевой цикл на каждом поддерживаемом host; прогресс считается по хостам отдельно |
| 2C | integration candidate, Git preconditions/drift/conflict, повторная полоса | результат безопасно возвращается в актуальную feature-ветку |
| 3A | immutable bundles, registry, `list-installs`, `plan-upgrade/upgrade`, migrations, batch | установленные проекты получают новую версию доказуемо |
| 3B | `reinit`, `heal`, `rollback`, `uninstall`, `--clean`, state migrations | полный восстановимый lifecycle без сноса по умолчанию |
| 4A | **схема декларативного адаптера, generic-режим, `surface`-контракт** | новый стек заводится манифестом без патча оркестратора |
| 4B | референсные адаптеры по осям различий: HTTP+БД (Symfony), HTTP без БД (Node/Bun), компилируемый CLI/библиотека (Rust), фронтенд-сборка (React) | абстракция проверена на непохожих тулчейнах |
| 4C | WordPress plugin/theme/site + `wp-env`/DDEV/Docker | самый тяжёлый случай `serve`, три формы одного стека |
| 4D | mixed/monorepo routing, `scope: package \| repo`, граф зависимостей `serve`, барьер `contract` | затронутые пакеты определяют профиль и полосу, а кросс-пакетная граница проверяется дёшево |
| 5A | профили 4/6, escalation/de-escalation и профиль 0 | полная лестница размеров без лишнего расхода |
| 5B | hardening, mutation/security/performance barriers, dogfooding и John Henry | полная проверка самой полосы и честные эксплуатационные границы |

> **Install/release manifests — обязательны в slice 1B.** Ретроспективно
> восстановить, какие
> файлы принадлежат инструменту, невозможно: после первой установки без манифеста
> любой upgrade превращается в угадывание. По той же причине `MIGRATIONS.md`
> заводится вместе с ним, даже если первая миграция появится только в slice 3A.
>
> Slices 3A/3B стоят перед framework slices 4A–4C, а не в конце: как только
> конвейер начнёт работать на
> реальных задачах, недостатки полезут сразу, и чинить их надо будет во всех
> инсталляциях, а не только в исходнике.
>
> **2C зависит от 2B по одному хосту, не по всем трём.** Git-протокол,
> integration candidate и drift живут в ядре и проверяются stub-исполнителем из
> 2A. Если бы 2C ждал готовности всех трёх adapters, доска слайсов вставала бы
> на самом слабом хосте — а какой из них слабый, до фазы 0 неизвестно.
> Референсный host для 2B выбирается **по evidence capability matrix**, а не по
> предпочтению; остальные два портируются следом и отмечаются отдельно.

Каждый slice получает **отдельный implementation plan после утверждения SPEC** —
не в этой фазе.

- [ ] Slices определены, у каждого свой критерий полезности
- [ ] Для каждого сказано, что он НЕ делает
- [ ] Порядок обоснован

## Матрица slice → acceptance criteria

Номера берутся из [08-acceptance-criteria.md](08-acceptance-criteria.md). Фаза 4
уточняет конкретные строки, но не оставляет критерий без owning slice.

| Slice | Основные acceptance criteria |
|---|---|
| 1A | AC-CP-01–02, AC-CP-14, AC-ST-01–02, AC-ST-10, AC-ST-12, AC-SAFE-05–06 |
| 1B | AC-CP-03–08, AC-HOST-01–04, AC-HOST-08–09, AC-UP-01–02, AC-GATE-01–02, AC-SAFE-09–10 |
| 2A | AC-CP-09–10, AC-CP-13, AC-GIT-01–03, AC-SAFE-03–04, AC-SAFE-11 |
| 2B | AC-HOST-05–06, AC-ROLE-01–03 |
| 2C | AC-GIT-04–08, AC-COMMIT-01–05 |
| 3A | AC-UP-03–09, AC-UP-15–16 |
| 3B | AC-UP-10–14, AC-CP-11–12, AC-HOST-07 |
| 4A | AC-ST-06–08 (схема адаптера, generic-режим, `surface`) |
| 4B | AC-ST-03–05, **AC-GATE-05** (референсные стеки по осям различий) |
| 4C | AC-ST-03–05, **AC-GATE-05** (WordPress plugin/theme/site fixtures) |
| 4D | AC-ST-02–05, AC-ST-09, AC-ST-11, AC-GATE-07–09 (mixed/monorepo fixtures) |
| 5A | AC-ROLE-04–07 |
| 5B | AC-GATE-03–04, AC-GATE-06, AC-SAFE-01–08, AC-LEARN-01–03, AC-DOC-01–03 |

> Два критерия перевешены осознанно. **AC-GATE-05** (`serve`: свободный порт,
> fixtures, readiness, гарантированный teardown) принадлежит 4A и 4B — именно там
> `serve` и строится; оставлять его за 5B значило бы поставлять возможность без
> владельца её приёмки. **AC-GATE-01–02** (барьеры собраны из реальных команд
> проекта, у них пороги, cwd, timeout и evidence) переезжают в 1B, где рождается
> capability manifest.

## Граница первой полезной поставки и полный scope

- [ ] Первая end-to-end поставка заканчивается после 2C и запускает профиль 2 в
      Codex, Claude Code и Cursor: отсутствие нужной native capability закрывает
      portable fallback; прочие ещё не реализованные capabilities честно
      возвращают `unsupported` до мутации
- [ ] Полный согласованный объём заканчивается после 5B; ни один заявленный host,
      стек, профиль, lifecycle-команда или barrier не выносится «когда-нибудь»
- [ ] Для временно недоступной возможности на промежуточном slice указан рабочий
      fallback и следующий owning slice

## Чего в этой фазе НЕ делать

- Не писать implementation plan отдельных slices — они пишутся по одному, после
  review SPEC.
- Не писать код.
- Не копировать критерии приёмки в SPEC — ссылаться.

## Промпт запуска

```text
[вставить общие правила из README.md]

Делаем фазу 4 — файл docs/proposals/ai-pipeline/06-phase4-spec.md.
Прочитай tools/ai-pipeline/VARIANTS.md, tools/ai-pipeline/BRIEF.md и все решения
из docs/proposals/ai-pipeline/DECISIONS.md.

Готово, когда есть tools/ai-pipeline/SPEC.md по формуле outcome-first (результат →
критерии готовности → ограничения → живой контекст, НЕ список шагов), со всем
из раздела «Что обязано войти», включая Git decision tables и финальный автомат
состояний — их теперь можно писать, архитектура выбрана.

Плюс карта granular vertical slices и матрица slice → acceptance criterion:
каждый slice полезен без следующего, у каждого сказано и что он делает, и чего
не делает; ни один criterion не остаётся без owning slice.

Ограничения:
- Implementation plan отдельных slices не пиши — они пойдут по одному после
  review SPEC.
- Критерии приёмки не копируй в SPEC, сошлись на 08-acceptance-criteria.md.
- Код не пиши.
```
