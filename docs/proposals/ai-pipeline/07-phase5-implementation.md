# Фаза 5 — реализация

**Статус:** ☐ не начата
**Выход:** работающий `tools/ai-pipeline`
**Зависимости:** фаза 4 (SPEC утверждён, slices нарезаны).

---

## Правила

Один slice — один implementation plan — один запуск. TDD. План хранится в
`docs/superpowers/plans/YYYY-MM-DD-ai-pipeline-slice-<id>.md` и содержит точные
файлы/интерфейсы, сначала падающие и затем проходящие команды тестов, commit
boundaries/messages и owning AC IDs. Следующий slice не начинается, пока
предыдущий не проверен на применимой fixture-матрице.

## Fixture-матрица

Один happy-path прогон ничего не доказывает. Но и «прогонять всё на каждом
slice» — нереализуемо: часть случаев требует настоящих агентных прогонов в трёх
разных клиентах. Смешать их в один список значит получить матрицу, которую со
второго slice начнут молча игнорировать.

Поэтому матрица разделена по **стоимости прогона**, а не по важности.

### A. Автоматическая регрессия — гоняется целиком на каждом slice

Быстрая, детерминированная, без настоящих агентов: роли подменяются
**stub role executor** (см. врезку ниже).

- [ ] пустой каталог без Git
- [ ] новый Git с одним коммитом
- [ ] существующий `AGENTS.md` с чужими managed-блоками
- [ ] проект вообще без тестов (legacy)

Стековые fixtures — по осям различий, а не по списку фреймворков:

- [ ] Symfony — интерпретируемый, HTTP, нужна БД
- [ ] Node или Bun-сервис — интерпретируемый, HTTP, без БД
- [ ] React-приложение — сборка, фронтенд, dev server
- [ ] Rust-крейт — компилируемый, `surface: cli`
- [ ] Rust-библиотека или пакет без бинаря — `surface: library`
- [ ] WordPress plugin
- [ ] WordPress theme
- [ ] **mixed / monorepo — эталонный fixture по образцу `../iladno`**: Symfony
      API + React-админка + корневые e2e на Playwright + pytest-тесты деплоя,
      один `serve` на весь стек, `CLAUDE.md` симлинком на `AGENTS.md`.
      Проверяются четыре вещи:
      - [ ] правка только в админке → барьеры только её пакета
      - [ ] правка только в Symfony → барьеры только его пакета
      - [ ] **кросс-пакетная правка** → union барьеров плюс обязательные
            repo-scoped `contract` и `e2e`
      - [ ] корневые `tests/e2e` и `tests/deployment` не теряются при
            маршрутизации по затронутым пакетам
- [ ] **граф `serve`**: цепочка поднимается в правильном порядке, гасится в
      обратном; стек, поднятый пользователем заранее, не убивается
- [ ] **контракт сломан намеренно**: изменить форму ответа API, не трогая
      админку. Барьер `contract` обязан упасть; если его нет — штамп верификации
      обязан явно назвать непроверенную границу
- [ ] **симлинк instruction-файлов**: managed-блок записан один раз, fingerprint
      один, симлинк цел; повторный `upgrade` не видит фантомный drift
- [ ] **коллизия имён**: в проекте уже есть скрипт с именем, которое инструмент
      собирается занять (в iladno это `swarm-start.sh`) — change plan показывает
      коллизию, apply без её разрешения не идёт
- [ ] **переполненный бюджет инструкций** (по образцу `msh-nto`: `AGENTS.md`
      44 626 байт при лимите 32 KiB): `apply` отказывается, предлагает варианты
      разрешения; установка «всё равно» помечает дефект в install manifest
- [ ] **пустые скрипты в манифесте** (по образцу `msh-nto`: `composer.json` без
      `scripts`, но с `phpunit.xml.dist`): команда попадает в `inferred`
      и не идёт в полосу без подтверждения
- [ ] **CI недоступен** (`include` из чужого репозитория): статус `unknown`,
      а не «проверок нет»
- [ ] **untracked, но не ignored** (по образцу `msh-nto`: `?? AGENTS.md`):
      в профиле `shared-repo` путь добавляется в `.git/info/exclude`, общий
      `.gitignore` не меняется
- [ ] **многопакетный продуктовый репозиторий** (по образцу `playflowb2b`:
      Rust workspace + React + VitePress + статические сайты + SDK на трёх языках
      + интеграции + bash-тесты):
      - [ ] `sdk/js/playflow.js` без манифеста обнаружен как пакет
      - [ ] правка Rust API помечает `docs-site` как требующий регенерации
            (`sync:openapi`), протухший артефакт валит барьер `generate`
      - [ ] правка, затрагивающая `sdk/` или `integrations/`, повышает профиль
      - [ ] граф джобов `.github/workflows/ci.yml` предложен как определение
            порядка барьеров, а не проигнорирован
- [ ] **нераспознанный стек** — generic-режим: инструмент не падает, предлагает
      шаблон манифеста, работает на подтверждённых человеком командах
- [ ] **пользовательский адаптер с тем же `id`, что у встроенного** — побеждает
      пользовательский, `upgrade` его не перезаписывает
- [ ] passive inspect на repository с опасным package script: команда обнаружена,
      но не исполнена; active probe требует отдельный plan id
- [ ] symlink/path traversal за пределы target и secret-файлы
- [ ] dirty worktree
- [ ] detached HEAD
- [ ] target-ветка ушла вперёд во время прогона
- [ ] merge conflict на интеграции
- [ ] crash в середине роли → resume
- [ ] двойной `start` (writer lock)
- [ ] rollback и `uninstall` после ручного drift
- [ ] `shared-repo`: `git status` и tracked tree до и после установки совпадают
- [ ] **апгрейд с версии N-1**: managed-файлы синхронизированы, конфиг и ответы
      init сохранены, миграции применены
- [ ] **апгрейд с локально правленным ролевым файлом**: файл не перезаписан,
      создан `.new` сидекар
- [ ] **апгрейд при активном run**: отказ с внятной инструкцией, состояние цело
- [ ] **`reinit` после изменения проекта** (добавили тесты / обновили фреймворк):
      capability manifest пересчитан, дельта показана
- [ ] **`reinit --clean`**: перечислены потери до выполнения, после — установка целая
- [ ] **батч `upgrade --all-root`** на трёх fixture-проектах разных версий:
      fail-fast оставляет текущий rolled_back, следующие untouched; отдельный
      прогон проверяет `--continue-on-error`
- [ ] **`rollback`** возвращает предыдущую версию рабочей

### B. Ручная приёмка — один раз на затрагивающем slice

Настоящие агенты в настоящих клиентах. Повторяется только при изменении
соответствующего adapter, а не на каждом slice. Результат каждого прогона
записывается с датой и версиями хостов.

- [ ] одна и та же profile-2 задача через Codex, Claude Code и Cursor; по каждой
      capability доказан native / fallback / unsupported путь до мутации
      — *повтор при изменении любого role/handoff adapter*
- [ ] `shared-repo`: новая сессия каждого хоста и worker в свежем worktree
      **находят** local runtime — *повтор при изменении bootstrap*
- [ ] изолированный probe на живом Symfony и живом WordPress: side effects
      совпали с заявленными в plan, teardown отработал
      — *повтор при изменении probe или стекового adapter*
- [ ] dogfooding: реальная задача от спецификации до приёмки
- [ ] замер «Джон Генри» на эталонной задаче

> **Требование к архитектуре, которое отсюда следует.** Группа A существует
> только если роль можно подменить: детерминированный **stub role executor**,
> который отдаёт заранее заданный результат и коммит вместо вызова живого
> агента. Без такого шва вся логика Git-протокола, состояния, resume, drift и
> интеграции проверяется исключительно живыми прогонами — то есть медленно,
> дорого и недетерминированно, а значит на практике не проверяется вовсе.
>
> Шов закладывается в **slice 2A** вместе с run state, а не достраивается потом.

> Известные дефекты для проверки полосы подсаживаются **только в disposable
> fixture или отдельную временную ветку**, никогда в реальный рабочий проект.

---

## Мутационная проверка самой полосы

- [ ] В disposable fixture подсажены N известных дефектов
- [ ] Посчитаны survivors, каждый разобран
- [ ] Доказано, что реальный target при этом не менялся

**Полоса, которая не ловит подсаженные дефекты, — это иллюзия контроля.**
Формулировка Мартина: ноль выживших — не вердикт о качестве, а условие выхода
из цикла.

---

## Замер «Джон Генри»

Свой замер обязателен — но без фиксированной задачи он нефальсифицируем и даст
ровно ту цифру, которую хочется получить.

- [ ] **Названа одна маленькая повторяемая эталонная задача.** Кандидат:
      «добавить поле + валидацию + тест в Symfony CRUD». Записать её как
      спецификацию до первого прогона.
- [ ] Прогнать её тремя способами: руками · 2 роли · 4 роли
- [ ] По каждому замерить: общее время, **человеческое внимание отдельно**,
      токены, что поймала полоса
- [ ] Записать оговорки честно: одна задача, один судья — как это сделал Мартин

## Промпт запуска (для одного slice)

```text
Делаем slice N из tools/ai-pipeline/SPEC.md.
Прочитай README плана, SPEC, DECISIONS и owning AC IDs. Сначала напиши
implementation plan в docs/superpowers/plans/YYYY-MM-DD-ai-pipeline-slice-N.md:
точные пути файлов и интерфейсы, порядок TDD-задач, конкретные red/green команды,
fixture cases, verification и короткие commit messages по политике этого
репозитория. Не оставляй placeholders. Покажи мне план и остановись.

После моего одобрения реализуй по TDD.

Готово, когда:
- slice полезен сам по себе, без следующих;
- пройдена применимая часть fixture-матрицы из
  docs/proposals/ai-pipeline/07-phase5-implementation.md;
- доказаны перечисленные в карте slice пункты 08-acceptance-criteria.md;
- в MIGRATIONS.md инструмента добавлена запись этого slice.

Ограничения:
- Известные дефекты подсаживай только в disposable fixture, никогда в реальный
  проект.
- Сохраняй переносимый core-контракт; Codex, Claude Code и Cursor не своди к
  фиктивной общей capability.
- Следующий slice не начинай.
```
