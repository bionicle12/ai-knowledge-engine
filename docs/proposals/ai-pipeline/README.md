## Как этим пользоваться

Одна фаза — один запуск в отдельной сессии, с приёмкой между ними. В каждом файле
фазы есть готовый промпт запуска и чекбоксы; закрываем их по мере выполнения и
двигаем статус в таблице выше.

**Общие правила для исследовательских фаз 0–4** — вставлять в начало каждого
промпта. Для фазы 5 действуют утверждённый implementation plan и commit policy
целевого репозитория:

```text
Прочитай docs/proposals/ai-pipeline/README.md и 00-context.md, затем файл своей фазы.
Решения из DECISIONS.md согласованы — по ним не переспрашивай.

Правила исследовательской фазы:
- Раздел «Выжимка из статьи» в 00-context.md заморожен на 2026-08-23. Если фаза 0
  уже прошла, источник правды по внешним фактам — notes/00-fresh-context.md.
- Не забегай вперёд: артефакты следующих фаз не производи, даже если кажется, что
  готов. Список того, что НЕ делать, есть в каждом файле фазы.
- Всё, что ты не смог проверить, помечай `unknown` — не угадывай.
- В конце перечисли допущения и всё, что оставил недоделанным.
- Закрой чекбоксы в файле своей фазы и обнови статус в README.
- Коммит не делай.
```

```
0 (свежий контекст)

      ├──► 1b-I  (обнаружение и адаптеры)     ─┤  три параллельных черновика
      └──► 1b-II (жизненный цикл, обновление) ─┤
                                               │
                                  2 (сверка трёх → слепые зоны → интервью)
                                       │                         └─► DECISIONS.md
                                       │
                                  3 (четыре варианта)  ← здесь появляются
                                       │                 state machine, walkthrough
                                       │                 и истории drift/resume
                                  4 (SPEC + slices)
                                       │
                                  5 (реализация по slices)
```

**Жёсткие правила порядка:**

- **Фаза 0 — первой всегда.** Знания модели отстают: `swarm-forge` создан
  17.04.2026, статья от 07.08.2026, API хостов меняется ежемесячно.
- **1a, 1b-I и 1b-II можно готовить параллельно, но нельзя считать
  согласованными.** Фаза 2 сначала устраняет пересечения и противоречия между
  ними, затем начинает интервью. До этой сверки ни один из трёх анализов не
  является общей SPEC.
- **Автомат состояний, walkthrough и Git decision tables — не раньше фазы 3.**
  Они зависят от выбранной архитектуры: для host-native family, portable runner
  и CI-oriented варианта они разные. Написать их в фазе 1 — значит выбрать
  архитектуру молча, а потом подгонять под неё «четыре варианта».
- **Фазу 3 не пропускать.** Именно она вытаскивает требования, которые иначе
  всплывут в середине реализации. Она же — **точка выхода**: там появляется
  оценка трудоёмкости, и «не строим» или «строим только 1A–1B» — законные
  исходы, а не поражение.

## Что делает этот инструмент, в двух абзацах

Из этого репозитория анализирует **целевой рабочий или pet-проект**, предлагает
подходящую конфигурацию конвейера ИИ-агентов, а после подтверждения разворачивает
её в проект. Цель — не только скопировать роли, но и оставить проект в состоянии,
в котором новая сессия Codex / Claude Code / Cursor понимает: когда запускать
конвейер, как продолжить незавершённый прогон и как безопасно вернуть его
результат в актуальную feature-ветку.

Первый фокус — веб-проекты, новые и существующие, включая Symfony и WordPress и
смешанные JS/TS + PHP-репозитории. Фреймворки не зашиваются в оркестратор:
стековые адаптеры обнаруживают команды проекта, generic-режим закрывает
неизвестный и legacy-стек. Оркестратор состоит из переносимого ядра и трёх
равноправных capability-checked adapters: Codex, Claude Code и Cursor.

Универсальность — не фиктивный общий знаменатель. Ядро одинаково отвечает за
plans, state, budgets, Git preconditions, handoff и integration candidate;
host-adapter отвечает за обнаружение инструкций, запуск ролей и доступные
нативные возможности. Если конкретный host не умеет операцию безопасно, adapter
сообщает `unsupported` **до любой мутации** и предлагает внешний portable fallback.

**Инструмент обязан быть обновляемым.** Он будет дорабатываться на живых задачах,
исходник правится здесь, и исправление должно доезжать до всех проектов, где
конвейер уже стоит. Отсюда две независимые команды: `upgrade` (изменилась тулза)
и `reinit` (изменился сам проект), install manifest с первой же версии и реестр
миграций. Подробности — в [1b.11](03b-phase1b2-lifecycle.md).
