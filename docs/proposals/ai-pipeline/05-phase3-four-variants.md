# Фаза 3 — четыре непохожих варианта

**Статус:** ☐ не начата
**Выход:** `tools/ai-pipeline/VARIANTS.md` + `tools/ai-pipeline/BRIEF.md`
**Зависимости:** фаза 2 (решения записаны в `DECISIONS.md`).

**Эту фазу не пропускать.** Именно она вытаскивает требования, которые иначе
всплывут в середине реализации. Каждый вариант обязан сохранять переносимое ядро
и одинаково честно разбирать Codex, Claude Code и Cursor.

---

## Зачем

Приём 3 Шихипара: когда не можешь описать словами, что нужно, — не описывай,
**реагируй**. Цель — не выбрать победителя из четырёх, а получить собственные
реакции, из которых соберётся бриф.

Четыре, не десять: «на десятой картинке глаз замыливается, и ты начинаешь
выбирать нормальное, а не узнавать своё».

**Здесь же впервые появляются автомат состояний, walkthrough и истории drift/
resume.** Они умышленно не писались в фазе 1: для native family, portable runner
и CI-oriented варианта они разные, и написать их заранее — значит выбрать
архитектуру молча, а потом подгонять под неё «варианты».

---

## Варианты

Кардинально разные направления, а не оттенки одного:

| | Направление |
|---|---|
| **А** | **Host-native family** — общее core, но Codex/Claude Code/Cursor запускают роли своими проверенными primitives; Git-изоляция только где нужна |
| **Б** | **Portable external runner** — одинаковый внешний lifecycle и Git/worktree-протокол, host используется как вызываемый CLI/worker |
| **В** | **Single-agent + deterministic gauntlet** — один агент, роли как последовательные контракты, полоса локально/в CI |
| **Г** | **Hybrid** — нативные workers там, где capability подтверждён, portable runner и детерминированная локальная/CI-полоса как fallback |

## Что обязан содержать каждый вариант

Одинаковый набор, чтобы варианты были сравнимы:

- [ ] **Автомат состояний run** — свой для этого варианта. Минимальный каркас, от
      которого отталкиваться:
      ```text
      proposed → awaiting-spec-approval → running:<role> → gauntlet
               → awaiting-acceptance → integration-ready → integrating → completed
               ↘ paused / blocked / awaiting-conflict-resolution / aborted
      ```
- [ ] **Walkthrough 1 — greenfield:** от команды в AI Knowledge Engine до
      результата в feature-ветке.
- [ ] **Walkthrough 2 — существующий Symfony или WordPress-проект:** то же самое,
      но с уже имеющимися тестами, CI и `AGENTS.md`.
- [ ] **История inspect/init:** что читается, что пишется, что показывается.
- [ ] **История probe:** пассивный inspect уже завершён; какие активные команды
      попадают в plan, где выполняются и как доказывается cleanup.
- [ ] **История resume:** новая сессия через два дня, что восстанавливается и откуда.
- [ ] **История drift:** target-ветка ушла вперёд, пока шёл прогон.
- [ ] **История конфликта:** merge conflict на интеграции.
- [ ] **История доработки:** человек не принял результат — куда возвращается
      работа, что происходит со спецификацией и с уже сделанными handoff-коммитами,
      как выглядит вторая итерация. Это самый частый реальный исход, и варианты
      расходятся по нему сильно.
- [ ] **История апгрейда:** тулза поправлена, в проекте стоит прошлая версия —
      что синхронизируется, что мигрируется, что остаётся локальным. Отдельно —
      как это выглядит сразу для десяти проектов.
- [ ] **История reinit:** проект изменился (добавили тесты, обновили фреймворк) —
      как пересчитывается capability manifest и что показывается человеку.
- [ ] **Что остаётся в проекте** — точный список файлов.
- [ ] **Матрица трёх хостов** — для Codex, Claude Code и Cursor по каждой
      возможности указано `native / portable fallback / unsupported`; никакой
      host не описан как необязательный второй класс.
- [ ] **Shared-repo bootstrap** — новая сессия и worker в новом worktree находят
      runtime без tracked-изменений; если это невозможно, вариант честно
      показывает `unsupported` и следующий fallback.
- [ ] **Что происходит без сети** и без установленного tmux.
- [ ] **Где живёт `serve`** — кто поднимает приложение для QA-роли.
- [ ] **Цена:** сколько ролей реально параллелятся, сколько это стоит на типовой
      задаче, где узкое место.
- [ ] **Где этот вариант ломается** — честный раздел, по одному на вариант.

## Как работать с результатом

Не выбирать вариант, а **проговаривать реакции**, даже сырые: «вот это лишнее»,
«вот это мне нравится, но не для рабочего репозитория», «здесь я не понимаю, кто
поднимает базу». Каждая такая реплика — формулировка требования, которой раньше
не было.

Из реакций собирается финальный бриф в `tools/ai-pipeline/BRIEF.md`. Он может не
совпадать ни с одним из четырёх вариантов — это нормальный и ожидаемый исход.

- [ ] Реакции проговорены по каждому варианту
- [ ] Финальный бриф собран из реакций, а не выбран из списка
- [ ] Выбор архитектуры записан в `DECISIONS.md` с причиной

## Оценка трудоёмкости и точка выхода

Фаза 3 — последний момент, когда цена уже видна, а реализация ещё не начата.
Здесь принимается решение **строить или не строить**, и без двух артефактов
ниже оно будет принято вслепую.

**Оценка трудоёмкости по выбранному варианту.** Не «сколько строк», а вилка по
группам слайсов: ядро (1A–2C) · обновляемость (3A–3B) · стековые адаптеры
(4A–4D) · хвост (5A–5B). Отдельно — что из этого масштабируется с числом стеков
и хостов, а что делается один раз. Раньше фазы 3 такая оценка была бы выдуманной:
цена сильно зависит от того, победит host-native family, portable runner или
CI-вариант.

**Off-ramp — легитимные исходы, кроме «строим всё».** План не должен
предполагать, что инструмент обязательно будет построен. Честные варианты:

| Исход | Когда разумен |
|---|---|
| строим полный объём до 5B | оценка приемлема, задач много, стеки разнообразны |
| строим только 1A–1B | нужен честный отчёт по проекту и managed-блок, конвейер пока не нужен |
| строим до 2C и останавливаемся | двухролевой цикл на одном хосте закрывает потребность |
| берём `swarm-forge` как есть | своё не окупается против готового |
| не строим ничего | хватает CI и одного агента с хорошей спецификацией |

Это тот же **профиль 0**, применённый к самому инструменту: прежде чем
автоматизировать, спроси, поручил бы ты это живому сотруднику. План требует
такой фильтр от конвейера — логично применить его и к себе.

- [ ] Дана вилка трудоёмкости по группам слайсов для выбранного варианта
- [ ] Сказано, что масштабируется с числом стеков и хостов, а что делается раз
- [ ] Явно рассмотрены все исходы из таблицы, включая «не строим»
- [ ] Решение об объёме записано в `DECISIONS.md` с причиной

## Чего в этой фазе НЕ делать

- Не писать SPEC — фаза 4.
- Не писать код и шаблоны.
- Не сводить четыре варианта к трём «потому что один явно хуже»: слабый вариант
  тоже даёт реакцию.
