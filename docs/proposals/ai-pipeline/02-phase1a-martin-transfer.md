# Фаза 1a — перенос системы Мартина

**Статус:** ☐ не начата
**Выход:** `tools/ai-pipeline/ANALYSIS-transfer.md`
**Зависимости:** фаза 0. Выполняется параллельно с 1b-I и 1b-II как
самостоятельный черновик; расхождения разрешаются reconciliation gate в фазе 2.

---

## Зачем

Ответить, что из системы Мартина мы переносим, во что превращаем и от чего
отказываемся. Всё в этой фазе — **архитектурно-независимо**: инварианты общего
ядра не должны зависеть от того, какой native/portable механизм выберет фаза 3.

## Вопросы

### 1a.1. Механика запуска: повторять tmux + worktree или взять родное?

> Поддерживаемые хосты — **Codex, Claude Code и Cursor**. У них общее переносимое
> ядро, но разные adapters. Нативные возможности одного хоста нельзя считать
> доступными в другом и нельзя скрывать отсутствие через фиктивный общий API.

Мартин строил рой поверх внешних CLI, поэтому worktree и tmux были клеем.
Разобрать по отдельности, что ложится на родные примитивы, а что придётся клеить:

- **Codex** — параллельные роли, изоляция, стоп-условия, ролевые конфиги,
  `AGENTS.md` / `AGENTS.override.md`. **Не считать вложенный `AGENTS.md` готовым
  механизмом роли:** если worktree открыт в корне проекта, инструкция из каталога
  `.ai-pipeline/roles/<role>/` сама к коду проекта не применяется. Нужен
  проверяемый host adapter, который передаёт роль в контекст агента и не меняет
  публичные файлы проекта на время прогона.
- **Claude Code** — субагенты, Agent Teams, `/goal`, worktree-изоляция, hooks и
  local-only project instructions.
- **Cursor** — rules, background agents, checkout/worktree model, lifecycle и
  local-only project instructions.
- **Portable fallback** — внешний runner + Git/worktree без привязки к native
  orchestration, если хост честно сообщает `unsupported`.

**Развилка, от которой зависит вся архитектура.** В этой фазе — только
собрать evidence и разложить варианты; **выбор делается в фазе 3**.

Важно: механизм запуска ролей и Git-протокол — разные решения. Даже если Codex
умеет нативных субагентов, инструмент всё равно обязан детерминированно хранить
базовый commit, цепочку handoff и способ интеграции результата.

- [ ] Собран evidence по каждому хосту, с версиями из фазы 0
- [ ] Для всех трёх заполнена одна таблица `native / fallback / unsupported`
- [ ] Разложены варианты «родное / portable runner / гибрид» с последствиями
- [ ] Явно записано: выбор отложен до фазы 3

### 1a.2. Чем заменить CRAP и мутационное тестирование вне мира Мартина

Таблица «барьер → инструмент → порог». Актуальность проверять по фазе 0, а не по
памяти. Колонки — **не список поддерживаемых стеков**, а проверка гипотезы, что
абстракция барьеров переживает переход между очень разными тулчейнами.

| Барьер | PHP | JS/TS (Node) | Bun | Rust | Python |
|---|---|---|---|---|---|
| юнит-тесты + покрытие | pest / phpunit | vitest / jest | `bun test` | `cargo test` + llvm-cov / tarpaulin | pytest-cov |
| мутационное тестирование | Infection | Stryker | ? проверить | cargo-mutants | mutmut / cosmic-ray |
| сложность / чистота | phpstan, phpmd | eslint complexity, ts-prune, biome | oxlint / biome | clippy, `cargo udeps` | ruff, radon |
| приёмка снаружи | зависит от поверхности, см. ниже | | | | |
| внешняя поверхность | HTTP | HTTP / CLI | HTTP / CLI | CLI-бинарник / библиотека / HTTP | CLI / библиотека |
| CRAP-аналог | считается из сложности + покрытия — вероятно, свой скрипт поверх любых двух метрик |

Знаки вопроса оставлять честными: если для стека нет зрелого мутационного
инструмента, capability помечается `missing`, а не подменяется суррогатом.

**Отдельный барьер `contract` — между `unit` и `e2e`.** В репозитории, где два
пакета общаются через API, самый дорогой барьер оказывается единственным, кто
ловит их расхождение. Живой пример — `../iladno`: Symfony отдаёт JSON, React-
админка его потребляет. Меняешь форму ответа — phpunit зелёный, vitest зелёный,
phpstan и deptrac зелёные, админка сломана. Ловит только Playwright, которому
нужен поднятый Docker-стек с traefik и TLS.

Барьер такой цены будут пропускать, а штамп верификации при этом скажет
`verified: unit+static` — формально правда, практически ложь ровно того сорта,
от которого мы защищаемся.

`contract` — дешёвая детерминированная проверка совместимости границы:
экспорт OpenAPI/JSON-схемы и сверка с типами потребителя, снапшот форм ответов,
генерация клиентских типов и проверка компиляции. Ловит большинство
кросс-пакетных поломок без поднятия стека.

- [ ] Разобрано, чем закрывается `contract` в каждом стеке из таблицы
- [ ] Сказано, что делать, когда контрактной проверки нет: штамп обязан назвать
      непроверенную границу явно, например
      `verified: unit+static; контракт API↔admin не проверен`

**Обобщить «поднять приложение» до «внешней поверхности».** У Мартина роль QA
проверяет только снаружи, как пользователь. Для веб-приложения «снаружи» — это
запущенный сервер и Playwright. Для CLI-бинарника на Rust — собранный бинарь и
проверка его stdin/stdout/exit code. Для библиотеки — только публичный API, и
никакого HTTP вообще. Для TUI — эмулятор терминала или ничего.

Если оставить `serve` в web-only формулировке, у Rust-крейта и Node-CLI внешней
приёмки не будет **вовсе**, а роль QA у них выродится в «прогнали юнит-тесты» —
то есть исчезнет главный инвариант системы Мартина.

Поэтому в анализе нужна не строка «поднять приложение», а **классификация
внешних поверхностей** с ответом на четыре вопроса по каждой: как её поднять,
как к ней обратиться, как понять, что она готова, как гарантированно погасить.
Кандидаты: `http` · `cli` · `library` · `tui` · `none`.

Для `none` (например, библиотека без публичных примеров) честный ответ —
«внешняя приёмка недоступна, уровень верификации ниже», а не имитация.

- [ ] Таблица заполнена и проверена на актуальность; отсутствующие инструменты
      помечены `missing`, а не заменены суррогатом
- [ ] Для каждого барьера указано, чем он проверяем и какой порог осмыслен
- [ ] Составлена классификация внешних поверхностей с четырьмя ответами по каждой
- [ ] Явно сказано, что делает роль QA при поверхности `none`
- [ ] Проверено, что абстракция барьеров не течёт: один и тот же контракт
      описывает `cargo test` и `wp-env`, или зафиксировано, где именно течёт

### 1a.3. Что здесь «исполняемая спецификация»

Gherkin у Мартина в центре, потому что это единственный артефакт, который человек
читает и подписывает, и он **не может протухнуть** — разойдётся с кодом, конвейер
упадёт. Кандидаты для веба: Gherkin + Playwright-шаги, Playwright-сценарии с
человекочитаемыми названиями, markdown-чеклист приёмки, привязанный к e2e.

Помнить критику: формат уже дважды хоронили за большие деньги. Нужен честный
разбор, а не автоматический перенос.

- [ ] Три и более кандидата разобраны, с плюсами и минусами
- [ ] Явно сказано, что делать, когда e2e в проекте нет вообще
- [ ] Критика Gherkin разобрана применительно к нашему случаю

### 1a.4. Конституция и ролевые инструкции, которые не разбухнут

У Мартина конституция — три коротких файла, и запретов в них больше, чем
разрешений. Это уже правильная форма: запрет — настоящий инвариант, а не
правило-90%.

Требования: каждая роль описана один раз; ограничения ролей помечены как
инварианты; всё остальное — критерии, а не списки шагов.

**Гниение инструкций — не гипотеза, а наблюдённый факт** (статья 08-14, «Ловушка
2»). У инструмента будет установленный runtime в N проектах, и `upgrade`
синхронизирует файлы, но не чинит накопленное. Не изобретать своё: рядом уже
спроектирован паттерн — `instructions_review` (под какое поколение моделей
писано), `MIGRATIONS.md` (что доустановить уже установленному runtime) и `!heal`
(догоняющая починка). Разобрать, что из этого переносится.

- [ ] Форма конституции и ролевого файла предложена, с бюджетом размера
- [ ] Механизм ревизии описан как механизм, а не пожелание
- [ ] Решено, что берём из паттерна `MIGRATIONS.md` / `instructions_review` / `!heal`

### 1a.5. Лестница размеров, профиль 0 и точки человека

Инструмент разворачивает **выбираемый** размер, а не только полный: Мартин прямо
говорит, что полный конвейер на каждую задачу — перебор, и признаёт, что «часто
хватает юнит-тестов и CRAP».

**Профиль 0 — «конвейер не нужен» — полноправный исход рекомендации.** Сейчас в
плане есть только bypass по типу файла (typo/docs-only), а это фильтр по форме,
не по существу. Нужен содержательный фильтр из статьи о циклах: *что именно
система узнает после очередной попытки и как это изменит следующую?* Плюс фильтр
Черни: *а поручил бы ты это живому сотруднику?* Без такого гейта инструмент будет
запускаться на всём подряд просто потому, что установлен, и жечь лимиты там, где
хватило бы одного промпта.

Две обязательные точки человека в нормальном feature-cycle:

1. одобрение исполняемой спецификации перед кодированием;
2. ручная приёмка перед интеграцией.

Safety stops (см. 1b) считаются отдельно и не подавляются ради красивой метрики
«всего две точки».

**Публикуемый артефакт повышает профиль.** В `playflowb2b` каталог `sdk/` — это
JS, PHP и Python-клиенты, которые уходят покупателям, плюс `integrations/` для
Shopify и WordPress. Ошибка внутри бэкенда чинится следующим коммитом; ошибка в
опубликованном SDK уже стоит у клиентов. Признак «изменение затрагивает
публикуемый артефакт» должен поднимать профиль и делать приёмку обязательной,
даже если правка выглядит мелкой.

- [ ] Описаны профили 0 / 2 / 4 / 6: состав, порядок ролей, когда какой
- [ ] Сформулирован содержательный критерий «конвейер не нужен»
- [ ] Две точки человека отделены от safety stops
- [ ] Признак «публикуемый артефакт» включён в правила эскалации профиля

### 1a.6. Паспорт цикла и бюджет

Заполнить семь полей из статьи о loops явно: **цель · триггер · одна итерация ·
проверка · память · тормоза · человек**.

Особое внимание тормозам: честный ноль, застой (две итерации без прогресса),
исчерпанный бюджет. У Мартина мутационное упрочнение съело 32 минуты из 62 —
половину машинного времени. Это отдельная строка расходов.

**Оценка стоимости до старта.** Между «оценкой при установке» и «бюджетом как
стоп-условием» дыра: перед подписью под спецификацией человек не видит, во что
обойдётся **эта** задача. На реальном репозитории с шестью ролями одна фича может
выжечь дневной лимит. Нужна вилка «время / токены» по выбранному профилю до
одобрения спеки, и потраченное против бюджета в `status`.

- [ ] Паспорт цикла заполнен по всем семи полям
- [ ] Тормоза перечислены с условиями срабатывания
- [ ] Описано, как считается предварительная оценка и как показывается расход
