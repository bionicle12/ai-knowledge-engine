## 1. Что мы хотим получить

Инструмент, который из этого репозитория анализирует **целевой рабочий или
pet-проект**, предлагает подходящую конфигурацию конвейера ИИ-агентов, а после
подтверждения разворачивает её в проект. Цель — не только скопировать роли, но и
оставить проект в состоянии, в котором новая сессия Codex / Claude Code / Cursor
понимает: когда запускать конвейер, как продолжить незавершённый прогон и как
безопасно вернуть его результат в актуальную feature-ветку пользователя.

Целевые проекты — **любые, у которых есть или могут появиться исполняемые
проверки**: PHP (Symfony, WordPress), JS/TS (Node, Bun, React), Rust, Python,
смешанные репозитории и монорепы. Список не закрыт и не должен быть закрыт.

**Фреймворки не зашиваются в оркестратор — это не пожелание, а требование к
архитектуре.** Стековый адаптер — данные, а не код: декларативный манифест,
который описывает, как обнаружить стек, какими командами закрывается каждая
capability и что в этом стеке значит «проверить снаружи». Встроенные адаптеры
поставляются **в том же формате**, что и написанные пользователем, иначе точка
расширения сгнивает первой же.

Референсные адаптеры выбираются не по списку любимых фреймворков, а так, чтобы
покрыть **оси различий**, на которых ломаются наивные решения:

| Ось | Полюса | Кто ломается |
|---|---|---|
| исполнение | интерпретируемый ↔ компилируемый | шаги build и время прогона |
| внешняя поверхность | HTTP ↔ CLI-бинарник ↔ библиотека ↔ TUI ↔ нет | вся роль QA «снаружи» |
| внешние сервисы | нужна БД/Docker ↔ ничего не нужно | изоляция probe, `serve`, fixtures |
| форма репозитория | один пакет ↔ workspace/монорепа | маршрутизация профиля и барьеров |
| зрелость проверок | полный набор ↔ только компилятор ↔ ничего | достижимый уровень верификации |

Symfony, WordPress, Rust-крейт, Bun/Node-сервис и React-приложение попадают в
разные клетки этой таблицы — поэтому они и берутся в референсы. Проект на стеке,
которого в поставке нет, обязан заводиться **манифестом, а не патчем
оркестратора**.

Сам конвейер строится с «полосой препятствий» — по образцу `swarm-forge` Роберта
Мартина, но адаптированной под наш стек и переносимой между Codex, Claude Code и
Cursor.

Модель поставки — та же, что у AI Knowledge Engine: **deployment kit**, но с
явным разделением двух частей:

1. **Control plane в этом репозитории:** пассивный `inspect`, активный
   двухфазный `probe`, рекомендация, exact plan/apply, обновление и удаление
   установки в целевом проекте.
2. **Project-local runtime:** короткие инструкции, конфиг, адаптеры полосы и
   восстанавливаемое состояние прогонов, нужные будущим агентным сессиям уже без
   повторного чтения этого репозитория.

Внутри control plane — **одно host-agnostic ядро и три first-class adapters**.
Ядро владеет schemas, state, планами, бюджетом и Git safety. Adapter владеет
обнаружением инструкций, передачей worker-контекста и запуском ролей в конкретном
host. Нельзя выдавать эмуляцию за поддержку: отсутствие безопасной возможности
возвращается как `unsupported` до записи файлов или запуска процессов.

> **Многохостовость здесь настоящая, а не «на всякий случай».** Владелец работает
> с Codex, Claude Code и Cursor примерно поровну, на разных проектах разные
> инструменты, и Codex здесь используется даже чуть реже остальных.
>
> Это отличается от соседнего плана `docs/proposals/2026-08-23-boosty-kb-improvements.md`,
> где база знаний сознательно спроектирована **Codex-first** (~90% работы) —
> та цифра относится только к базе и **не переносится сюда**. Не выводить из
> соседнего документа приоритет одного хоста для конвейера.

`finalize` из Knowledge Engine нельзя переносить буквально: рабочая часть
конвейера должна остаться в проекте. Для AI pipeline нужно отдельно определить
`init/apply`, `upgrade`, `doctor`, `uninstall/rollback` и очистку только временных
артефактов.

Место в репозитории: `tools/ai-pipeline/` (рядом с `tools/ai-skills-fixer/`).
Отдельный инструмент, **не** часть базы знаний.

### 1.1. Целевой пользовательский поток

Инициализация проекта:

```text
«Используй AI pipeline для /work/acme-shop»
  → read-only inspect
  → вопросы только о том, чего нет в репозитории
  → рекомендация профиля и точный change plan
  → явное одобрение
  → установка project-local runtime + подходящий host bootstrap
  → doctor + отчёт, как запустить первую задачу
```

Обычная разработка уже внутри инициализированного проекта:

```text
«Сделай feature X»
  → host bootstrap: найти незавершённый run или создать новый
  → оценить, нужен ли конвейер вообще (профиль 0 — валидный ответ)
  → зафиксировать текущую integration-ветку и её HEAD
  → подобрать профиль для конкретной задачи
  → провести эстафету ролей в изолированных execution contexts
  → собрать проверенный integration candidate
  → показать план слияния и расхождение с актуальной веткой
  → после проверки безопасно интегрировать или остановиться на конфликте
```

Инициализация рекомендует **профиль по умолчанию**, а не навсегда фиксирует число
агентов. Размер и состав конвейера повторно оцениваются для каждой задачи:
маленькая правка может идти через 2 роли, рискованная миграция — через 4 или 6,
а часть задач конвейера не заслуживает вовсе. Пользователь всегда видит причину
рекомендации и может её переопределить.

## 3. Выжимка из статьи ❄️ заморожена на 2026-08-23

> Нужна, чтобы сессия понимала предмет до чтения первоисточника. **Не считать
> актуальной после фазы 0** — сверяться с `notes/00-fresh-context.md`.

**Тезис.** Мартин не читает код, написанный агентами. Вместо чтения — «полоса
препятствий» (run the gauntlet): набор автоматических проверок, сквозь которые
прогоняется всё, что произвёл агент. Формула: *«Агенту нельзя сказать "пиши чисто".
Ты должен измерять чистоту того, что он производит, и заставлять исправлять
провалы»*. Подпись: *«I am the engineer because I am accountable»*.

**Устройство роя.** Каждый агент — в своей копии проекта (git worktree) и своём
окне терминала (tmux); работа передаётся эстафетой. Под капотом — codex / claude /
grok build на выбор.

**Роли, по убыванию размера:**

| Размер | Роли |
|---|---|
| полный (6) | specifier · coder · cleaner · architect · hardener · QA |
| ужатый (4) | specifier · coder · refactorer · architect |
| минимум (2) | coder · cleaner |

**Инвариант при любом размере: агент, писавший код, сам его не проверяет.**

**Запретов больше, чем обязанностей** — главная конструктивная идея:

- кодеру запрещено запускать проверки чистоты и мутационные тесты;
- QA запрещено заглядывать внутрь проекта — только снаружи, как пользователь;
- разговаривать с человеком может только specifier;
- «конституция» — три коротких файла, общих для всего роя;
- свободная переписка между агентами запрещена: ровно два типа сообщений —
  передача работы и служебная заметка (заметка — только по явному разрешению);
- при любой неоднозначности — остановиться и спросить;
- работать только в своей копии, в чужие ветки не заглядывать;
- каждый коммит подписывать своей ролью.

> Последнее правило — описание `swarm-forge`, **не требование нашего инструмента**.
> В рабочих репозиториях публичная история не должна содержать `AI`, `Codex`,
> `Claude`, роль агента или `Co-authored-by` без явного разрешения пользователя.
> Техническая трассировка ролей хранится в состоянии прогона, а сообщения коммитов
> подчиняются политике самого целевого проекта.

**Человек в контуре ровно дважды:** подпись под Gherkin-спецификациями перед
передачей кодеру, и приёмка руками по QA-процедурам. Выход одной задачи склеен со
входом следующей.

**Барьеры полосы:** юнит-тесты → Gherkin (исполняемая спецификация — единственный
артефакт, который читает и утверждает человек) → QA-процедуры прозой (только
снаружи) → метрики чистоты (CRAP = Change Risk Anti-Pattern, порог ≤6, в соседнем
проекте ≤8) → мутационное тестирование («убить выживших»; 2773 мутации / 2773
killed / 0 survivors — это **условие выхода из цикла**, а не вердикт о качестве).

**Замер «Джон Генри»** (Hunt the Wumpus): пять живых программистов — в среднем
146,6 мин; рой из 4 ролей — 62 мин, из них 32 мин на мутационное упрочнение.
Человеческого внимания — 15 мин против 146. Покрытие 97%, CRAP ≤5,0.
Оговорки: одна маленькая задача, судья — сам автор роя.

**Критика, которую нельзя игнорировать:** полосу построили сами агенты;
Грэди Буч — метрики дают уверенность в функциональности и ноль уверенности в
отсутствии уязвимостей, мёртвого кода и провалов по производительности;
Gherkin уже дважды хоронили за большие деньги (SmartBear, Tricentis);
метрики — «прокси с малым количеством информации». Сам Мартин называет свою
позицию **ставкой**, а не теоремой, и признаёт: «часто я просто использую
юнит-тесты и CRAP».

**Куда он движется дальше:** лидер + специализированные исполнители, жёсткий
конечный автомат вместо свободной эстафеты, симулятор отказов, прогоны
Монте-Карло. Направление — не «более умные агенты», а более жёсткие рамки.
*«Дисциплина масштабируется лучше интеллекта.»*

## 4. Явные ограничения этой работы

- Мартин сам называет свою систему **ставкой**. Мы строим один из вариантов, а не
  канон. В README инструмента это должно быть написано прямо.
- Замер «Джон Генри» — одна маленькая задача, судья — автор роя. Не цитировать его
  как доказательство эффективности.
- Метрики не ловят уязвимости, мёртвый код и провалы производительности (Буч).
  Либо добавляем отдельные барьеры под это, либо честно пишем, что не покрываем.
- Не строим сразу шесть ролей. Начинаем с двух — это уже полноценный рабочий цикл.
- Не обещаем одинаковую нативную оркестрацию во всех hosts. Codex, Claude Code и
  Cursor поддерживаются как равноправные adapters поверх одного контракта, но
  каждый может использовать свои нативные примитивы или portable fallback.
- Не устанавливаем тестовый стек, hooks, CI, зависимости и внешние сервисы молча.
  Для legacy-проекта полезным результатом может быть честный минимальный профиль
  и список prerequisites, а не «полный зелёный конвейер» за один init.
- Не делаем автоматически push, PR, force-update, stash/reset, глобальный
  `git config` или удаление пользовательских веток/worktree.
- Не храним полные prompt/transcript и исходный код в run state ради аудита;
  достаточно SHA, роли, команды, exit status и короткой структурированной причины.
- Поддерживаемые ОС первой версии выбираются в SPEC после проверки worktree и
  host API. Отсутствие tmux на платформе не должно ломать ни один host adapter:
  используется иной подтверждённый native path или portable fallback.
- **Конвейер, который не может честно проверить результат, не должен делать вид,
  что проверил.** Отсутствие тестов — это не повод понизить порог, это повод
  вернуть результат со штампом «не верифицировано».
