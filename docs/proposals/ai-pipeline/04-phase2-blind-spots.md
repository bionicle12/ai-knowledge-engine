# Фаза 2 — слепые зоны и интервью

**Статус:** ☐ не начата
**Выход:** `tools/ai-pipeline/notes/01-reconciliation.md` + записи в

**Зависимости:** фазы 1a, 1b-I и 1b-II все завершены.

---

## Зачем

Задача большая, и это ровно тот случай, для которого придуман приём Шихипара:
основная работа происходит **до** написания промпта — когда выясняешь, чего именно
ты не знаешь. Три из четырёх квадрантов незнания теряются, если проектировать
сразу.

Порядок обязателен: сначала модель сводит три параллельных черновика, затем
рассказывает тебе о слепых зонах и только потом спрашивает тебя (интервью).

---

## Задачи

- [ ] **Reconciliation gate.** Сопоставить `ANALYSIS-transfer.md`,
      `ANALYSIS-discovery.md` и `ANALYSIS-lifecycle.md`: выписать совпадения,
      противоречия, термины с разным смыслом и требования, которые один анализ
      считает инвариантом, а другой — выбором архитектуры. Разрешённое записать в
      `tools/ai-pipeline/notes/01-reconciliation.md`; всё, что требует владельца,
      перенести в интервью. До этого шага анализы не считаются единым контрактом.

  **Правило разрешения — механическое, не на глазок.** Применять по порядку:

  1. Противоречие зависит от архитектуры → **не разрешать**, унести в фазу 3.
     Выбор архитектуры не является разрешением противоречия.
  2. Спор о lifecycle, safety, состоянии, планах, Git-протоколе, приватности,
     обновляемости или формате артефактов → **побеждает 1b-II**.
  3. Спор об обнаружении, capability, стековых адаптерах, `surface` или штампе
     верификации → **побеждает 1b-I**.
  4. Спор о ролях, барьерах, точках человека, профилях или семантике конвейера →
     **побеждает 1a** (перенос Мартина).
  5. Один и тот же термин в разных смыслах → выбрать формулировку 1b-I для
     предметной области и 1b-II для процесса, зафиксировав словарь в
     `01-reconciliation.md`.
  6. Анализы опираются на непроверенный факт → пометить `unknown` и вернуть
     в фазу 0, а не решать голосованием.
  7. Всё остальное → в интервью, шаг 3.

  Правило нужно, чтобы gate был процедурой. Иначе каждое расхождение будет
  разрешаться суждением, и результат окажется невоспроизводимым.
- [ ] **Проход по слепым зонам.** Промпт: *«Архитектуру пока не предлагай.
      Сначала пройдись по моим слепым зонам: чего люди, которые впервые ставят
      конвейер ИИ-агентов на свой рабочий веб-проект, обычно даже не подозревают?
      Что стоит решить до того, как выбирать архитектуру?»* Часть пунктов
      отсеется как уже известное — важны те два-три, что станут открытием.
- [ ] **Интервью по одному-двум вопросам за раз, в порядке важности** — сначала
      то, что меняет архитектуру инструмента, детали в конце.
- [ ] Каждое решение записано в `DECISIONS.md` с датой и одной строкой «почему».

## Вопросы, которые обязаны быть закрыты первыми

Порядок — по убыванию влияния на архитектуру:

1. **Границы нативного и portable fallback** — какие host-specific ограничения
   Codex, Claude Code и Cursor допустимы, а где поведение обязано совпадать.
2. **Scope первой поставки** — какие ОС и стеки входят в первые fixtures; все три
   host adapter входят в продукт, но конкретная возможность может быть честно
   `unsupported` до её реализации.
2a. **Референсные стеки для slice 4B** — какие клетки таблицы осей из
   `00-context.md` закрываются первыми и какими проектами. Решение по стекам,
   не по фреймворкам: нужен компилируемый, нужен `surface: cli`, нужен «без БД».
   Symfony, Node/Bun, React и Rust — кандидаты, порядок за владельцем.
3. **Стратегия финальной интеграции** — squash, rebase/ff или сохранение коммитов.
4. **Допустимость новых зависимостей и хуков** в целевых проектах.
5. **Бюджет на задачу** — какая вилка времени и токенов приемлема, выше какой
   инструмент обязан остановиться и спросить.
6. **Изоляция активного probe** — допустимы ли контейнер, disposable worktree и
   сеть для рабочих проектов.
7. **Локальный bootstrap `shared-repo`** — какие user-level настройки/wrappers
   допустимы, чтобы не менять tracked tree.
8. **Политика public integration history сверх D-002** — squash/preserve,
   issue-id, signoff/GPG/DCO и язык сообщения.

Решения D-001–D-016 уже зафиксированы: их не переоткрывать без нового evidence.

## Чего в этой фазе НЕ делать

- Не проектировать варианты архитектуры — это фаза 3.
- Не писать SPEC.
- Не задавать вопросов, ответ на которые уже есть в любом из трёх анализов
  фазы 1. Сначала перечитать их.
