## D-001 · Поддерживаемые хосты и граница адаптера

**Дата:** 2026-08-23
**Решение:** переносимое ядро + равноправные capability-checked adapters для
Codex, Claude Code и Cursor.
**Почему:** владелец работает во всех трёх хостах примерно поровну — разные
проекты, разные инструменты, Codex здесь даже чуть реже остальных; проект не
должен привязывать состояние и Git safety к жизненному циклу одного клиента.
Соотношение «Codex ~90%» из плана базы знаний относится только к базе и на
конвейер не переносится.
**Следствия:** core-контракты state/plan/Git одинаковы; нативный запуск ролей
может отличаться. Adapter обязан вернуть `unsupported` до мутации или применить
явно выбранный portable fallback. Фиктивный общий знаменатель запрещён.

## D-002 · Атрибуция агентов в публичной истории

**Дата:** 2026-08-23
**Решение:** режим `work/private` по умолчанию — никаких AI/Codex/Claude/ролей/
`Co-authored-by` в публичных коммитах.
**Почему:** рабочие репозитории видят коллеги и заказчики.
**Следствия:** трассировка ролей живёт только в run manifest; internal handoff
commits сразу пишутся в публично допустимом стиле, на squash полагаться нельзя.

## D-003 · Минимальный стартовый профиль

**Дата:** 2026-08-23
**Решение:** начинаем с двух ролей, не с шести.
**Почему:** Мартин сам говорит, что полный конвейер на каждую задачу — перебор:
«часто хватает юнит-тестов и CRAP».
**Следствия:** первый end-to-end runtime реализует профиль из 2 ролей на Codex,
Claude Code и Cursor через native capability либо portable fallback; профили 4/6
идут последующими slices, но входят в полный объём этой работы.

## D-004 · Обновляемость установленных инсталляций

**Дата:** 2026-08-23
**Решение:** инструмент обязан быть upgradeable. Две независимые команды:
`upgrade` (изменилась тулза) и `reinit` (изменился проект). Снос-и-установка —
только явный `reinit --clean`, не поведение по умолчанию.
**Почему:** тулза будет дорабатываться по ходу эксплуатации, и правку исходника
нужно доводить до всех проектов, где конвейер уже стоит. При этом снос по
умолчанию выбрасывает заработанную конфигурацию, не атомарен и убивает локальные
правки под конкретный проект.
**Следствия:** install/release manifests обязательны в slice 1B; заводится `MIGRATIONS.md`
тулзы; нужны три состояния файла (`up_to_date` / `clean_overwrite` /
`customized`), `list-installs`, батч по всем инсталляциям, backup + `rollback`,
`state_schema_version` и отказ при активном run. Slices 3A/3B идут до установки
на реальные framework fixtures 4A–4C.

## D-005 · Пассивный анализ и активная проверка

**Дата:** 2026-08-23
**Решение:** `inspect` всегда пассивный и read-only; запуск команд, контейнеров,
серверов и фикстур выполняет отдельный двухфазный `probe`.
**Почему:** тесты, coverage, Composer/NPM scripts, Symfony, WordPress и Docker
могут писать кеши, менять БД и выполнять произвольный код проекта.
**Следствия:** capability различает `declared / runnable / verified / failed /
missing / unsupported`, хранит evidence и время проверки. `probe` требует plan id
и запускается в изоляции либо с явно показанными side effects.

## D-006 · Локальная установка в общем репозитории

**Дата:** 2026-08-23
**Решение:** профиль `shared-repo` не меняет отслеживаемые файлы, но новая сессия
каждого поддерживаемого хоста и каждый worker-worktree обязаны обнаружить runtime.
**Почему:** инфраструктура одного разработчика не должна навязываться коллегам,
но невидимый конвейер не выполняет основную задачу продукта.
**Следствия:** phase 3 выбирает host-specific local bootstrap. Приёмка проверяет
автодискавери во всех трёх хостах и неизменный `git status`.

## D-007 · Ошибка пакетного обновления

**Дата:** 2026-08-23
**Решение:** `upgrade --all-root` по умолчанию fail-fast; транзакция атомарна на
уровне одного проекта, уже завершённые проекты остаются валидны, текущий
откатывается, ещё не начатые не меняются.
**Почему:** одна и та же ошибка bundle или миграции с высокой вероятностью
повторится во всех проектах; безопаснее остановиться и показать общий отчёт.
**Следствия:** best-effort допускается только явным `--continue-on-error`; отчёт
различает `updated / rolled_back / failed / untouched`.

## D-008 · Двухфазность всех мутаций

**Дата:** 2026-08-23
**Решение:** probe, init, start, integrate, abort/cleanup, heal, upgrade, reinit,
rollback, uninstall и любая будущая control-plane мутация выполняются только по
exact plan id с drift-check. Внутри одобренного run спецификация и manifest
задают ограниченный capability envelope для worker; выход за него требует plan.
**Почему:** прямые команды разрушали бы единый safety contract именно в самых
опасных операциях.
**Следствия:** у rollback есть исходный apply/backup id; preview показывает
точные изменения, а повторное применение того же plan id идемпотентно.

## D-009 · Идентичность поставки

**Дата:** 2026-08-23
**Решение:** semantic version недостаточно; каждая поставка имеет immutable
`bundle_id`, content hash, source commit и release manifest shipped-файлов.
**Почему:** локально изменённые сборки могут иметь одинаковую версию, а upgrade
должен доказуемо знать историю каждого файла.
**Следствия:** install manifest хранит bundle provenance и transaction ids;
`clean_overwrite` допустим только для хеша из известного release manifest.

## D-010 · Стековые адаптеры — данные, а не код

**Дата:** 2026-08-23
**Решение:** адаптер стека — версионируемый декларативный манифест (detect,
capabilities, `surface`, пороги, prerequisites). Встроенные адаптеры
поставляются в том же формате и грузятся тем же путём, что пользовательские.
Новый стек заводится манифестом, без патча оркестратора.
**Почему:** реальный набор стеков — PHP, Node, Bun, React, Rust, Python и что-то
ещё через полгода. Если каждый стек требует кода и отдельного slice, инструмент
застынет на наборе дня релиза. Привилегированный путь для встроенных адаптеров
превращает чужой манифест в гражданина второго сорта.
**Следствия:** slice 4A строит схему и generic-режим до любых конкретных стеков;
референсы в 4B выбираются по осям различий, а не по списку фреймворков; в ядре
запрещены ветки по имени стека, и это проверяется тестом (AC-ST-06);
пользовательский адаптер всегда `customized` и не перезаписывается upgrade.

## D-011 · Внешняя поверхность вместо «поднять приложение»

**Дата:** 2026-08-23
**Решение:** адаптер объявляет `surface`: `http` / `cli` / `library` / `tui` /
`none`. Для каждого вида определено, как поднять, как обратиться, как понять
готовность и как погасить. При `none` внешняя приёмка честно недоступна и
результат получает пониженный штамп верификации.
**Почему:** роль QA у Мартина проверяет только снаружи. Web-only формулировка
`serve` отменяет внешнюю приёмку для Rust-крейта, CLI и библиотеки — то есть
убивает главный инвариант системы на половине стеков.
**Следствия:** `serve` перестаёт быть отдельной capability общего назначения и
становится реализацией `surface: http`; AC-GATE-05 и AC-ST-08 проверяют оба
конца спектра.

## D-012 · Scope capability, граф `serve` и барьер `contract`

**Дата:** 2026-08-23
**Решение:** у capability есть `scope: package | repo`; repo-scoped барьеры
обязательны при кросс-пакетном изменении. `serve` объявляет зависимости
поверхностей, а repo-level `serve` перекрывает package-level. В набор барьеров
добавляется `contract` — между `unit` и `e2e`.
**Почему:** проверено на `../iladno` (Symfony API + React-админка + корневые e2e
+ pytest деплоя). Три поломки модели «одна capability = один пакет»:
корневые `tests/e2e` и `tests/deployment` не принадлежат пакетам и теряются при
маршрутизации; e2e админки требует поднятой цепочки `mysql → symfony → traefik`;
а изменение формы JSON проходит phpunit, vitest, phpstan и deptrac зелёными и
ловится только самым дорогим барьером — который поэтому будут пропускать, оставив
штамп `verified: unit+static`, формально правдивый и практически лживый.
**Следствия:** slice 4D получает scope, граф `serve` и `contract`;
AC-ST-09, AC-GATE-07, AC-GATE-08. Эталонный mixed-fixture строится по образцу
iladno. При отсутствии `contract` штамп обязан называть непроверенную границу.

## D-013 · Существующая инфраструктура проекта имеет приоритет

**Дата:** 2026-08-23
**Решение:** `inspect` обнаруживает и переиспользует существующие скрипты подъёма
стека и symlink-алиасы instruction-файлов; коллизии имён показываются в change
plan и блокируют apply до разрешения.
**Почему:** в `../iladno` уже есть `./swarm-start.sh` (compose-стек, не рой
агентов — но имя занято) и `CLAUDE.md -> AGENTS.md`. Незамеченный symlink
означает managed-блок, записанный дважды в одни байты, и два fingerprint на один
файл, из-за чего `upgrade` увидит несуществующий drift.
**Следствия:** AC-CP-14 и AC-HOST-08; instruction-пути резолвятся по inode или
каноническому пути до записи; инструмент не создаёт файлы с занятыми именами.

## D-014 · Бюджет инструкций блокирует установку

**Дата:** 2026-08-23
**Решение:** `inspect` меряет весь instruction budget хоста, а не только свой
блок. Занято > 90% или лимит превышен — `apply` отказывается до разрешения
человеком. Установка «всё равно» записывает в install manifest известный дефект
«блок может не читаться».
**Почему:** в `/home/popovalpe/www/esia/msh-nto` `AGENTS.md` весит 44 626 байт —
на 36% больше известного лимита Codex сам по себе. Managed-блок там может не
прочитаться никогда, а инструмент будет считать себя установленным. Молчаливый
отказ, замаскированный под успех, — худший исход из возможных.
**Следствия:** AC-HOST-09; пороги 60% / 90%; варианты разрешения инструмент
предлагает, но не выбирает.

## D-015 · Провенанс возможностей и границ

**Дата:** 2026-08-23
**Решение:** capability различает `declared` (объявлена проектом) и `inferred`
(выведена из конфига); `inferred` не идёт в полосу без подтверждения. Нечитаемый
или внешний CI — `unknown`, не «проверок нет». Границы пакетов задаются
манифестами и явными путями. Добавляется барьер `generate`.
**Почему:** проверено на двух реальных проектах. В `msh-nto` `composer.json`
вообще без `scripts`, но с `phpunit.xml.dist` — команда выводится догадкой; а
весь `.gitlab-ci.yml` там сводится к `include` из чужого репозитория, то есть
настоящий пайплайн нечитаем. В `playflowb2b` `sdk/{js,php,python}` — публикуемые
артефакты без единого манифеста, а `docs-site` генерируется из OpenAPI бэкенда,
и протухшая генерация не роняет ни один тест.
**Следствия:** AC-ST-10, AC-ST-11, AC-ST-12, AC-GATE-09; capability хранит путь и
строку источника обнаружения; читаемый граф джобов CI предлагается как готовое
определение порядка барьеров.

## D-016 · `shared-repo` проверяет игнорирование, а не индекс

**Дата:** 2026-08-23
**Решение:** каждый устанавливаемый путь проверяется через `git check-ignore`;
правило добавляется в `.git/info/exclude`, а не в общий `.gitignore`.
Недостижимое игнорирование — blocking finding. Публикуемый артефакт повышает
профиль.
**Почему:** в `msh-nto` `AGENTS.md` в состоянии `??` — untracked, но не
игнорируется: один `git add .` уводит локальные инструкции вместе с нашим блоком
в общий репозиторий команды. «Сейчас не в индексе» гарантией не является.
**Следствия:** AC-SAFE-09, AC-SAFE-10, AC-ROLE-07.

## D-017 · Петля доработки и накопление между прогонами

**Дата:** 2026-08-23
**Решение:** отказ на приёмке возвращает run в работу по определённому переходу с
структурно зафиксированной причиной и собственными тормозами. По итогам прогонов
накапливаются причины отказов, статистика барьеров и дырявые места спецификаций;
N повторов одного класса замечаний дают **предложение** завести барьер или
правило роли — предложение, а не автоприменение.
**Почему:** самый частый реальный исход приёмки — «почти, переделай вот это», а в
автомате состояний ребра назад не было вовсе. При этом причина отказа — это
единственный настоящий внешний сигнал от человека, то есть ровно то, что делает
итерацию легитимной по правилу из статьи о циклах. Без накопления агент будет
наступать на одни грабли столько раз, сколько запусков.
**Следствия:** AC-SAFE-11, AC-LEARN-01–03; автомат состояний фазы 3 обязан
содержать переходы доработки; 1b.10 получает обратный поток в базу знаний;
ноль уроков — валидный результат, квоты нет.

## D-018 · Фаза 3 — точка выхода, а не только выбор архитектуры

**Дата:** 2026-08-23
**Решение:** фаза 3 дополнительно выдаёт вилку трудоёмкости по группам слайсов и
явно рассматривает исходы «строим только 1A–1B», «строим до 2C», «берём
swarm-forge как есть», «не строим ничего». Решение об объёме принимает владелец.
**Почему:** план был устроен так, будто инструмент точно будет построен, и не
содержал ни оценки стоимости, ни точки выхода. Фаза 3 — последний момент, когда
цена видна, а реализация не начата. Это тот же профиль 0, применённый к самому
инструменту: план требует такой фильтр от конвейера, логично применить его к себе.
**Следствия:** раздел «Оценка трудоёмкости и точка выхода» в файле фазы 3 с
четырьмя чекбоксами; решение об объёме записывается сюда же отдельной записью.
